## 1. What it is

**Agent protocols** are open standards that define *how* AI agents connect to the
outside world and to each other. The flagship is the **Model Context Protocol
(MCP)** — introduced by Anthropic in late 2024 — which standardizes how an
LLM/agent ("host") discovers and calls **tools**, reads **resources** (data), and
uses **prompts** exposed by external **servers**. Adjacent protocols — **A2A**
(Agent-to-Agent, Google), **ACP** (Agent Communication Protocol) — standardize how
*independent agents* discover and delegate to each other.

It exists to kill the **M×N integration problem**. Before MCP, every agent
framework needed a custom integration for every tool/data source — *M* agents ×
*N* tools = a combinatorial mess of bespoke glue. MCP makes it *M+N*: build one
MCP server for your tool and *any* MCP-compatible client can use it; build one
client and it can use *any* MCP server. It is, in Anthropic's framing, "a USB-C
port for AI applications."

## 2. Why employers want it

Section 11 ranks this #32 and flags it **rising fast** — named at Anthropic FDE
(S4), GE Vernova (S30), Deloitte (S29). It's *early-but-accelerating*, which makes
it a real differentiator now. The signal:

- **You build the interoperability layer.** You can expose internal systems
  (databases, APIs, file stores) as MCP servers that any agent can safely use —
  the connective tissue of agentic products.
- **You're current.** MCP went from announcement to broad adoption (OpenAI, Google,
  Microsoft, the major IDEs and agent frameworks) in under a year. Knowing it
  signals you track the frontier.
- **You understand agent interop.** Multi-agent systems need a way for agents to
  discover and delegate to each other (A2A/ACP); you can design those topologies.
- **You design for safety at the protocol boundary.** Tool permissions, sandboxing,
  and injection defense at the MCP layer (ties to #19) are exactly the hard part.

## 3. Mental model

**MCP is a client–server protocol (JSON-RPC 2.0) with three core primitives.**

```
   HOST (Claude Desktop / IDE / your agent app)
     └── MCP CLIENT (one per server connection)  ◄── JSON-RPC 2.0 ──►  MCP SERVER
                                                  (stdio | Streamable HTTP/SSE)
   SERVER EXPOSES three primitives:
     • TOOLS      — functions the model can CALL (model-controlled): query_db(sql), send_email(...)
     • RESOURCES  — data the host can READ (app/user-controlled): file://, db://table, GET-like
     • PROMPTS    — reusable templated workflows (user-controlled): "/summarize-ticket"

   Handshake: client/server exchange CAPABILITIES → client discovers what's available
              (tools/list, resources/list) → model calls tools/get resources as needed.

   ──────── A2A / ACP (a DIFFERENT layer): agent ◄──► agent ────────
     each agent publishes an "Agent Card" (skills, endpoint, auth);
     agents discover, then delegate TASKS to one another (peer collaboration),
     vs MCP's agent → tool/data relationship.
```

**Distinctions to keep straight:**

- **MCP = agent ↔ tools/data** (vertical: an agent reaching down to capabilities).
  **A2A/ACP = agent ↔ agent** (horizontal: agents collaborating as peers). They're
  complementary, not competitors.
- **The three MCP primitives differ by *who controls them*:** *tools* are
  **model-controlled** (the LLM decides to call them), *resources* are
  **application/user-controlled** (the host decides what context to load), *prompts*
  are **user-controlled** (the user invokes them, e.g. a slash command). Getting
  this right is the design crux.
- **Transports:** **stdio** (local subprocess — the server runs as a child process,
  great for local tools), **Streamable HTTP / SSE** (remote servers over the
  network). Same JSON-RPC messages, different pipe.
- **Why JSON-RPC + capability discovery:** the host doesn't hard-code a server's
  abilities — it *asks* (`tools/list`) and the model gets typed schemas at runtime.
  This dynamic discovery is what makes M+N work.

**Security is first-class and non-optional.** An MCP server is, by design, granting
an LLM the ability to *act* — so least-privilege tool scopes, sandboxing,
authentication (OAuth for remote servers), human approval for dangerous actions,
and defense against tool-poisoning / prompt-injection through resource content
(#19) are core to building one responsibly.

## 4. The landscape

**MCP**
- **Spec & SDKs** (Anthropic-led, now an open standard): official SDKs in
  **Python**, **TypeScript**, **Java/Kotlin**, **C#**, **Go**, **Rust**, **Swift**.
- **FastMCP** (Python) — the ergonomic high-level way to build servers
  (decorators); now largely folded into the official SDK.
- **Hosts/clients:** Claude Desktop & Claude Code, OpenAI Agents SDK & ChatGPT,
  Google (Gemini), Microsoft Copilot Studio, Cursor, VS Code, Windsurf, Zed,
  Cline, and most agent frameworks (LangChain/LangGraph, LlamaIndex, CrewAI).
- **Server ecosystem:** reference servers (filesystem, git, fetch, memory,
  Postgres, Slack, GitHub) + thousands of community/vendor servers; registries
  (mcp.so, Smithery, PulseMCP, the official registry).
- → in repo: [`../07.frameworks/mcp/`](../07.frameworks/mcp/) and
  [`../08.claudecode/`](../08.claudecode/).

**Agent-to-agent protocols**
- **A2A** (Agent2Agent, Google → Linux Foundation) — agents publish **Agent Cards**
  (capabilities, endpoint, auth) and delegate **tasks** to each other over
  HTTP/JSON-RPC/SSE. For cross-vendor multi-agent collaboration.
- **ACP** (Agent Communication Protocol, IBM/BeeAI / Linux Foundation) — REST-based
  agent messaging/discovery.
- **AGNTCY / others** — emerging interop efforts. Space is young and consolidating.

**Related standards:** OpenAPI/function-calling schemas (the pre-MCP way; MCP
builds on JSON Schema for tool definitions), OAuth 2.1 (remote-server auth).

**Tradeoffs / when to use what:**
- Exposing *your* tool/data to many agents → build an **MCP server** (write once,
  any client uses it).
- An agent needs to *use* tools → be an **MCP client/host**.
- Independent agents must *collaborate/delegate* → **A2A/ACP** (on top of, not
  instead of, MCP).
- Just one app, one tool, no reuse → a plain function-call may be simpler than a
  full server. MCP's payoff is *reuse and interoperability*; for a closed one-off
  it can be overkill.
- **Maturity caveat:** the ecosystem is fast-moving (spec revisions, evolving
  auth/security guidance) — pin versions and follow the security advisories.

## 5. Worked example

A complete, runnable **MCP server** exposing a tool, a resource, and a prompt using
the official Python SDK's high-level `FastMCP` API — the canonical "build a server"
artifact. Any MCP host (Claude Desktop/Code, Cursor, etc.) can then discover and
use it.

```python
"""weather_server.py — a minimal MCP server: one tool, one resource, one prompt.
Run (stdio): pip install "mcp[cli]" ; python weather_server.py
Register it in an MCP host (e.g. Claude Desktop config) to use it.
"""
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")          # the server's name, surfaced to clients

# --- TOOL: model-controlled. The LLM decides to CALL this. Typed args + docstring
#     become the schema the host advertises via tools/list. ---
@mcp.tool()
def get_forecast(city: str, days: int = 1) -> str:
    """Get a (stub) weather forecast for a city.

    Args:
        city: name of the city.
        days: how many days ahead (1-7).
    """
    if not 1 <= days <= 7:
        raise ValueError("days must be 1-7")   # errors surface back to the model
    # In production: call a real weather API here (with least-privilege creds).
    return f"{city}: sunny, 22C for the next {days} day(s). [stub data]"

# --- RESOURCE: application/user-controlled. The HOST reads this as context,
#     addressed by a URI template. Not called by the model — loaded by the app. ---
@mcp.resource("weather://cities")
def known_cities() -> str:
    """List of cities this server can serve (read as context)."""
    return "Paris, Tokyo, New York, Sydney"

# --- PROMPT: user-controlled. A reusable templated workflow the user invokes
#     (e.g. a slash command in the host UI). ---
@mcp.prompt()
def trip_weather(city: str) -> str:
    """Generate a prompt asking for a travel weather briefing."""
    return (f"Give me a concise weather briefing for a trip to {city}: "
            f"call get_forecast for the next 3 days and summarize what to pack.")


if __name__ == "__main__":
    mcp.run()        # defaults to stdio transport; use transport="streamable-http" for remote
```

The whole protocol is visible here: **one server** exposes a *tool* the model can
call, a *resource* the host can read, and a *prompt* the user can invoke — each
distinguished by *who controls it*. Because it speaks MCP (JSON-RPC over stdio),
*any* MCP client discovers these via capability negotiation and uses them with no
bespoke integration. That M+N reuse — write the server once, every agent benefits —
is the entire point. Security note: a real `get_forecast` would use least-privilege
credentials and the host would gate side-effecting tools behind user approval.

## 6. How to learn it

**Beginner (weeks).** Install an MCP host (Claude Desktop/Code), connect a
reference server (filesystem/git), and watch the tool/resource discovery happen.
Read the MCP spec's core concepts (host/client/server, the three primitives,
transports). *Milestone:* you can explain MCP's M+N value and the tool/resource/
prompt distinction.

**Job-ready (1–3 months).** Build an MCP **server** exposing a real internal tool
and data source (the example above, scaled up) with proper input validation and
error handling; build/configure an MCP **client** in an agent; use both stdio and
Streamable HTTP transports; add auth for a remote server. Understand A2A vs MCP.
*Milestone:* a deployed MCP server that a real agent uses, with auth and
least-privilege tool scopes.

**Expert.** Design secure MCP deployments (sandboxing, OAuth, approval gates,
defense against tool-poisoning/injection); architect multi-agent systems with
**A2A/ACP** delegation on top of MCP tool access; reason about versioning,
discovery/registries, and the evolving spec; contribute servers/SDK work.
*Milestone:* you own the agent-interop layer of a product and can defend its
security model.

## 7. Interview signals

What's probed: do you understand the protocol, *why* it exists, and its security
implications?

**Q: "What problem does MCP solve?"**
Strong answer: the **M×N integration explosion** — every agent needing custom glue
for every tool/data source. MCP standardizes the interface (JSON-RPC, capability
discovery, tools/resources/prompts) so it becomes **M+N**: one server works with
any client and vice-versa. Analogy: a "USB-C port for AI."

**Q: "MCP vs A2A — what's the difference?"**
Strong answer: **MCP** connects an agent *down* to tools and data (agent ↔
tool/resource). **A2A** connects agents *across* to each other as peers (agent ↔
agent, via Agent Cards + task delegation). They're complementary layers — an agent
can use MCP for its tools *and* A2A to delegate to other agents.

**Q: "Walk me through the three MCP primitives."**
Strong answer: **tools** are model-controlled (the LLM decides to call them, like
function calling); **resources** are application/user-controlled data the host
loads as context (addressed by URI); **prompts** are user-controlled reusable
templated workflows (e.g. slash commands). The distinguishing axis is *who
controls invocation*, which matters for both UX and security.

**Q: "What are the security risks of MCP and how do you mitigate them?"**
Strong answer: you're granting an LLM the ability to *act*, so risks include
prompt injection via resource content, tool poisoning (malicious tool
descriptions), over-broad permissions, and unauthenticated remote servers.
Mitigate with least-privilege tool scopes, sandboxing, OAuth on remote servers,
human approval for side-effecting/destructive tools, validating tool inputs, and
treating resource content as untrusted data (ties to #19).
