# 01 · GPU Architecture — how a GPU is built, and why it's fast

> The mental model you need before writing a single kernel. We build it from the
> ground up: why GPUs look the way they do, the execution hierarchy (threads →
> warps → blocks → grid mapped onto cores → SMs → device), the memory hierarchy
> (registers → shared/L1 → L2 → global → host), and the two ideas that make it
> all pay off: **occupancy** and **latency hiding**.

---

## 1. The core intuition: throughput, not latency

A **CPU** is a *latency* machine. It spends most of its transistor budget making
*one* thread finish *one* instruction stream as fast as possible: deep
out-of-order pipelines, branch predictors, big multi-level caches, speculative
execution. A few fat cores, each very smart.

A **GPU** is a *throughput* machine. It spends its transistors on *many* simple
arithmetic units and assumes you have *thousands* of independent work items.
Instead of avoiding memory latency with caches and prediction, it *hides* it: when
one group of threads stalls on a memory load, the hardware instantly switches to
another group that's ready to compute. With enough threads in flight, the
arithmetic units never go idle.

| | CPU | GPU |
|---|---|---|
| Cores | ~8–64 fat cores | thousands of thin "CUDA cores" (lanes) |
| Per-core smarts | OoO, branch predict, big cache | in-order, SIMT, tiny cache/thread |
| Optimizes | latency of one thread | throughput of many threads |
| Memory strategy | avoid latency (caches) | hide latency (oversubscribe threads) |
| Peak FP32 | ~1 TFLOP | ~30–80 TFLOP (consumer/datacenter) |
| Memory BW | ~50–100 GB/s (DDR) | ~1–3 TB/s (HBM/GDDR) |

The consequence for you as a programmer: **expose massive parallelism** and
**feed the memory system efficiently**. Every optimization in this section is one
of those two things.

The roofline picture (developed fully in `06.optimization-patterns.md`): a kernel
is either **compute-bound** (limited by FLOP/s) or **memory-bound** (limited by
GB/s). Most deep-learning kernels — elementwise ops, softmax, layernorm,
attention — are *memory-bound*, which is why fusion (section 05) and coalescing
(section 06) matter more than raw FLOPs.

## 2. The execution hierarchy (software side)

CUDA exposes a three-level hierarchy you choose when you launch a kernel:

```
              grid                         (the whole launch)
        ┌───────────────┐
        │ block  block  │                  blocks run independently,
        │ block  block  │                  in any order, on any SM
        │ block  block  │
        └───────────────┘
              │  one block ↓
        ┌───────────────┐
        │ thread thread │                  threads in a block share fast memory
        │ thread thread │                  and can synchronize (__syncthreads)
        └───────────────┘
              │  32 threads ↓
        ┌───────────────┐
        │ a single WARP │                  32 threads issued in LOCKSTEP (SIMT)
        └───────────────┘
```

- **Thread** — the finest unit; runs your kernel body once, with a unique index.
- **Block** (a.k.a. *cooperative thread array*, CTA) — a group of threads (up to
  1024) that run on **one SM**, share that SM's **shared memory**, and can
  **synchronize** with `__syncthreads()`. Blocks are the unit of cooperation.
- **Grid** — all the blocks of one kernel launch. Blocks are *independent*: the
  runtime may run them in any order, concurrently or serially, which is what lets
  the same binary scale from a laptop GPU to a datacenter one.

Threads and blocks can be 1-, 2-, or 3-dimensional (a convenience for mapping
onto vectors, matrices, volumes). Indexing math is identical regardless:

```
global_id_x = blockIdx.x * blockDim.x + threadIdx.x
```

You will write that line, or `cuda.grid(1)` / `tl.program_id(0)`, in essentially
every kernel — see `03.numba-cuda/01.vector_add.py`.

### The warp / wavefront — the real unit of execution

The block is the *programming* unit; the **warp** is the *hardware* unit. The SM
does not schedule individual threads — it schedules **warps of 32 threads**
(AMD calls it a **wavefront**, historically 64 lanes). All 32 threads of a warp
execute **the same instruction at the same time** on different data — this is
**SIMT** (Single Instruction, Multiple Threads), NVIDIA's name for lockstep SIMD
with per-lane masking.

Two consequences dominate kernel performance:

1. **Warp divergence.** If threads in a warp take different branches of an
   `if`, the warp executes *both* paths with the inactive lanes masked off —
   serializing the branches. Divergent control flow within a warp is the classic
   GPU performance bug. (Branches that are uniform across a warp are free.)

2. **Coalescing.** When the 32 lanes of a warp access memory, the hardware
   tries to merge them into as few 32/64/128-byte transactions as possible. If
   the lanes touch consecutive addresses (`A[tid]`), one transaction serves the
   whole warp — *coalesced*, full bandwidth. Strided or scattered accesses need
   many transactions — wasted bandwidth. (Section 06.)

Modern NVIDIA hardware adds **independent thread scheduling** (Volta+), so
threads in a warp have their own program counters and divergence is more
forgiving — but coalescing and warp-uniform branches still rule performance.

## 3. The hardware (device side)

```
GPU device
 ├── L2 cache  (a few MB, shared by ALL SMs)
 ├── Global memory  (HBM/GDDR, 8–192 GB, ~1–3 TB/s) ── off-chip DRAM
 └── many Streaming Multiprocessors (SMs), e.g. 80–144:
        each SM:
          ├── warp schedulers (issue ready warps each cycle)
          ├── CUDA cores  (FP32/INT ALUs — the "lanes")
          ├── Tensor Cores  (matrix-multiply-accumulate units, for fp16/bf16/…)
          ├── register file  (huge: ~64K 32-bit registers, partitioned per thread)
          ├── shared memory / L1  (configurable split, ~100–228 KB)
          └── special-function units (exp, sin, rsqrt), load/store units
```

- **SM (Streaming Multiprocessor)** — the GPU's fundamental processor. A GPU is
  basically *N copies of an SM* plus a shared L2 and memory controllers. Each SM
  runs many warps concurrently and switches between them every cycle to hide
  latency. When you launch a grid, blocks are distributed across SMs; an SM holds
  several resident blocks at once if resources allow.
- **CUDA cores** — the scalar ALU lanes. A warp's 32 threads map onto these.
- **Tensor Cores** — dedicated units that do a small matrix-multiply-accumulate
  (`D = A·B + C`) per instruction, the reason fp16/bf16 GEMMs and attention are
  an order of magnitude faster than FP32. Triton's `tl.dot` and cuBLAS target
  them; see `04.triton/03.matmul.py`.

## 4. The memory hierarchy — fast & tiny → slow & huge

This is the most important diagram in GPU programming. Latency and bandwidth
change by **orders of magnitude** as you move down it; the entire optimization
game is keeping data high in this pyramid.

```
       ┌──────────────────────────────────────────────┐  fastest, smallest
       │ Registers       per-thread, ~1 cycle          │  (per thread)
       ├──────────────────────────────────────────────┤
       │ Shared memory / L1   per-block, ~20–30 cycles │  (per SM, ~100–228 KB)
       │   programmer-managed scratchpad (shared mem)  │
       ├──────────────────────────────────────────────┤
       │ L2 cache        device-wide, ~200 cycles      │  (a few MB)
       ├──────────────────────────────────────────────┤
       │ Global memory   HBM/GDDR, 400–800 cycles      │  (GBs, ~1–3 TB/s)
       ├──────────────────────────────────────────────┤
       │ Host (CPU) RAM  over PCIe/NVLink, µs latency  │  slowest, biggest
       └──────────────────────────────────────────────┘
```

- **Registers** — private to each thread, the fastest storage. Your loop
  accumulator (`acc` in the matmul kernels) lives here. Registers are a *finite*
  resource per SM: more registers per thread → fewer threads can be resident →
  lower occupancy (see §5). Spilling registers to "local memory" (actually
  global) is a silent performance killer.
- **Shared memory** — a programmer-managed **scratchpad** physically on the SM,
  shared by all threads in a block, ~100× faster than global. You *explicitly*
  stage data here to reuse it across threads. This is the engine of **tiling**
  (`03.numba-cuda/03.matmul_tiled.py`): load a tile once from global into shared,
  let the whole block reuse it. Shared memory is banked (32 banks); conflicting
  accesses serialize — **bank conflicts** (section 06).
- **L1** — on most architectures shares physical SRAM with shared memory; you can
  configure the split. Caches global accesses automatically.
- **L2** — a single cache for the whole device; the last line of defense before
  the long trip to DRAM. Grouped tile ordering (the `GROUP_M` trick in the Triton
  matmul) exists to improve L2 reuse.
- **Global memory** — the big HBM/GDDR pool where your tensors live. High
  bandwidth but high latency; the target of *coalescing*. Crossing it is what you
  pay for, so fused kernels minimize the number of trips.
- **Host memory** — CPU RAM, reached over PCIe (~16–64 GB/s) or NVLink. Copies
  here are expensive; **pinned (page-locked) memory** + **async copies** overlap
  them with compute (section 05).

There are also **constant** and **texture** memories (small, cached, read-only,
good for broadcast/spatial-locality data) — niche for DL, mentioned for
completeness.

## 5. Occupancy — keeping the SM full

**Occupancy** = (resident warps on an SM) / (max warps the SM supports). It is a
*proxy* for how much latency-hiding parallelism the SM has available. Each SM has
a fixed budget of three resources, and a block consumes some of each:

- **Registers** — `registers/thread × threads/block`.
- **Shared memory** — bytes your block declares.
- **Warp/block slots** — hardware caps (e.g. 64 warps, 32 blocks per SM).

Whichever runs out *first* caps how many blocks fit, and thus occupancy. A kernel
that uses too many registers or too much shared memory per block runs *fewer*
blocks per SM, leaving the warp schedulers with too little to switch to.

Key nuances (this is widely misunderstood):

- **Higher occupancy is not always faster.** It is necessary to *hide latency*,
  but past the point where latency is hidden, more occupancy gives nothing — and
  a lower-occupancy kernel that keeps more data in registers/shared memory can
  win. Volkov's classic result: you can hit peak with surprisingly low occupancy
  if each thread does enough independent work (instruction-level parallelism).
- The goal is **enough** parallelism to hide memory latency, *and* efficient
  memory access, *and* enough work per thread. Occupancy is one dial, not the
  objective.

The CUDA Occupancy Calculator / `cudaOccupancyMaxActiveBlocksPerMultiprocessor`
tells you the achievable occupancy for a given block size and resource usage.

## 6. Latency hiding — the punchline

Put it together. A global-memory load costs ~500 cycles. A CPU would stall. The
GPU instead:

1. The warp issues its load and is marked *not ready* (waiting on memory).
2. The warp scheduler immediately issues an instruction from **another** ready
   warp on the same SM.
3. With dozens of warps resident, by the time we cycle back to the first warp,
   its data has arrived — the latency was completely **hidden** behind other
   warps' compute.

This is why GPUs *want* to be oversubscribed with threads: parallelism isn't just
for doing more work, it's the mechanism that hides memory and pipeline latency.
"A GPU is a latency-hiding machine that happens to do a lot of arithmetic."

A useful rule of thumb (Little's law): to hide latency `L` with throughput `T`
you need `L × T` operations in flight. That is exactly what thousands of resident
threads provide.

## 7. Putting numbers on it (orders of magnitude)

| Operation | Approx latency | Approx bandwidth |
|---|---|---|
| Register access | ~1 cycle | — |
| Shared memory | ~20–30 cycles | ~10+ TB/s on-chip |
| L2 hit | ~200 cycles | several TB/s |
| Global (HBM) | ~400–800 cycles | ~1–3 TB/s |
| PCIe H2D/D2H | microseconds | ~16–64 GB/s |
| NVLink (GPU↔GPU) | sub-µs | ~300–900 GB/s |

(Exact numbers vary by architecture — Ampere/Hopper/Ada differ. Treat these as
the *shape* of the cliff, which is what your code must respect.)

## 8. Vendor terminology cheat-sheet

| Concept | NVIDIA / CUDA | AMD / ROCm | Intel / SYCL |
|---|---|---|---|
| Compute unit | SM | CU (Compute Unit) | EU / Xe-core |
| Lockstep group | warp (32) | wavefront (64) | sub-group |
| Block | thread block / CTA | workgroup | work-group |
| Scratchpad | shared memory | LDS (Local Data Share) | local memory |
| Thread index | threadIdx | local id | local id |

This curriculum uses CUDA/NVIDIA terms (and Numba/Triton, which target them), but
the architecture and the optimization principles transfer directly.
