# 12 · Fine-Tuning & Model Adaptation

> Skill #12 (Tier 2 — Important). *Full/PEFT (LoRA/QLoRA), SFT, instruction
> tuning, data curation.* ~50% — R1 calls LLM fine-tuning "the most sought-after
> specialized skill in enterprise AI." See the rationale in
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

Adapting a pretrained model to a domain or task: **full fine-tuning**,
**parameter-efficient fine-tuning (PEFT)** — chiefly **LoRA / QLoRA** —
supervised fine-tuning (**SFT**), instruction tuning, preference tuning (DPO,
skill [`27`](27.rlhf-preference-optimization.md)), and the data curation that
makes or breaks it. And, crucially, **knowing when *not* to fine-tune** (often
RAG or prompting wins).

It exists to **squeeze quality/latency/cost beyond what prompting gives, and to
build differentiated models on proprietary data** — a custom tone, a domain
vocabulary, a structured-output format, or a small fast model that matches a big
one on your task.

## 2. Why employers want it

R1 names it the most sought-after specialized enterprise skill. The signal:

- **You can build a moat** — a model tuned on proprietary data that competitors
  can't prompt their way to.
- **You cut cost/latency** — fine-tune a small model to replace a big one on a
  narrow task.
- **You exercise judgment.** You know fine-tuning is often the *wrong* answer
  (knowledge → RAG; format → structured output/prompting), and you can say so.

## 3. Mental model

**Adapt vs. retrain.** You start from a pretrained model and nudge it, not train
from scratch. The spectrum of how much you touch:

```
prompt only ─► few-shot ─► RAG (add knowledge) ─► PEFT/LoRA ─► full fine-tune ─► (pretrain)
 cheapest, fastest to change                                      most expensive, most powerful
```

**The decision rule:** *behavior/format/style/latency* → fine-tune; *knowledge/
freshness* → RAG; *one-off* → prompt. Fine-tuning teaches the model **how to
respond**, not **what facts to know** — don't fine-tune to inject facts (it
hallucinates and goes stale); use RAG.

**LoRA — the key idea.** Full fine-tuning updates all $W$ (huge memory). LoRA
freezes $W$ and learns a tiny **low-rank update** $\Delta W = BA$ (with rank
$r \ll d$), so you train ~0.1–1% of the parameters:

$$
W' = W + \frac{\alpha}{r} B A, \qquad B \in \mathbb{R}^{d\times r},\; A \in \mathbb{R}^{r\times k}
$$

Only $A,B$ are trained; the adapter is a few MB and can be swapped per task.
**QLoRA** adds 4-bit **quantization** of the frozen base (NF4) so a large model
fits on one consumer GPU, with LoRA adapters trained in higher precision on top.

**The pipeline:** curate data (the dominant factor) → format into instruction/
chat pairs → pick method (LoRA/QLoRA/full) → train (small LR, few epochs, watch
for overfitting/catastrophic forgetting) → **eval** (skill [`07`](07.evaluation-llm-testing.md))
→ serve the adapter (skill [`16`](16.inference-optimization-serving.md)).

## 4. The landscape

**Methods.**

| Method | Trains | Memory | Use when |
|---|---|---|---|
| **Full FT** | all params | very high | small models, max quality, abundant compute |
| **LoRA** | low-rank adapters (~0.1–1%) | low | the default PEFT; swappable adapters |
| **QLoRA** | LoRA on a 4-bit base | lowest | large model on one GPU |
| **Prefix/Prompt/IA³ tuning** | tiny prompt/scale params | minimal | lightest-touch adaptation |
| **DoRA / rsLoRA** | LoRA variants | low | improved LoRA quality/stability |

**Training types.** **SFT** (supervised on input→output pairs; the workhorse) ·
**instruction tuning** (SFT on diverse instructions) · **preference tuning**
(**DPO**, ORPO, KTO — align to preferred outputs without a reward model; skill
[`27`](27.rlhf-preference-optimization.md)) · **continued pretraining** (more
domain text, unsupervised).

**Tools.** Hugging Face **PEFT** + **TRL** (`SFTTrainer`, `DPOTrainer`) +
**Transformers** + **bitsandbytes** (quant) + **Accelerate** (skill [`26`](26.hugging-face-ecosystem.md)) ·
**Unsloth** (fast, memory-lean) · **Axolotl** / **LLaMA-Factory** (config-driven
fine-tuning) · hosted fine-tuning (OpenAI, together, Vertex).

**Data curation (the real work).** Quality > quantity; diverse, clean,
deduplicated, correctly formatted pairs; avoid label noise and leakage; balance;
and a held-out eval set. A few thousand great examples beat a million mediocre
ones.

**Pitfalls.** Catastrophic forgetting (model loses general ability — keep LR low,
few epochs, mix in general data), overfitting (memorizes the train set), wrong
chat template (silent quality loss), and fine-tuning when RAG/prompting would
have sufficed.

## 5. Worked example

A **LoRA SFT** setup with Hugging Face PEFT + TRL — the standard, idiomatic way to
fine-tune an open model on instruction data. (Real runs need a GPU; the code is
correct and is the pattern interviewers expect.)

```python
"""lora_sft.py — LoRA supervised fine-tuning with PEFT + TRL (idiomatic)."""
import torch
from datasets import load_dataset
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig
from trl import SFTConfig, SFTTrainer

BASE = "meta-llama/Llama-3.2-1B"      # a small base for illustration

# 1. 4-bit quantized base (QLoRA): fits a large model on one GPU.
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)
tok = AutoTokenizer.from_pretrained(BASE)
tok.pad_token = tok.eos_token
model = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb, device_map="auto")

# 2. LoRA: train only small low-rank adapters on the attention/MLP projections.
lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],   # which weights get adapters
)

# 3. Instruction data formatted as chat (use the model's chat template!).
ds = load_dataset("databricks/databricks-dolly-15k", split="train[:1000]")
def fmt(ex):
    msgs = [{"role": "user", "content": ex["instruction"]},
            {"role": "assistant", "content": ex["response"]}]
    return {"text": tok.apply_chat_template(msgs, tokenize=False)}
ds = ds.map(fmt)

# 4. Train: small LR, 1 epoch -> adapt without catastrophic forgetting.
trainer = SFTTrainer(
    model=model,
    train_dataset=ds,
    peft_config=lora,
    args=SFTConfig(
        output_dir="out", num_train_epochs=1, per_device_train_batch_size=2,
        gradient_accumulation_steps=4, learning_rate=2e-4, bf16=True,
        logging_steps=10, dataset_text_field="text", max_seq_length=1024,
    ),
)
trainer.train()
trainer.save_model("out/adapter")     # a few MB — the LoRA adapter, swappable at serve time
```

The load-bearing choices: **QLoRA** (4-bit base) to fit memory, **LoRA on the
projection layers** to train ~1% of params, the **chat template** applied to the
data (a common silent bug if skipped), a **small LR + 1 epoch** to adapt without
forgetting, and saving a tiny **adapter** rather than a full model. Always
evaluate the adapter against a held-out set before shipping.

## 6. How to learn it

**Beginner (0–3 months).** Understand the prompt→RAG→PEFT→full spectrum and the
decision rule; LoRA-fine-tune a tiny model on a toy instruction set (Colab/
Unsloth). *Milestone:* a LoRA adapter you trained and can load.

**Intermediate / job-ready (3–9 months).** QLoRA a real open model on curated
domain data; apply the chat template correctly; eval against a held-out set and a
prompted baseline; try DPO. *Milestone:* a fine-tune that beats prompting on your
task, with evals proving it.

**Expert (9+ months).** Data-curation pipelines; preference tuning (DPO/ORPO);
avoid forgetting/overfitting; multi-adapter serving; decide fine-tune vs RAG vs
prompt rigorously per problem. *Milestone:* a production fine-tuned model with a
curated dataset, eval suite, and a serving story.

## 7. Interview signals

- **"When would you fine-tune vs RAG vs prompt?"** Behavior/format/style/latency
  → fine-tune; knowledge/freshness → RAG; one-off → prompt. The strongest signal
  is leading with *"often you shouldn't fine-tune."*
- **"Explain LoRA."** Freeze $W$; learn a low-rank $\Delta W = BA$ (rank $r\ll d$);
  train ~1% of params; swappable few-MB adapter. QLoRA = LoRA on a 4-bit base to
  fit memory.
- **"What dominates fine-tuning quality?"** Data — quality, diversity, clean
  formatting (right chat template), dedup, no leakage, held-out eval. A few
  thousand great examples beat a million mediocre ones.
- **"How do you avoid catastrophic forgetting?"** Low LR, few epochs, PEFT
  (smaller footprint), mix in general data, and evaluate general ability, not
  just the target task.
- **"How do you serve many fine-tunes?"** LoRA adapters swapped per request on a
  shared base (e.g. vLLM multi-LoRA) — far cheaper than many full models.
