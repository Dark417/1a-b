## 1. What it is

Fluency in **PyTorch** — the lingua franca of model work — to build, train, and
fine-tune neural networks: tensors and autograd, `nn.Module`, data loaders, the
training loop, optimizers/schedulers, mixed precision, checkpointing,
`torch.compile`, and GPU execution. Plus awareness of the wider stack (JAX for
research/performance, TensorFlow/Keras in legacy/enterprise).

It exists because **PyTorch is where models are actually written and trained.**
Even if you mostly call APIs, the moment you fine-tune, build a custom layer, run
inference on open weights, or debug a training run, you're in PyTorch.

## 2. Why employers want it

PyTorch leads the named frameworks (R1 37.7%); Mistral live-codes DL components
in it, Meta/NVIDIA require it. The signal:

- **You can go below the API.** Fine-tune, customize, and run open models, not
  just consume hosted ones.
- **You can read and modify model code.** The whole open ecosystem (Hugging Face,
  research repos) is PyTorch.
- **You debug training.** OOM, NaN loss, slow data loading, device mismatches —
  you fix them.

## 3. Mental model

PyTorch is **NumPy + autograd + GPU + neural-net building blocks.**

```
data ─► DataLoader ─► model(nn.Module) ─► loss
                                            │ loss.backward()  (autograd builds + walks the graph)
        optimizer.step() ◄── grads ◄────────┘
        optimizer.zero_grad()  (reset grads each step)
```

The canonical training loop — memorize this skeleton:

```
for epoch:
    for batch in loader:
        optimizer.zero_grad()         # 1. clear old gradients
        out  = model(x)               # 2. forward
        loss = loss_fn(out, y)        # 3. compute loss
        loss.backward()               # 4. backprop (autograd)
        optimizer.step()              # 5. update weights
```

Concepts to own cold: **tensors** (shape, dtype, device), **autograd**
(`requires_grad`, `.backward()`, `torch.no_grad()` for eval), **`nn.Module`**
(parameters, `forward`, `train()`/`eval()` modes — which toggle dropout/BN),
**device movement** (`.to(device)`; everything on the same device),
**broadcasting**, and the train/eval distinction (no grad + eval mode at
inference). Production extras: **mixed precision** (`autocast` + `GradScaler`,
~2× faster, less memory), **`torch.compile`** (graph capture + kernel fusion),
gradient clipping, LR schedulers, and **checkpointing** (save/restore
`state_dict`).

## 4. The landscape

**PyTorch ecosystem.** Core (`torch`, `torch.nn`, `torch.optim`,
`torch.utils.data`) · **`torch.compile`** (the default speedup) · **AMP** (mixed
precision) · **DDP/FSDP** (multi-GPU, skill [`24`](24.distributed-training.md)) ·
TorchScript/`torch.export` (deployment) · domain libs (torchvision, torchaudio).

**Higher-level wrappers.** **PyTorch Lightning** (removes loop boilerplate),
**Hugging Face Accelerate** (device/distributed glue), **Trainer/TRL** (HF
training loops, skills [`12`](12.fine-tuning-model-adaptation.md)/[`26`](26.hugging-face-ecosystem.md)),
Fabric, Composer.

**Other frameworks (when/why).** **JAX** (functional, `jit`/`vmap`/`grad`,
TPU/perf, research — Flax/Optax) · **TensorFlow/Keras** (enterprise, mobile/edge
via TFLite, some legacy) · **ONNX** (interchange/runtime for cross-framework
deployment).

**Tradeoffs.** PyTorch: dynamic graphs, best ecosystem, easiest to debug — the
default. JAX: fastest for research-scale training and custom transforms, steeper
curve. TF/Keras: strong deployment/edge story, less common for new LLM work.

**Tooling around it.** Experiment tracking (Weights & Biases, MLflow — skill
[`11`](11.mlops-llmops.md)), profiling (`torch.profiler`, Nsight), config
(Hydra), and reproducibility (seeding, `torch.use_deterministic_algorithms`).

## 5. Worked example

A complete, correct, CPU-fast PyTorch training loop with the production touches —
device handling, train/eval modes, scheduler, checkpointing, and mixed precision
(guarded so it works on CPU too). Idiomatic and runnable.

```python
"""train_loop.py — idiomatic PyTorch training loop. Seeded, CPU-fast, exit 0."""
import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(0)
torch.set_num_threads(1)                                  # CPU-fast for the demo

def get_device():
    if torch.cuda.is_available(): return torch.device("cuda")
    if torch.backends.mps.is_available(): return torch.device("mps")
    return torch.device("cpu")

device = get_device()

# Toy data: y = 1 if sum(x) > 0 else 0  (a learnable binary task).
X = torch.randn(512, 10)
y = (X.sum(1) > 0).long()
loader = DataLoader(TensorDataset(X, y), batch_size=32, shuffle=True)

model = nn.Sequential(nn.Linear(10, 32), nn.ReLU(), nn.Linear(32, 2)).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
sched = torch.optim.lr_scheduler.CosineAnnealingLR(opt, T_max=5)
loss_fn = nn.CrossEntropyLoss()
use_amp = device.type == "cuda"                          # mixed precision on GPU only
scaler = torch.cuda.amp.GradScaler(enabled=use_amp)

for epoch in range(5):
    model.train()                                        # enables dropout/BN training behavior
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        opt.zero_grad()
        with torch.autocast(device_type=device.type, enabled=use_amp):
            loss = loss_fn(model(xb), yb)
        scaler.scale(loss).backward()                    # scaled backprop (AMP-safe)
        scaler.unscale_(opt)
        nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # guard against exploding grads
        scaler.step(opt)
        scaler.update()
    sched.step()

    model.eval()                                         # eval mode: no dropout
    with torch.no_grad():                                # no graph -> faster, less memory
        acc = (model(X.to(device)).argmax(1).cpu() == y).float().mean().item()
    print(f"epoch {epoch}  acc {acc:.3f}  lr {sched.get_last_lr()[0]:.2e}")

torch.save(model.state_dict(), "model.pt")               # checkpoint the weights
print("saved checkpoint")
```

Every line is load-bearing for *production* training: `zero_grad` before
backward, `model.train()/eval()` toggling, `no_grad` at eval, grad clipping,
AMP guarded by device, a scheduler, and a `state_dict` checkpoint. This skeleton
scales — swap in a real dataset and model and add DDP/FSDP for multi-GPU.

## 6. How to learn it

**Beginner (0–3 months).** PyTorch's *60-Minute Blitz*; build tensors, autograd,
an MLP, and the training loop from scratch; train an MNIST CNN. *Milestone:* a
classifier you trained end to end with checkpointing.

**Intermediate / job-ready (3–9 months).** Custom `nn.Module`s and datasets;
mixed precision; `torch.compile`; LR schedules; profile and fix a slow loop;
fine-tune a small transformer. *Milestone:* the loop above, extended to a real
dataset, profiled and reproducible.

**Expert (9+ months).** Multi-GPU (DDP/FSDP); custom autograd/ops; memory and
throughput optimization; one project in JAX or TF for breadth. *Milestone:* you
can train a non-trivial model efficiently on multiple GPUs and reason about its
FLOPs/memory.

## 7. Interview signals

- **"Write a training loop."** zero_grad → forward → loss → backward → step;
  `train()`/`eval()`; `no_grad` at inference. They watch for the
  *forgotten-`zero_grad`* bug.
- **"What does `loss.backward()` do?"** Autograd walks the recorded computation
  graph applying the chain rule, accumulating `.grad` on leaf tensors; the
  optimizer then steps.
- **"Why `model.eval()` and `torch.no_grad()`?"** `eval()` switches dropout/BN to
  inference behavior; `no_grad()` stops graph building → less memory, faster. Both
  matter at inference.
- **"Your training is slow / OOMs. What do you check?"** Data-loading bottleneck
  (`num_workers`, pin_memory), batch size, mixed precision, gradient
  accumulation, `torch.compile`, and where tensors live (device mismatches).
- **"PyTorch vs JAX vs TF?"** PyTorch = default, dynamic, best ecosystem; JAX =
  functional/perf/TPU; TF/Keras = deployment/edge. Pick by team + target.
