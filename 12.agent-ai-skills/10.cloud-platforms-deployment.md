# 10 · Cloud Platforms & Deployment

> Skill #10 (Tier 1 — Core). *AWS/GCP/Azure, containers, IaC, CI/CD, scaling,
> cost control.* ~60% of sources — productionizing is the job. See the rationale
> in [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

Shipping AI systems on the cloud: **AWS / GCP / Azure** services, containers,
serverless, managed ML platforms (SageMaker / Vertex AI / Azure ML),
**infrastructure-as-code** (Terraform), CI/CD, secrets management, autoscaling,
and **cost control**.

It exists because **a model that only runs on your laptop has no value.**
Productionizing — getting the system to run reliably, securely, and affordably
where users can reach it — *is* the job for most applied AI roles.

## 2. Why employers want it

Deployment skill appears across nearly every applied posting (S1, S11, S13, S15,
S25, R1, R2). The signal:

- **You can take a prototype to production** — container, deploy, scale, monitor —
  not hand it off and hope.
- **You control cost.** GPU inference and LLM API spend are the dominant costs;
  you right-size, autoscale, cache, and batch.
- **You operate safely.** Secrets, IAM, networking, IaC, and reproducible
  deploys — not click-ops.

## 3. Mental model

Deployment is moving a workload up a ladder of **abstraction vs control**:

```
bare VM ─► container ─► orchestrated containers (K8s) ─► serverless ─► managed ML platform
 most control                                                          least ops
```

The decision tree for an AI workload:

- **Stateless API around a hosted model** (RAG, agents calling Claude/OpenAI) →
  containerized service on serverless/managed compute (Cloud Run, App Runner,
  Lambda, Container Apps). Cheap, autoscales, no GPU.
- **Self-hosted model inference** → GPU instance or GPU-backed container/K8s, with
  a serving engine (vLLM/TGI — skill [`16`](16.inference-optimization-serving.md)).
  GPU cost dominates; autoscale and batch aggressively.
- **Training/fine-tuning** → managed ML (SageMaker/Vertex/Azure ML) or a GPU
  cluster; spot/preemptible instances to cut cost.

**Cross-cutting primitives** every deploy needs: **compute** (VMs, containers,
serverless, GPUs), **storage** (object stores like S3/GCS, databases), **network**
(VPC, load balancers, ingress), **identity** (IAM, least privilege), **secrets**
(Secrets Manager / KMS — never in code), **IaC** (Terraform for reproducible
infra), **CI/CD** (build → test → deploy pipelines), and **observability**
(metrics, logs, traces).

**Cost levers** for AI specifically: right-size GPUs, autoscale to zero when idle,
spot/preemptible for fault-tolerant jobs, prompt caching + batching + model
selection for API spend (skill [`04`](04.llm-apis-prompt-engineering.md)),
and budgets/alerts so spend doesn't drift silently.

## 4. The landscape

**The three clouds (rough equivalents).**

| Need | AWS | GCP | Azure |
|---|---|---|---|
| Containers (serverless) | App Runner / Fargate | Cloud Run | Container Apps |
| Functions | Lambda | Cloud Functions | Azure Functions |
| Managed K8s | EKS | GKE | AKS |
| Managed ML | SageMaker | Vertex AI | Azure ML |
| Object storage | S3 | GCS | Blob Storage |
| GPU compute | EC2 (P/G) | GCE / GKE GPU | NC/ND VMs |
| Secrets | Secrets Manager | Secret Manager | Key Vault |

**Containers & orchestration.** Docker (package once, run anywhere) →
**Kubernetes** for scaling/GPU scheduling (skill [`21`](21.containers-kubernetes.md);
KServe/Ray Serve for model serving) → serverless containers for simpler cases.

**IaC & CI/CD.** **Terraform** (multi-cloud, declarative) / Pulumi /
CloudFormation; GitHub Actions / GitLab CI / Cloud Build for pipelines; image
registries; blue-green & canary deploys.

**Serving paths.** Hosted LLM API (no infra) · serverless container (CPU app) ·
GPU container + serving engine (self-hosted model) · managed endpoint
(SageMaker/Vertex). GPU-on-demand platforms (Modal, RunPod, Replicate, Baseten,
Together) sit between rolling-your-own and managed.

**Reliability.** Health checks, autoscaling policies, rate limiting, retries/
timeouts, graceful degradation/fallbacks, and multi-AZ. Plus monitoring +
alerting (skill [`11`](11.mlops-llmops.md)/[`22`](22.llm-observability-monitoring.md)).

## 5. Worked example

A production-shaped **Dockerfile + Terraform** for a stateless AI API (RAG/agent
service calling a hosted model) deployed to a serverless container platform — the
most common AI deployment. Correct and idiomatic; not GPU-bound.

```dockerfile
# Dockerfile — small, reproducible image for a FastAPI AI service.
FROM python:3.12-slim AS base
ENV PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
WORKDIR /app

# Install deps first (layer caching) — copy lockfile, then code.
COPY requirements.txt .
RUN pip install -r requirements.txt

COPY app/ ./app/
EXPOSE 8080
# Run as non-root; bind to the platform-provided port.
RUN useradd -m appuser && chown -R appuser /app
USER appuser
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

```hcl
# main.tf — deploy the image to Google Cloud Run (serverless, autoscaling).
# Secrets come from Secret Manager, never baked into the image.
resource "google_cloud_run_v2_service" "ai_api" {
  name     = "ai-api"
  location = "us-central1"

  template {
    scaling {
      min_instance_count = 0    # scale to zero when idle -> cost control
      max_instance_count = 10   # cap to bound spend under load
    }
    containers {
      image = "us-central1-docker.pkg.dev/${var.project}/svc/ai-api:${var.tag}"
      resources { limits = { cpu = "1", memory = "512Mi" } }

      env {
        name = "ANTHROPIC_API_KEY"
        value_source {
          secret_key_ref {                 # injected from Secret Manager at runtime
            secret  = google_secret_manager_secret.api_key.secret_id
            version = "latest"
          }
        }
      }
    }
  }
}

# Wire CI/CD (GitHub Actions): build image -> push to Artifact Registry ->
# `terraform apply` with the new tag. Repeatable, reviewable, rollback-able.
```

This captures the load-bearing production choices: small reproducible image,
**non-root** user, **secrets injected at runtime** (not in code or image),
**scale-to-zero** + a max cap for cost, declarative IaC, and a tag-driven CI/CD
deploy. For self-hosted model inference you'd swap Cloud Run for a GPU-backed
service (GKE + KServe, or Modal/Baseten) running vLLM/TGI.

## 6. How to learn it

**Beginner (0–3 months).** Containerize a FastAPI app; deploy to one serverless
platform (Cloud Run / App Runner); manage one secret; set a budget alert.
*Milestone:* a publicly reachable AI API you deployed, with secrets out of code.

**Intermediate / job-ready (3–9 months).** Terraform the infra; build a GitHub
Actions CI/CD pipeline; add autoscaling, health checks, and logging/metrics; do
one GPU deploy with a serving engine. *Milestone:* an IaC-managed, CI/CD-deployed
service with autoscaling and monitoring.

**Expert (9+ months).** Multi-environment (dev/stage/prod) IaC; canary/blue-green
deploys; cost optimization (spot, right-sizing, caching/batching); multi-region/
HA; security hardening (IAM, network policy). *Milestone:* you own a reliable,
cost-controlled production deployment others depend on.

## 7. Interview signals

- **"How would you deploy this RAG/agent service?"** Containerize → serverless
  container (CPU) or GPU service (self-hosted model); secrets via a manager; IaC;
  CI/CD; autoscaling; monitoring. Pick by hosted-vs-self-hosted model.
- **"Your inference bill is exploding. What do you do?"** Right-size/autoscale
  GPUs, scale to zero when idle, batch + continuous batching, quantize, cache
  prompts, pick a cheaper model, spot instances — and put budgets/alerts in place.
- **"Where do secrets go?"** A secrets manager (Secrets Manager/KMS/Key Vault),
  injected at runtime via IAM-scoped access — never in code, images, or env files
  in the repo.
- **"Why IaC?"** Reproducible, reviewable, versioned, rollback-able infra; no
  click-ops drift; the same infra in every environment.
- **"Serverless vs K8s for a model service?"** Serverless for stateless CPU apps
  and bursty traffic (no ops, scale to zero); K8s when you need GPU scheduling,
  fine control, or complex multi-service topologies.
