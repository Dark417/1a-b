# 05 · Mistral & Mixtral — sliding-window attention and sparse MoE

> **Intuition.** Mistral took the LLaMA backbone and asked two efficiency
> questions. (1) *Do you really need every token to attend to every other token?*
> → **sliding-window attention**: attend only to the last `W` tokens, but stack
> layers so information still propagates far. (2) *Do you need every parameter to
> fire on every token?* → **sparse Mixture-of-Experts**: have many FFN "experts"
> but route each token to only a couple. Together: more capacity, less compute.

---

## 1. Mistral-7B (Sept 2023)

LLaMA-style decoder (RMSNorm, RoPE, SwiGLU, **GQA**) plus:

### Sliding-Window Attention (SWA) — `10.sliding_window.py`
Each token attends only to itself and the previous `W − 1` tokens (Mistral
`W = 4096`). Per-layer the receptive field is `W`, but because attention stacks,
after `k` layers a token can be influenced by tokens up to `k·W` back — the
**effective context grows with depth** (≈ `W × num_layers`). Cost drops from
$O(n^2)$ toward $O(n\cdot W)$.

### Rolling buffer KV cache
With a fixed window you never need more than `W` cached keys/values, so the
**KV cache** (`08.kv_cache.py`) becomes a circular buffer of size `W` — constant
memory regardless of sequence length. Combined with **pre-fill chunking** for
long prompts. Mistral-7B (Apache-2.0) beat LLaMA-2-13B on most benchmarks.

---

## 2. Mixtral 8×7B (Dec 2023) and 8×22B (2024) — `07.moe.py`

A **Sparse Mixture-of-Experts (SMoE)** decoder. Replace each FFN with **8 expert
FFNs** + a **router** (a linear gate). For each token, the router scores the 8
experts; the **top-2** are selected, run, and their outputs combined weighted by
the (softmaxed) gate scores:

$$y = \sum_{i \in \text{top-2}(x)} \text{softmax}\!\big(g(x)\big)_i \cdot E_i(x)$$

**The key accounting:** "8×7B" has **47B total** parameters but only **~13B are
active** per token (2 experts of the FFN + the shared attention). You pay 13B-model
*compute* for 47B-model *capacity*. Attention is shared across experts (only the
FFN is sparse). Mixtral-8×22B scales this to **141B total / ~39B active**, 64k
context. Both Apache-2.0.

**Routing details that matter:**
- A **load-balancing auxiliary loss** discourages the router from collapsing onto
  a few experts (so all experts get trained) — see `07.moe.py`.
- Experts **specialize** somewhat (syntax/topic), though less interpretably than
  the name suggests.
- Serving is memory-hungry (all experts must be resident) but compute-cheap — a
  different tradeoff than a dense model.

## 3. Mistral-Nemo (July 2024)

A **12B dense** model (Mistral + NVIDIA), context **128k**, trained
quantization-aware (FP8). Introduces the **Tekken** tokenizer (tiktoken-based,
more efficient on code and many languages). Apache-2.0. Aimed at being a
drop-in, long-context 7B-class upgrade.

Other family members worth knowing: **Mistral Large** (closed flagship),
**Codestral** (code), **Mathstral**, **Mixtral-8x7B-Instruct**, **Ministral**
(edge). Mistral's hallmark is permissive licensing on strong open weights.

## 4. Strengths / limits

| | Sliding-window (Mistral-7B) | Sparse MoE (Mixtral) |
|---|---|---|
| Win | $O(n\cdot W)$ attention, constant KV cache | huge capacity at low active compute |
| Cost | far tokens only reachable via depth | all experts must fit in memory; routing imbalance risk |
| Use | long context on small hardware | best quality-per-FLOP when memory is available |
