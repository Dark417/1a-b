# 29 · Orchestration & Workflow Frameworks

> **Scope (from the ranked list):** multi-step LLM pipelines — LangGraph flows,
> Haystack pipelines, Flowise/Langflow, Burr, ControlFlow, DSPy — for composing
> applications with branching, retries, and state. *~20%* (S11, S29, S30). See
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

**Orchestration frameworks** are the tools for composing **multi-step LLM
applications** — graphs of LLM calls, tool invocations, retrieval steps, and
control logic with **branching, loops, retries, parallelism, and persistent
state**. Where a single agent loop (#06) is one model deciding its next action, an
orchestration framework is the *scaffold* that wires many such steps into a
reliable, observable, resumable pipeline.

It exists because **real products are not one LLM call.** A support assistant
retrieves, classifies, routes, calls tools, drafts, checks, and maybe escalates to
a human — a *graph* of steps with conditional edges and failure handling. Writing
that as ad-hoc Python becomes an unmaintainable tangle of `if`/`try`/`while`.
Orchestration frameworks give it structure: explicit nodes/edges, typed state,
checkpointing (resume after failure or human input), retries, and tracing.

## 2. Why employers want it

Section 11 ranks this #29 and notes real products are *graphs of LLM/tool/retrieval
steps, not one call* (S11, S29, S30). The signal:

- **You build production-grade pipelines, not demos.** You handle branching,
  retries, partial failure, parallelism, and state — the parts that make a flow
  reliable.
- **You can do human-in-the-loop.** Pause a flow for approval and resume it later —
  essential for high-stakes actions and a core framework feature.
- **You make complex apps observable & debuggable.** A structured graph is
  traceable; spaghetti is not (ties to #22).
- **You pick the right abstraction.** You know when to use a graph (LangGraph), a
  pipeline DAG (Haystack), an optimizer (DSPy), or just plain code.

## 3. Mental model

**A workflow is a graph of steps over a shared, evolving state.**

```
                 ┌──────── STATE (typed, persisted) ────────┐
                 │  messages, retrieved_docs, plan, results  │
                 └───────────────────────────────────────────┘
   start ─► [retrieve] ─► [classify] ─┬─(simple)─► [answer] ─► end
                                       └─(complex)─► [plan] ─► [tools]* ─► [check]
                                                                            │
                                          ┌──(fail)──────────────────────────┘
                                          ▼
                                     [human review] ──(approve)──► [answer]
   each NODE: pure-ish fn(state) → state-update
   each EDGE: static OR conditional (route on state)
   CHECKPOINT after each node → resume after crash / human pause
```

**Two dominant paradigms:**

- **Imperative graphs (LangGraph, Burr).** *You* define nodes (functions) and edges
  (including conditional routing), and the framework drives execution over a typed
  state object, checkpointing as it goes. Maximum control; the agent's *logic* is
  explicit and inspectable. LangGraph models this as a state machine; Burr as an
  explicit application state graph.
- **Declarative pipelines (Haystack, Flowise/Langflow).** You wire **components**
  (retriever → ranker → prompt → generator) into a DAG; the framework runs it.
  Great for RAG and linear-ish flows; Flowise/Langflow add a *visual* canvas for
  non-coders.
- **Programmatic / optimizing (DSPy).** You write the *program* (signatures +
  modules) declaratively and let DSPy **compile/optimize the prompts** (and even
  few-shot examples) against a metric — "programming, not prompting." Shifts effort
  from hand-tuning prompts to defining the task and letting an optimizer fit it.

**Concepts that recur across all of them:** typed **state** (what flows between
steps), **conditional edges** (routing/branching), **cycles** (agent loops:
plan → act → observe → repeat), **checkpointing/persistence** (durability +
human-in-the-loop pause/resume), **retries & fallbacks**, **parallel/map-reduce**
fan-out, **streaming**, and **tracing**. The art is the right *altitude*: too
coarse and you can't control flow; too fine and you've rebuilt the framework.

## 4. The landscape

| Framework | Paradigm | Sweet spot | Tradeoffs |
|---|---|---|---|
| **LangGraph** | Imperative state-graph (Python/JS) | Stateful agents, branching, cycles, human-in-the-loop, durability | Most control + ecosystem (LangChain/LangSmith); some boilerplate, learning curve |
| **Haystack** (deepset) | Declarative component pipeline | Production RAG/search, document workflows | Pipeline-shaped; less natural for free-form agents |
| **DSPy** (Stanford) | Programmatic + prompt optimization | Optimizing multi-step prompt programs to a metric | Different mental model; best when you have a metric to optimize against |
| **Burr** (DAGWorks) | Explicit state-machine app | Stateful apps with great built-in UI/telemetry | Smaller ecosystem |
| **ControlFlow / Prefect** | Tasks + orchestration | Mixing LLM steps with durable data-engineering workflows | Heavier; ops-oriented |
| **Flowise / Langflow** | Visual low-code canvas | Prototyping, non-engineers, demos | Hits a ceiling for complex/custom logic |
| **LlamaIndex Workflows** | Event-driven steps | Agentic RAG within LlamaIndex | Tied to that ecosystem |
| **CrewAI / AutoGen / OpenAI Agents / Anthropic SDK** | Agent/multi-agent (→ #06) | Role-based or conversational multi-agent | Agent-first rather than graph-first |

**Adjacent / underneath:** durable-execution engines (**Temporal**, **Prefect**,
**Dagster**, **Airflow**) for long-running/reliable orchestration of the *non-LLM*
parts; observability (LangSmith/Langfuse, → #22) to trace flows.

**Tradeoffs / when *not* to use one:** for a 2–3 step linear flow, plain
async Python is clearer than a framework. Reach for orchestration when you have
branching, cycles, human-in-the-loop, durability needs, or parallel fan-out — and
pick the paradigm by shape: **graph** for agentic/branching control (LangGraph/
Burr), **pipeline** for RAG/linear (Haystack), **optimizer** when you have a metric
(DSPy), **visual** for non-coders (Flowise/Langflow). Frameworks add a dependency
and an abstraction tax; the win is structure, durability, and observability.

## 5. Worked example

A minimal **stateful graph with conditional routing and a retry edge** — the core
mechanic every framework formalizes. Plain Python (no deps) so the *pattern* is the
lesson; the comments map it to LangGraph/Burr concepts.

```python
"""mini_orchestrator.py — a state-graph: nodes, conditional edges, a retry cycle.
Run: python mini_orchestrator.py
"""
from dataclasses import dataclass, field
from typing import Callable

# --- STATE: the typed object that flows between nodes (LangGraph's "State") ---
@dataclass
class State:
    question: str
    retrieved: list[str] = field(default_factory=list)
    answer: str = ""
    attempts: int = 0
    done: bool = False


# --- NODES: each is fn(state) -> state-update (here we mutate for brevity) ---
def retrieve(s: State) -> State:
    s.retrieved = ["France's capital is Paris."] if "France" in s.question else []
    return s

def answer(s: State) -> State:
    s.attempts += 1
    if s.retrieved:                       # grounded → succeed
        s.answer, s.done = "Paris.", True
    else:                                 # ungrounded → will trigger retry/fallback
        s.answer = "(no context)"
    return s

def human_fallback(s: State) -> State:    # human-in-the-loop terminal node
    s.answer, s.done = "Escalated to a human.", True
    return s


# --- EDGES: a conditional router decides the next node from STATE ---
def route_after_answer(s: State) -> str:
    if s.done:
        return "END"
    if s.attempts < 2:
        return "retrieve"                 # CYCLE: try again (the retry edge)
    return "human_fallback"               # give up → human


# --- ENGINE: drive nodes via the edge map, checkpointing each step ---
def run(start: str, nodes: dict[str, Callable], router, state: State, max_steps=10):
    node = start
    for _ in range(max_steps):
        state = nodes[node](state)        # execute node
        # checkpoint(state)  <-- here a real framework persists state (resume/HITL)
        if node == "answer":
            node = router(state)          # conditional edge after 'answer'
        elif node == "retrieve":
            node = "answer"               # static edge
        else:
            node = "END"
        if node == "END":
            break
    return state


if __name__ == "__main__":
    nodes = {"retrieve": retrieve, "answer": answer, "human_fallback": human_fallback}
    s1 = run("retrieve", nodes, route_after_answer, State("What is the capital of France?"))
    print("grounded  ->", s1.answer, f"({s1.attempts} attempt/s)")

    s2 = run("retrieve", nodes, route_after_answer, State("Tell me about Atlantis"))
    print("ungrounded ->", s2.answer, f"({s2.attempts} attempt/s)")  # → escalates
```

This is the essence: **typed state, nodes as functions, conditional edges that
route on state, and a cycle for retries** — with a checkpoint hook where a real
framework would persist state to resume after a crash or a human approval.
LangGraph/Burr give you exactly this plus persistence, streaming, parallelism,
and tracing for free; DSPy would instead let you *optimize* the prompts inside the
nodes against a metric; Haystack would express a linear RAG version as a component
DAG.

## 6. How to learn it

**Beginner (weeks).** Build a linear RAG pipeline (retrieve → prompt → generate) in
Haystack *and* as a plain function — feel the difference. Add one conditional
branch. *Milestone:* a working multi-step flow you can diagram as a graph.

**Job-ready (1–3 months).** Build a stateful agent in **LangGraph**: typed state,
conditional routing, a tool-use cycle, retries/fallbacks, **human-in-the-loop**
(pause for approval, resume), checkpointing, and streaming — traced in LangSmith/
Langfuse. Try **DSPy** to optimize a multi-step prompt program against a metric.
*Milestone:* a deployed graph app with branching, durability, HITL, and tracing.

**Expert.** Design large flows (parallel map-reduce fan-out, sub-graphs,
multi-agent supervisors), durable long-running workflows (Temporal/Prefect under
the LLM steps), and a clean state contract; pick the right framework/altitude per
problem and justify it; build evaluation and observability into the graph.
*Milestone:* a production orchestration platform other teams build flows on.

## 7. Interview signals

What's probed: can you structure a complex, reliable, debuggable LLM application?

**Q: "When do you reach for an orchestration framework vs plain code?"**
Strong answer: plain async code for 2–3 linear steps; a framework when you have
branching, cycles (agent loops), human-in-the-loop, durability/resume needs, or
parallel fan-out — because you get typed state, checkpointing, retries, and tracing
for free instead of reinventing them. Naming the *shape* (graph vs pipeline vs
optimizer) shows judgment.

**Q: "How do you implement human-in-the-loop in a long flow?"**
Strong answer: checkpoint the state at the approval node, *interrupt* execution,
persist, and resume from that checkpoint when the human responds — exactly what
LangGraph/Burr provide via durable state. Without persistence you'd lose context on
restart. Tie it to high-stakes actions needing approval (#19).

**Q: "What is DSPy and how is it different?"**
Strong answer: DSPy treats an LLM pipeline as a *program* (signatures + modules)
and **compiles/optimizes the prompts and few-shot examples against a metric**
rather than you hand-tuning them — "programming, not prompting." It shines when you
have an objective metric and a multi-step program to fit.

**Q: "Your multi-step agent fails intermittently. How do you debug it?"**
Strong answer: trace the graph (LangSmith/Langfuse) to see each node's input/output
and which edge fired; check the state at the failing node; add retries/fallbacks on
the flaky step; and use checkpointing to replay from just before the failure. The
graph structure is what makes this tractable (ties to #22).
