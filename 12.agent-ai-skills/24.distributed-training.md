## 1. What it is

**Distributed training** is training a single model across **many GPUs and many
nodes** at once — because the model, the data, or both are too big for one device.
It is the set of techniques (parallelism strategies, sharding, collective
communication, and the network fabric) that make a fleet of GPUs behave like one
enormous accelerator.

It exists because **frontier models cannot be trained any other way**. A 70B-param
model in mixed precision needs ~140 GB just for weights, plus gradients and
optimizer state (often 3–4× more) — far beyond a single 80 GB GPU. And even a
model that *fits* would take years on one GPU. Distributed training splits the
work so thousands of GPUs cooperate, and the hard part is doing that *efficiently*
— communication, not computation, is usually the bottleneck.

## 2. Why employers want it

Section 11 ranks this #24 and flags it as **gating infrastructure roles** (S27,
S28) and valued at labs. It's a scarce, high-leverage skill:

- **You can train models others can't.** Anything past a few billion parameters
  *requires* this; the talent pool who can do it well is tiny.
- **You make expensive clusters efficient.** The difference between 30% and 60%
  GPU utilization (MFU) on a 1000-GPU run is millions of dollars. You find and fix
  the communication/memory bottlenecks.
- **You debug the hardest failures.** NCCL hangs, stragglers, OOM at scale,
  checkpoint corruption — failures that don't exist on one GPU.
- **You understand the fabric.** You know why InfiniBand/NVLink topology dictates
  which parallelism goes where.

## 3. Mental model

**The core problem: where does the memory go, and what gets split?** Training
memory = weights + gradients + optimizer state (Adam keeps 2 moments → ~12 bytes/
param in fp32) + **activations** (often the biggest term). Each parallelism
strategy splits a *different* axis:

```
  DATA PARALLEL (DP) ── replicate the model on each GPU; split the BATCH.
     each GPU does a forward/backward on its shard, then ALL-REDUCE gradients.
     simplest; scales throughput; but every GPU holds a FULL model copy (memory wall).

  FSDP / ZeRO ── data-parallel BUT shard the weights+grads+optimizer across GPUs;
     gather a layer's params just-in-time for its forward/backward, then free them.
     gets DP's simplicity with far less per-GPU memory. The modern default.
       ZeRO-1: shard optimizer state · ZeRO-2: + gradients · ZeRO-3/FSDP: + params

  TENSOR PARALLEL (TP) ── split a single LAYER's matrices across GPUs (e.g. each GPU
     holds part of a big matmul). Needs fast intra-node links (NVLink); high comms.

  PIPELINE PARALLEL (PP) ── split the model by LAYERS across GPUs (stage 1 → stage 2…);
     micro-batches flow through like an assembly line to hide the "bubble".

  EXPERT PARALLEL (MoE) ── route tokens to expert sub-networks on different GPUs.

  3D / 4D PARALLELISM ── combine DP×TP×PP (×EP). TP within a node (NVLink),
     PP across nodes, DP outermost. This is how frontier models are trained.
```

**The communication primitives (NCCL collectives):** *all-reduce* (sum + share —
gradient sync in DP), *all-gather* (collect shards — FSDP param gathering),
*reduce-scatter* (FSDP gradient reduction), *broadcast*, *all-to-all* (MoE
routing). These run over the **fabric**: NVLink/NVSwitch (intra-node, ~TB/s),
InfiniBand/RoCE (inter-node, ~100s GB/s). Topology-aware placement (fast comms
inside a node, slow across nodes) is *the* efficiency lever.

**The metric:** **MFU** (Model FLOPs Utilization) — fraction of theoretical GPU
FLOPs actually used for useful work. Communication, bubbles, and memory stalls eat
it. Good large-scale runs target 40–60%+.

**Other essentials:** mixed precision (BF16/FP8) halves memory + bandwidth;
**activation/gradient checkpointing** trades recompute for memory; **gradient
accumulation** simulates a big batch on few GPUs; **distributed checkpointing**
(sharded, async) so a 1000-GPU run can resume after a node dies.

## 4. The landscape

**Frameworks / libraries**
- **PyTorch DDP** — the baseline data-parallel API (`DistributedDataParallel`):
  all-reduce gradients, one process per GPU. Learn this first.
- **PyTorch FSDP / FSDP2** — native fully-sharded data parallel (ZeRO-3 style);
  the standard PyTorch path for large models.
- **DeepSpeed** (Microsoft) — **ZeRO** stages 1/2/3, ZeRO-Offload/Infinity (to
  CPU/NVMe), pipeline parallelism, MoE; battle-tested for huge models.
- **Megatron-LM / Megatron-Core** (NVIDIA) — efficient **tensor + pipeline +
  sequence** parallelism; the reference for training giant transformers.
- **NeMo** (NVIDIA, built on Megatron-Core) — end-to-end LLM training framework.
- **HF Accelerate** — thin launcher that wraps DDP/FSDP/DeepSpeed with one config;
  the easy on-ramp. → [`../09.huggingface/accelerate`](../09.huggingface/accelerate).
- **Ray Train** — orchestrates distributed training (incl. on K8s via KubeRay).
- **torchtitan** (PyTorch-native large-scale reference), **JAX + GSPMD/`pjit`**
  (the lab/TPU path: parallelism via sharding annotations + XLA).

**Communication & fabric**
- **NCCL** (NVIDIA Collective Communications Library) — the all-reduce/all-gather
  engine under PyTorch/DeepSpeed; topology-aware. **RCCL** is the AMD analog.
- Fabric: **NVLink/NVSwitch** (intra-node), **InfiniBand**/**RoCE** (inter-node),
  GPUDirect RDMA. The network *is* the bottleneck at scale.

**Launch & orchestration:** `torchrun`/`torch.distributed`, **SLURM** (HPC
clusters), **KubeRay**/Kubeflow training operators / Volcano (K8s, gang-scheduled
— see #21).

**Tradeoffs (how to choose):**
- Model fits on one GPU, want speed → **DDP** (or FSDP for memory headroom).
- Model doesn't fit but ≤ a node → **FSDP / ZeRO-3** (shard everything).
- Truly huge, multi-node → **3D parallelism** (Megatron TP within node + PP across
  nodes + FSDP/DP outermost). TP needs NVLink; don't span TP across slow links.
- Limited GPUs, big model, OK with slow → **ZeRO-Offload** to CPU/NVMe.
- MoE → **expert parallelism** + all-to-all.

## 5. Worked example

The foundation everything else builds on: **PyTorch DDP**, runnable on CPU
(gloo backend) so you can see the mechanics — process group init, per-rank model
replica, and automatic gradient all-reduce — without a GPU cluster.

```python
"""ddp_demo.py — minimal Distributed Data Parallel (runs on CPU via gloo).
Run: torchrun --nproc_per_node=2 ddp_demo.py
"""
import os
import torch
import torch.distributed as dist
import torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP


def main():
    # torchrun sets RANK / WORLD_SIZE / LOCAL_RANK env vars per process.
    dist.init_process_group(backend="gloo")          # use "nccl" on GPUs
    rank, world = dist.get_rank(), dist.get_world_size()
    torch.manual_seed(0)

    # Each process holds a FULL replica of the model (this is data parallelism).
    model = nn.Sequential(nn.Linear(10, 32), nn.ReLU(), nn.Linear(32, 1))
    model = DDP(model)  # wraps the model: hooks all-reduce gradients in backward()
    opt = torch.optim.SGD(model.parameters(), lr=0.1)
    loss_fn = nn.MSELoss()

    for step in range(3):
        # In real training a DistributedSampler gives each rank a DIFFERENT shard.
        x = torch.randn(8, 10) + rank          # distinct data per rank
        y = torch.randn(8, 1)
        opt.zero_grad()
        loss = loss_fn(model(x), y)
        loss.backward()        # <-- DDP all-reduces (averages) grads across ranks here
        opt.step()             # every rank now applies the SAME averaged gradient
        if rank == 0:
            print(f"step {step}  loss={loss.item():.4f}  (grads synced across {world} ranks)")

    # All replicas stay identical because gradients are averaged every step.
    dist.barrier()
    dist.destroy_process_group()


if __name__ == "__main__":
    main()
```

The key mechanic is one line: `loss.backward()` on a `DDP`-wrapped model triggers
a **gradient all-reduce** across all ranks, so every replica takes the *same*
averaged step and stays in sync. FSDP/ZeRO change *what* is communicated (gather
params, reduce-scatter grads) to shed memory, and TP/PP split *within* the model —
but the DDP loop is the conceptual base you generalize from.

## 6. How to learn it

**Beginner (weeks).** Understand the training-memory breakdown (weights + grads +
optimizer + activations) and why one GPU runs out. Run DDP on 2 GPUs (or CPU via
gloo, above) with a `DistributedSampler`. Learn the NCCL collectives conceptually.
*Milestone:* a multi-process DDP run that matches single-GPU results and scales
throughput.

**Job-ready (1–3 months).** Train a model too big for one GPU with **FSDP** or
**DeepSpeed ZeRO-3**; add mixed precision, activation checkpointing, and gradient
accumulation; use HF Accelerate to switch strategies via config. Set up
distributed checkpointing and resume from a simulated failure. Profile to estimate
MFU. *Milestone:* you fine-tune a 7B+ model across multiple GPUs and can explain
where the memory and the communication go.

**Expert.** Compose **3D parallelism** (Megatron TP + PP + DP) for a large model;
reason about topology (TP on NVLink, PP across IB), overlap communication with
compute, and push MFU; debug NCCL hangs, stragglers, and load imbalance; train at
multi-node scale on SLURM/K8s. *Milestone:* you run a large-scale training job at
high MFU and can diagnose a hang from NCCL logs and the topology.

## 7. Interview signals

What's probed: do you understand *what gets split and why*, and can you reason
about the memory/communication bottleneck?

**Q: "Data vs tensor vs pipeline parallelism — when each?"**
Strong answer: **DP** replicates the model and splits the batch (simple, scales
throughput, but each GPU holds a full copy). **TP** splits individual layers'
matrices across GPUs — needed when a layer is too big, but comms-heavy, so keep it
*within* a node on NVLink. **PP** splits the model by layer-stages across nodes
(an assembly line; manage the bubble with micro-batches). Big models combine all
three (3D), DP outermost.

**Q: "What does ZeRO / FSDP actually shard?"**
Strong answer: standard DP replicates weights, gradients, *and* optimizer state on
every GPU — hugely redundant. ZeRO shards them in stages (1: optimizer state, 2: +
gradients, 3/FSDP: + parameters), gathering a layer's params just-in-time and
freeing them after. You keep DP's simplicity but cut per-GPU memory roughly by the
world size — that's what lets a model that doesn't fit, fit.

**Q: "Your 8-GPU run is barely faster than 1 GPU. Why?"**
Strong answer: communication-bound — gradient all-reduce or param all-gather isn't
overlapping with compute, the interconnect is slow (PCIe instead of NVLink/IB), a
straggler/load imbalance stalls the group, or the batch is too small to amortize
comms. Profile (e.g., torch profiler / Nsight), check the fabric and overlap, and
measure MFU.

**Q: "How do you handle a node dying mid-run?"**
Strong answer: frequent **distributed (sharded) checkpointing** — ideally async so
it doesn't stall training — plus elastic/`torchrun`-style restart to resume from
the last checkpoint. At thousand-GPU scale, failures are routine, so checkpoint
cadence vs overhead is a real tuning decision.
