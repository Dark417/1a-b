## 1. What it is

**Containers** (Docker/OCI) package an application *and* its entire environment —
OS libs, Python deps, CUDA runtime, model weights — into a single, reproducible,
portable image that runs the same on a laptop, a CI runner, and a cluster.
**Kubernetes (K8s)** is the orchestrator that runs those containers across a fleet
of machines: scheduling, scaling, self-healing, networking, storage, and — for AI
— **GPU scheduling**.

It exists because "works on my machine" is fatal at scale, and because AI
workloads have brutal infrastructure needs: gigabyte images, GPU drivers that must
match, models that take minutes to load, bursty traffic, and *expensive* GPUs that
must be shared across teams. Containers make the environment reproducible;
Kubernetes makes a *fleet* of GPU machines behave like one elastic, self-healing
computer.

## 2. Why employers want it

Section 11 ranks this #21 and notes Kubernetes is the **single most-named MLOps
tool** (~17.6%). The hiring signal:

- **You can ship a model to production reliably.** A `Dockerfile` + a K8s
  `Deployment` is the standard delivery vehicle; without it your model runs only
  on your laptop.
- **You can share scarce GPUs.** GPU scheduling, node pools, requests/limits, and
  bin-packing are how a company gets value from a $200k node across many teams.
- **You handle scale and failure.** Autoscaling (HPA/KEDA), rolling updates,
  health probes, and self-healing are table stakes for a live service.
- **You speak the platform language.** Pods, services, ingress, configmaps,
  secrets, namespaces — the vocabulary every infra/MLOps conversation assumes.

It's *the* operational substrate of MLOps (#11): observability, serving, and
deployment all assume a container running somewhere a scheduler placed it.

## 3. Mental model

**Two layers.** A container is a *process with its own filesystem and namespaces*
(isolation via Linux cgroups/namespaces — not a VM, no guest kernel). Kubernetes
is a *control loop* that drives the cluster's *actual* state toward your
*declared* state.

```
  Dockerfile ──build──► IMAGE ──push──► REGISTRY ──pull──► CONTAINER (a running process)

  Kubernetes (declarative, reconciliation loop):
    you DECLARE desired state (YAML) ─► API SERVER ─► etcd
                                          │
              ┌───────────────────────────┴─────────────────────┐
              ▼                                                   ▼
        SCHEDULER places Pods on Nodes              CONTROLLERS reconcile:
        (by CPU/GPU requests, affinity)             "want 3 replicas, have 2 → start 1"

   Pod  = smallest unit: 1+ containers sharing net/storage
   Deployment = manages a ReplicaSet of Pods (rolling updates, rollback)
   Service    = stable virtual IP + load-balances across Pods
   Ingress    = HTTP routing from outside into Services
   HPA        = autoscale replicas on CPU/GPU/custom metrics
```

**Concepts to own:**

- **Declarative + reconciliation.** You don't run commands; you declare desired
  state and controllers continuously make reality match. Self-healing falls out
  of this for free.
- **Requests vs limits.** *Requests* = guaranteed (used for scheduling/
  bin-packing); *limits* = ceiling (throttle/OOM-kill above it). Right-sizing
  these is most of cost control.
- **GPU scheduling.** GPUs are a *non-overcommittable* resource
  (`nvidia.com/gpu: 1`) exposed via the **NVIDIA device plugin**. A pod gets whole
  GPUs by default; **MIG** (slice an A100/H100 into instances) or **time-slicing**
  shares one GPU across pods. Node pools/taints keep GPU pods on GPU nodes.
- **Health probes.** *Liveness* (restart if hung), *readiness* (don't send
  traffic until the model is loaded — critical for slow model startup), *startup*
  (grace period for long loads).
- **Config & secrets.** ConfigMaps (non-secret) and Secrets (API keys) injected
  as env/volumes — never bake keys into images.
- **Stateless vs stateful.** Serving is stateless (scale freely); training jobs,
  vector DBs, and queues are stateful (StatefulSets, persistent volumes).

## 4. The landscape

**Container build/run**
- **Docker** (build + Docker Desktop), **Podman** (daemonless, rootless),
  **containerd**/CRI-O (the runtimes K8s actually uses), **BuildKit**/**Buildah**
  (faster, cache-mount builds), **`docker compose`** (multi-container local dev).
- Image hygiene: **multi-stage builds**, slim/distroless bases, `.dockerignore`,
  layer caching, pin digests. For ML: start from `nvidia/cuda` or
  `pytorch/pytorch` images; copy weights at build *or* mount at runtime.

**Kubernetes distributions & hosting**
- Managed: **EKS** (AWS), **GKE** (GCP), **AKS** (Azure) — the production default.
- Local/dev: **kind**, **minikube**, **k3s**/**k3d** (lightweight), Docker Desktop.

**ML-on-K8s ecosystem**
- **Kubeflow** — ML platform on K8s (pipelines, notebooks, training operators).
- **KServe** / **Seldon Core** — model-serving CRDs (autoscale-to-zero, canary,
  multi-framework).
- **Ray** / **KubeRay** — distributed Python (training, serving via Ray Serve,
  batch) on K8s; the rising default for scaling AI workloads. → relevant to
  [`24.distributed-training.md`](24.distributed-training.md).
- **NVIDIA GPU Operator** — installs/manages drivers, device plugin, MIG, DCGM
  metrics on GPU nodes (do not hand-install drivers).
- **Volcano** / **Kueue** — gang-scheduling & job queuing for batch/training
  (all-or-nothing pod groups, fair-share GPU quotas).

**Autoscaling & ops**
- **HPA** (pods on metrics), **KEDA** (event/queue-driven, scale-to-zero),
  **Cluster Autoscaler** / **Karpenter** (add/remove *nodes*, incl. GPU spot
  nodes — huge for cost), **VPA** (right-size requests).
- **Helm** / **Kustomize** (templating/packaging), **Argo CD** / **Flux**
  (GitOps), **Argo Workflows** (DAG jobs).

**Tradeoffs:** K8s is powerful but heavy — for a single small service, a managed
container runner (Cloud Run, ECS/Fargate, Fly.io) is often the right call. Reach
for K8s when you have *many* services, *shared GPUs*, multi-team scaling, or
portability needs. Don't run a cluster you don't need.

## 5. Worked example

The two artifacts every AI engineer must produce: a **production Dockerfile** for
a model service and the **Kubernetes manifests** that run it on a GPU with
autoscaling and a readiness gate for slow model loads.

```dockerfile
# Dockerfile — multi-stage build for a FastAPI model server (slim final image).
# --- build stage: install deps with cache, keep build tools out of final image ---
FROM python:3.11-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# --- runtime stage: copy only what we need ---
FROM python:3.11-slim
WORKDIR /app
COPY --from=build /install /usr/local
COPY app.py .
EXPOSE 8080
# exec form so signals (SIGTERM on rollout) reach the process for clean shutdown
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]
```

```yaml
# serve.yaml — Deployment (1 GPU/pod) + Service + HPA. Apply: kubectl apply -f serve.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: llm-server }
spec:
  replicas: 2
  selector: { matchLabels: { app: llm-server } }
  template:
    metadata: { labels: { app: llm-server } }
    spec:
      containers:
      - name: server
        image: registry.example.com/llm-server:1.0.0   # pin a tag, never :latest
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "2", memory: 8Gi, nvidia.com/gpu: 1 }  # 1 whole GPU
          limits:   { cpu: "4", memory: 16Gi, nvidia.com/gpu: 1 }
        env:
        - name: API_KEY
          valueFrom: { secretKeyRef: { name: llm-secrets, key: api-key } }
        # Don't route traffic until the model is loaded (can take minutes):
        readinessProbe:
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 30
          periodSeconds: 10
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 60
---
apiVersion: v1
kind: Service
metadata: { name: llm-server }
spec:
  selector: { app: llm-server }
  ports: [{ port: 80, targetPort: 8080 }]
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: llm-server }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: llm-server }
  minReplicas: 2
  maxReplicas: 8
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

The lesson is visible in the YAML: `nvidia.com/gpu: 1` schedules onto a GPU node;
the **readiness probe** stops K8s from sending traffic to a pod whose model is
still loading (the #1 cause of "deploy worked but requests 503'd"); the HPA scales
2→8 under load; the multi-stage Dockerfile keeps the shipped image lean.

## 6. How to learn it

**Beginner (weeks).** Write a `Dockerfile` for a Python app, build, run, push to a
registry; use `docker compose` for a multi-container local stack (app + vector
DB). Learn images vs containers, layers, volumes, ports, env. *Milestone:* your
app runs identically on your machine and a teammate's via one `docker run`.

**Job-ready (1–3 months).** Stand up a local cluster (kind/k3d). Deploy a model
service with a Deployment + Service + Ingress + HPA + ConfigMap/Secret + health
probes. Add GPU scheduling on a managed cluster (EKS/GKE) with the NVIDIA GPU
Operator. Package it with Helm; deploy via GitOps (Argo CD). *Milestone:* a model
served on K8s with autoscaling, a readiness gate, and a rolling update + rollback
you've actually performed.

**Expert.** Optimize GPU utilization (MIG/time-slicing, bin-packing, Karpenter on
spot GPU nodes); gang-schedule training with Volcano/Kueue; run KServe/Ray Serve
for autoscale-to-zero multi-model serving; own cluster cost (right-sized requests,
node pools, spot fallback) and reliability (PodDisruptionBudgets, multi-AZ).
*Milestone:* a multi-tenant GPU platform other teams deploy onto, with measured
utilization and cost-per-request.

## 7. Interview signals

What's probed: can you reliably and cheaply run model workloads at scale?

**Q: "Walk me through deploying a model to Kubernetes."**
Strong answer: containerize (multi-stage Dockerfile, slim base, pinned deps),
push to a registry, declare a Deployment with **GPU requests/limits**, a Service
for stable networking, an HPA for scaling, **readiness probes so traffic waits for
model load**, Secrets for keys, and rolling updates for zero-downtime deploys.
Mention GitOps/Helm for repeatability.

**Q: "How do you share one GPU across multiple workloads?"**
Strong answer: by default a pod gets a whole GPU. To share: **MIG** (hardware
partitioning on A100/H100), **time-slicing** (the device plugin oversubscribes one
GPU), or **MPS**. Use node pools/taints to keep GPU pods on GPU nodes and
requests to bin-pack. Note the tradeoff: isolation (MIG) vs flexibility
(time-slicing).

**Q: "requests vs limits?"**
Strong answer: requests are guaranteed and drive scheduling/bin-packing; limits
are the ceiling (CPU throttled, memory OOM-killed above it). Set requests from
observed usage; right-sizing them is most of cluster cost control. GPUs are
non-overcommittable, so request == limit there.

**Q: "Your model pods keep getting OOM-killed on deploy."**
Strong answer: the memory *limit* is below peak (model load spikes memory); raise
it, add a startup/readiness probe with enough `initialDelaySeconds`, check for a
memory leak with monitoring, and consider loading weights lazily or from a mounted
volume rather than into RAM at once.
