## What MCP is

The **Model Context Protocol (MCP)** is an open standard for connecting AI
applications to external tools and data. Instead of every app hard-coding an
integration for every service, MCP defines a common protocol: a service ships an
**MCP server**, and any **MCP host** (Claude Code, Claude Desktop, IDEs) can
connect to it and use its capabilities. Claude Code uses MCP to read your design
docs, update tickets, query databases, and call your own custom tooling.

## The participants

MCP follows a **client–server** architecture:

* **Host** — the AI application (e.g. Claude Code) coordinating one or more clients.
* **Client** — a connector the host creates, one per server, holding a dedicated
  connection.
* **Server** — a program that exposes capabilities (tools, data, prompts).

```
┌──────────── MCP Host (Claude Code) ────────────┐
│   Client 1 ───── dedicated conn ───── Server A  (local: filesystem)
│   Client 2 ───── dedicated conn ───── Server B  (local: database)
│   Client 3 ───── dedicated conn ───── Server C  (remote: Sentry)
└─────────────────────────────────────────────────┘
```

A server is "local" or "remote" only by *where it runs* and *which transport* it
uses — the protocol is identical either way.

## Two layers

* **Data layer** — a **JSON-RPC 2.0** protocol defining the messages: lifecycle
  management, and the primitives (tools, resources, prompts, notifications).
* **Transport layer** — how bytes move:
  * **stdio** — the host launches the server as a subprocess and talks over its
    stdin/stdout. Best for local servers; no network overhead.
  * **Streamable HTTP** — HTTP POST for requests with optional Server-Sent
    Events for streaming. For remote servers; supports OAuth / bearer-token auth.

## The primitives

A server can expose three things to the host:

| Primitive | What it is | Discovery / use |
|---|---|---|
| **Tools** | Executable functions the model can invoke (file ops, API calls, queries). | `tools/list` then `tools/call` |
| **Resources** | Data sources that provide context (file contents, records, API responses). | `resources/list` then `resources/read` |
| **Prompts** | Reusable interaction templates (system prompts, few-shot examples). | `prompts/list` then `prompts/get` |

(Clients can also expose primitives back to servers — **sampling**, **elicitation**,
**logging** — but the common case is a server offering tools to the host.)

## The lifecycle (and the wire)

MCP is a *stateful* protocol with a capability-negotiation handshake. The
mini-agent's stdio client implements the real sequence:

1. **initialize** — the client sends its protocol version + capabilities; the
   server replies with its `serverInfo` and `capabilities`.

   ```json
   → {"jsonrpc":"2.0","id":1,"method":"initialize",
      "params":{"protocolVersion":"2025-06-18","capabilities":{},
                "clientInfo":{"name":"mini-agent-mcp-client","version":"0.1.0"}}}
   ← {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18",
        "capabilities":{"tools":{"listChanged":false}},
        "serverInfo":{"name":"example-mcp-server","version":"0.1.0"}}}
   ```

2. **notifications/initialized** — the client signals readiness (a notification:
   no `id`, no response expected).

3. **tools/list** — discover the available tools (each with `name`,
   `description`, `inputSchema`).

4. **tools/call** — invoke a tool by name with arguments; the result is an array
   of content blocks.

   ```json
   → {"jsonrpc":"2.0","id":3,"method":"tools/call",
      "params":{"name":"add","arguments":{"a":40,"b":2}}}
   ← {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"42"}]}}
   ```

**Notifications** also flow the other way: a server that declared
`tools.listChanged` can send `notifications/tools/list_changed` when its tool set
changes, prompting the client to re-`tools/list`.

## How the host adapts MCP tools

The host fetches each connected server's tools and **merges them into the unified
tool registry** the model sees — alongside the built-in Read/Write/Bash tools.
Claude Code namespaces them `mcp__<server>__<tool>` so they don't collide. The
model then calls an MCP tool exactly like any other tool; the host routes the
call to the right client, which `tools/call`s the server.

The mini-agent does precisely this: `mcp_tools_as_agent_tools()` wraps each
discovered MCP tool as a normal agent `Tool` whose function calls back into the
MCP client, naming them `mcp__example__add`, `mcp__example__upper`, …:

```python
with StdioMCPClient([sys.executable, "mcp_server_example.py"]) as client:
    for tool in mcp_tools_as_agent_tools(client):   # mcp__example__add, ...
        registry.register(tool)                     # now callable by the agent loop
```

The bundled [`mcp_server_example.py`](../python/mcp_server_example.py) /
[`mcp_server_example.rb`](../ruby/mcp_server_example.rb) implements just enough of
the spec (`initialize`, `tools/list`, `tools/call`) to make the whole loop run
**offline on the standard library** — `python demo.py` and `ruby demo.rb` each
perform a live MCP round-trip.
