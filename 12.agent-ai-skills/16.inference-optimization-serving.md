# 16 · Inference Optimization & Serving

> Skill #16 (Tier 2 — Important). *KV-cache, batching, quantization, vLLM/TGI/

> latency driver. See the rationale in

## 1. What it is

Making models **fast and cheap to run** in production: KV-cache and **paged
attention**, **continuous batching**, **quantization** (GPTQ/AWQ/GGUF/FP8),
**speculative decoding**, and the serving engines that implement these —
**vLLM, TGI, SGLang, TensorRT-LLM, Triton, Ollama**, plus deployment knobs
(tensor parallelism, max batch/seq, prefix caching).

It exists because **inference is the dominant production cost and latency
driver.** A model that's accurate but too slow or too expensive to serve doesn't
ship. This is required for serving-team roles and valued everywhere self-hosted
models run.

## 2. Why employers want it

Required at NVIDIA and perf/inference teams (S9, S10, S18, S28), valued broadly
(R1). The signal:

- **You squeeze the biggest cost lever** — inference throughput and cost-per-token
  is where the money is.
- **You hit latency targets** — TTFT (time-to-first-token) and inter-token latency
  decide UX.
- **You operate serving engines** — vLLM/TGI/etc., not just a naive `model.
  generate()` loop.

## 3. Mental model

**LLM inference is two phases with different bottlenecks:**

```
PREFILL: process the whole prompt in parallel  → compute-bound  (sets TTFT)
DECODE:  generate one token at a time, reusing  → memory-bandwidth-bound (sets throughput)
         the KV-cache; each step reads all weights + the growing KV-cache
```

The key facts that drive every optimization:

- **The KV-cache** stores past keys/values so each new token doesn't recompute
  attention over the whole sequence (skill [`03`](03.llm-transformer-architecture.md)).
  It's the **dominant memory consumer** at long context, and its fragmentation is
  what **paged attention** (vLLM) fixes — treat the cache like OS virtual memory,
  in pages, so you waste almost no GPU memory and fit far more concurrent
  requests.
- **Decode is memory-bandwidth-bound**: you re-read the model weights every token.
  So **batching** (process many sequences together) amortizes the weight read
  across requests → throughput scales. **Continuous (in-flight) batching** adds/
  removes sequences as they finish instead of waiting for the whole batch — the
  single biggest throughput win for real traffic.
- **Quantization** shrinks weights (and sometimes KV-cache) to fewer bits → less
  memory, more bandwidth headroom, lower cost, usually a small quality hit.
- **Speculative decoding** uses a small draft model to propose several tokens that
  the big model verifies in one pass → fewer big-model steps, no quality loss.

**The metrics you optimize:** throughput (tokens/sec, requests/sec),
**TTFT** (latency to first token — prefill-bound), **inter-token latency**
(decode-bound), and **cost per million tokens**. They trade off — batching
raises throughput but can raise per-request latency.

## 4. The landscape

**Serving engines.**

| Engine | Strength | Notes |
|---|---|---|
| **vLLM** | throughput; PagedAttention, continuous batching | the open default for self-hosting |
| **TGI** (HF) | production-ready, HF-integrated | easy with HF models |
| **SGLang** | fast, RadixAttention (prefix caching) | structured/agentic workloads |
| **TensorRT-LLM** | max perf on NVIDIA | compile-heavy, lowest latency |
| **Triton Inference Server** | multi-model serving | pairs with TensorRT-LLM |
| **llama.cpp / Ollama** | CPU/edge/local, GGUF | dev, on-device, no GPU |
| **LMDeploy, MLC-LLM** | alt high-perf / cross-platform | |

**Quantization formats.**

| Format | Bits | Where |
|---|---|---|
| **GPTQ / AWQ** | 4-bit | GPU inference (vLLM/TGI) |
| **GGUF** | 2–8-bit | llama.cpp / Ollama (CPU/edge) |
| **FP8 / INT8** | 8-bit | modern GPUs, near-lossless |
| **bitsandbytes (NF4)** | 4-bit | QLoRA training, some inference |

**Techniques.** PagedAttention (memory) · continuous batching (throughput) ·
**prefix/prompt caching** (reuse shared prefixes across requests) · speculative
decoding · chunked prefill · FlashAttention kernels · **tensor/pipeline
parallelism** for models too big for one GPU (skill [`24`](24.distributed-training.md)) ·
**multi-LoRA serving** (many adapters on one base, skill [`12`](12.fine-tuning-model-adaptation.md)).

**Knobs you actually tune.** `max_num_seqs` / `max_num_batched_tokens` (batch
size), `gpu_memory_utilization`, `max_model_len` (context = KV-cache budget),
`tensor_parallel_size`, quantization choice, and enabling prefix caching.

## 5. Worked example

Serving an open model with **vLLM** — continuous batching and PagedAttention come
for free — plus the throughput-vs-latency reasoning. The serving code is the
idiomatic pattern; the comments are the interview-relevant knobs. (Real runs need
a GPU.)

```python
"""serve_vllm.py — high-throughput serving with vLLM. Knobs that matter, annotated."""
from vllm import LLM, SamplingParams

# PagedAttention + continuous batching are automatic. The knobs below set the
# throughput/latency/memory tradeoff.
llm = LLM(
    model="meta-llama/Llama-3.1-8B-Instruct",
    quantization="awq",            # 4-bit weights -> less memory, lower cost, small quality hit
    max_model_len=8192,            # context length == KV-cache budget per sequence
    gpu_memory_utilization=0.90,   # how much VRAM to use for weights + KV-cache
    tensor_parallel_size=1,        # split across N GPUs if the model doesn't fit on one
    enable_prefix_caching=True,    # reuse a shared prompt prefix across requests (cost win)
)

params = SamplingParams(temperature=0.7, top_p=0.9, max_tokens=256)

# Batch many prompts in ONE call -> continuous batching amortizes the weight read
# across all of them. This is the throughput win: decode is bandwidth-bound, so
# more concurrent sequences = more tokens/sec from the same weight reads.
prompts = [f"Summarize fact #{i} about LLM inference." for i in range(64)]
outputs = llm.generate(prompts, params)   # served concurrently, not one-by-one

for out in outputs[:3]:
    print(out.outputs[0].text[:80])

# In production you'd run vLLM's OpenAI-compatible server instead:
#   vllm serve meta-llama/Llama-3.1-8B-Instruct --quantization awq \
#       --max-model-len 8192 --enable-prefix-caching
# and point any OpenAI-style client at it. Then load-test: measure tokens/sec,
# TTFT, and p95 inter-token latency; tune max_num_seqs / batched-tokens to the
# latency budget; add tensor_parallel_size for bigger models.
```

The reasoning that matters in interviews, embedded above: **batch to raise
throughput** (decode is bandwidth-bound), **quantize to cut memory/cost**,
**prefix-cache shared prompts**, and **tensor-parallelize** when the model is too
big for one GPU — while watching TTFT and inter-token latency against the UX
budget.

## 6. How to learn it

**Beginner (0–3 months).** Run a model locally with Ollama/llama.cpp (GGUF);
understand prefill vs decode and the KV-cache; serve a small model with vLLM.
*Milestone:* a local served model you can hit via an OpenAI-style API.

**Intermediate / job-ready (3–9 months).** Benchmark throughput/TTFT/latency;
quantize (AWQ/GPTQ/GGUF) and measure the quality/speed tradeoff; tune batch and
KV-cache knobs; enable prefix caching; try speculative decoding. *Milestone:* a
vLLM/TGI deployment you load-tested and tuned to a latency budget.

**Expert (9+ months).** Tensor/pipeline parallelism for large models;
TensorRT-LLM compilation; multi-LoRA serving; custom kernels (skill [`23`](23.gpu-programming-cuda.md));
cost-per-token optimization at scale. *Milestone:* you own a serving stack hitting
strict latency/cost SLOs.

## 7. Interview signals

- **"Why is LLM inference slow, and how do you speed it up?"** Two phases:
  prefill (compute-bound, TTFT) and decode (bandwidth-bound, throughput). Speed
  up via batching, KV-cache/PagedAttention, quantization, speculative decoding,
  better kernels.
- **"What does continuous batching do?"** Adds/removes sequences from the batch as
  they arrive/finish instead of waiting for the whole batch — keeps the GPU busy,
  the biggest real-traffic throughput win.
- **"What limits how many requests you can serve?"** KV-cache memory (grows with
  context × concurrency) — which is why PagedAttention and quantizing the cache
  matter; plus weight memory and bandwidth.
- **"Quantization tradeoffs?"** Fewer bits → less memory, lower cost, more
  throughput, usually small quality loss; AWQ/GPTQ (GPU 4-bit), GGUF (CPU/edge),
  FP8 (near-lossless on modern GPUs). Always *measure* the quality hit.
- **"Throughput vs latency?"** Bigger batches raise throughput but can raise
  per-request latency; tune to the SLO (TTFT and inter-token latency).
