# 00 · The Hugging Face Hub — Manifest

> What the Hub *is*, what lives on it, how naming/licensing/gating work, and how
> you search, download, cache, and authenticate. Read this before the
> architecture map ([`01.architecture.md`](01.architecture.md)) and the
> end-to-end workflow ([`02.workflow.md`](02.workflow.md)).

The **Hugging Face Hub** (https://huggingface.co) is a git-based platform for
sharing machine-learning artifacts. Think "GitHub for models, datasets, and ML
apps," with extra ML-specific machinery: large-file storage, a metadata layer
(model cards / dataset cards), an inference layer, and tight integration with
the `transformers` / `datasets` / `diffusers` Python libraries.

---

## 1. What lives on the Hub

| Artifact | URL shape | Backed by | Python entry point |
|---|---|---|---|
| **Model** | `huggingface.co/<org>/<name>` | git repo + LFS / Xet | `from_pretrained`, `hf_hub_download`, `snapshot_download` |
| **Dataset** | `huggingface.co/datasets/<org>/<name>` | git repo + Parquet/Arrow | `datasets.load_dataset` |
| **Space** | `huggingface.co/spaces/<org>/<name>` | git repo (Gradio/Streamlit/Docker) | hosted app; clone or `gradio` |
| **Paper page** | `huggingface.co/papers/<arxiv-id>` | metadata over arXiv | web only (discovery) |
| **Collection** | `huggingface.co/collections/...` | curated lists | web / API |

Every repo is **a real git repository**. Large binaries (weights, Parquet) are
tracked with **git-LFS** (legacy) or **Xet** (the newer content-addressed
chunked store that replaced LFS for most repos in 2024–2025). You can
`git clone` any public repo, but the Python libraries give you caching,
resumable downloads, revision pinning, and partial (single-file) fetches that
raw git does not.

### Repo file anatomy (a model repo)
```
<org>/<model>/
  config.json            # architecture + hyperparameters (drives AutoModel)
  model.safetensors      # weights (safetensors preferred over pytorch_model.bin)
  tokenizer.json         # fast-tokenizer serialization
  tokenizer_config.json  # tokenizer class + special-token map
  vocab.txt / merges.txt # tokenizer vocab (model-dependent)
  generation_config.json # default decoding params for generative models
  README.md              # the MODEL CARD (YAML front-matter + prose)
  .gitattributes         # which files are LFS/Xet tracked
```
`config.json` is the keystone: its `"architectures": ["BertForMaskedLM"]` and
`"model_type": "bert"` fields are exactly what the `Auto*` classes read to pick
the right Python class. (More in [`01.architecture.md`](01.architecture.md).)

## 2. Naming conventions

A repo id is **`namespace/name`** (a.k.a. `org/repo` or `user/repo`):

- `google-bert/bert-base-uncased` — canonical org-owned model.
- `meta-llama/Llama-3.1-8B-Instruct` — gated, license-gated.
- `sshleifer/tiny-gpt2` — a community user's *tiny* test model.
- `hf-internal-testing/tiny-random-gpt2` — HF's own CI fixtures (smallest possible).
- A **bare** id like `gpt2` or `bert-base-uncased` is a *canonical/legacy* repo
  with no namespace (HF maintains a small set of these; new repos always have a
  namespace).

Common name suffixes encode the variant:
`-base` / `-large` (size) · `-instruct` / `-it` / `-chat` (instruction-tuned) ·
`-cased` / `-uncased` · `-GGUF` / `-AWQ` / `-GPTQ` (quantized format) ·
`-distil*` (distilled). These are conventions, not rules — always read the card.

### Revisions
Every download can pin a **revision**: a branch (`main`), a tag (`v1.0`), or a
commit SHA. Pinning a SHA is the reproducibility best practice:
```python
AutoModel.from_pretrained("prajjwal1/bert-tiny", revision="<commit-sha>")
```

## 3. Model cards & dataset cards

The `README.md` of a repo is the **card**. It has two parts:

1. **YAML front-matter** (machine-readable metadata):
   ```yaml
   ---
   license: apache-2.0
   language: [en]
   tags: [text-classification]
   datasets: [glue]
   metrics: [accuracy]
   pipeline_tag: text-classification
   library_name: transformers
   ---
   ```
   `pipeline_tag` powers the website's task filter and the Inference widget;
   `license` drives the license filter; `library_name` tells the Hub which
   "Use this model" snippet to show.
2. **Prose**: intended use, training data, evaluation, limitations, bias,
   environmental impact. Good cards follow the *Model Cards* paper
   (Mitchell et al., 2019) and the HF card template.

You can read card metadata programmatically without downloading weights via the
`HfApi` (`model_info(...).cardData`) — see [`hub/`](hub/).

## 4. Gated & licensed models

Some repos are **gated**: you must (a) be logged in and (b) accept terms /
request access before downloads succeed. Examples: Llama, Gemma, Mistral
research checkpoints.

- **License** (`license:` in front-matter) is metadata — `apache-2.0`, `mit`,
  `llama3`, `gemma`, `cc-by-nc-4.0` (non-commercial), `openrail` (responsible AI
  license), or `other`. It tells you what you may legally do; it does **not** by
  itself block downloads.
- **Gating** is an access control on top: clicking "Agree and access" or
  filling a form. After approval, your token unlocks downloads.
- Hitting a gated repo without access raises **HTTP 401/403**
  (`GatedRepoError` / `HfHubHTTPError`). The offline-safe examples in this
  section catch these and fall back gracefully.

For teaching we use **only** ungated, permissively-licensed *tiny* models so
everything downloads fast on CPU and never needs a token.

## 5. Searching the Hub

**Web:** facet filters for task (`pipeline_tag`), library, language, license,
dataset, plus full-text and "trending."

**API / CLI:**
```python
from huggingface_hub import HfApi
api = HfApi()
# Smallest text-generation models, most-downloaded first:
for m in api.list_models(filter="text-generation", sort="downloads",
                         direction=-1, limit=5):
    print(m.id, m.downloads)
```
```bash
hf search model bert --limit 5          # newer unified `hf` CLI
huggingface-cli search ...              # legacy alias
```
Filters mirror the front-matter: `task`, `library`, `language`, `license`,
`tags`, `author`. See [`hub/02.search_and_info.py`](hub/02.search_and_info.py).

## 6. Downloading & the cache

Three download primitives (all in `huggingface_hub`, all used by the high-level
libraries under the hood):

| Function | Gets | Use when |
|---|---|---|
| `hf_hub_download(repo_id, filename)` | **one** file | you need just `config.json` or one shard |
| `snapshot_download(repo_id)` | **all** matching files | you want the whole repo (optionally `allow_patterns`) |
| `Auto*.from_pretrained(repo_id)` | what the model needs | normal `transformers` usage (calls the above) |

All three write into a **shared local cache** so repeated loads are instant and
multiple libraries deduplicate.

### The cache layout
```
$HF_HOME/                         # default: ~/.cache/huggingface
  hub/
    models--<org>--<name>/        # '/' → '--'
      blobs/      <sha256>        # content-addressed actual bytes
      snapshots/  <commit-sha>/   # a revision: symlinks → blobs
      refs/       main            # branch → commit map
    datasets--<org>--<name>/
  token                           # your auth token (after login)
```
Downloads are **content-addressed**: two snapshots that share a file share one
blob (symlinked), so pinning many revisions is cheap. Downloads are **resumable**
and **atomic** (temp file → rename).

### Cache & path environment variables
| Var | Controls | Default |
|---|---|---|
| `HF_HOME` | root for everything HF | `~/.cache/huggingface` |
| `HF_HUB_CACHE` | just the hub blob/snapshot cache | `$HF_HOME/hub` |
| `HF_DATASETS_CACHE` | datasets cache | `$HF_HOME/datasets` |
| `HF_HUB_OFFLINE=1` | never hit the network; use cache only | unset |
| `HF_HUB_ENABLE_HF_TRANSFER=1` | use the Rust `hf_transfer` for fast parallel downloads | unset |
| `HF_TOKEN` | auth token (CI-friendly, instead of `login()`) | unset |

Inspect / prune the cache:
```bash
hf cache scan          # table of repos, sizes, last-used (legacy: huggingface-cli scan-cache)
hf cache delete        # interactive cleanup       (legacy: huggingface-cli delete-cache)
```

## 7. Authentication

You need a token only for: gated/private repos, pushing, and higher rate limits.

```bash
hf auth login                 # interactive; stores token in $HF_HOME/token
                              # (legacy: huggingface-cli login)
export HF_TOKEN=hf_xxx        # non-interactive / CI
```
```python
from huggingface_hub import login, whoami
login(token="hf_xxx")         # or rely on HF_TOKEN env
print(whoami())               # confirm identity
```
Tokens have **scopes**: `read`, `write`, and fine-grained per-repo tokens.
Never commit a token; the libraries read `HF_TOKEN` / the cached token file.

## 8. Offline & reproducible operation

- Pre-download in a connected environment, then run with `HF_HUB_OFFLINE=1`.
- Pin **revisions** (commit SHAs) for byte-for-byte reproducibility.
- Prefer `safetensors` (memory-mapped, no arbitrary-code `pickle` risk) over
  `.bin`. `transformers` prefers it automatically when present.
- Every example in this section is **offline-safe**: model/dataset loading is
  wrapped in `try/except` and degrades to a tiny local fallback that still
  demonstrates the API shape, so `python file.py` exits 0 with or without a
  network. See the `_lib.py` helper in each folder.
