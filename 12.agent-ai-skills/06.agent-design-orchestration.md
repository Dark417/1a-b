# 06 · Agent Design & Orchestration

> Skill #06 (Tier 1 — Core). *Agent loops, tool use, memory, multi-agent
> topologies, MCP.* ~70% of sources and rising fastest — the highest-opportunity,
> lowest-supply category of 2026 (R1/R2). See the rationale in
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

Building **agents**: systems where an LLM runs in a loop, decides which **tools**
to call, observes the results, and keeps going until a goal is met. Covers the
agent loop, tool/function calling, planning/reasoning, **memory and context
management**, multi-agent topologies (supervisor, pipeline, swarm), and
interoperability protocols — chiefly **MCP** (Model Context Protocol).

It exists because agents are **how LLMs move from chat to *doing work*** — filing
PRs, running analyses, operating software, orchestrating multi-step tasks. The
talent pool is thin and demand is exploding.

## 2. Why employers want it

R1/R2 call agentic the top-opportunity, lowest-supply skill of 2026. The signal:

- **You can build systems that take actions**, not just answer — the frontier of
  product value.
- **You manage the hard parts**: looping without runaway cost, tool design,
  context/memory over long horizons, error recovery, and human-in-the-loop gates.
- **You know the ecosystem**: the agent frameworks, when to use one vs a plain
  loop, and emerging standards like MCP (skill [`32.mcp-agent-protocols.md`](32.mcp-agent-protocols.md)).

## 3. Mental model

An agent is a **loop around an LLM with tools**:

```
        ┌─────────────────────────────────────────────┐
        ▼                                             │
  observe (context) ─► LLM decides ─► tool_use? ──yes─┘ execute tool, append result
        ▲                              │
        │                             no
   (memory, state)                     ▼
                                  final answer
```

In API terms: send messages + tool definitions → if `stop_reason == "tool_use"`,
execute the requested tool(s), append the `tool_result`, and call again; repeat
until `end_turn`. That's it — everything else is engineering *around* this loop.

**The four design problems** that separate a demo agent from a real one:

1. **Tool surface.** What tools, with what typed schemas and descriptions? Start
   with a broad `bash`-style tool for breadth; promote an action to a *dedicated*
   tool when you need to gate it (destructive/irreversible), render it, audit it,
   or run it in parallel safely.
2. **Context management.** Context grows every turn. Use **compaction**
   (summarize old turns), **context editing** (prune stale tool results), and
   **memory** (persist across sessions) so the loop stays affordable and coherent.
3. **Control & safety.** Bound the loop (max iterations / token budget), gate
   side-effecting tools behind human approval, validate tool inputs, and recover
   from tool errors.
4. **Topology.** One agent, or many? A **supervisor** delegates to specialist
   sub-agents; a **pipeline** chains fixed stages; a **swarm** hands off
   peer-to-peer. Sub-agents isolate context and can use cheaper models.

**Should you even build an agent?** Only if the task is multi-step and hard to
fully specify, the outcome justifies the cost/latency, the model is capable at
it, and errors are recoverable (tests, review, rollback). Otherwise a single call
or a fixed **workflow** (code-orchestrated steps) is simpler and more reliable.

## 4. The landscape

**Build-it-yourself.** A plain agentic loop on the provider API (full control,
the SDK `tool_runner` for the loop, or a manual loop for approval gates) — often
the right default. *Managed agents* (Anthropic-hosted loop + sandbox) when you
want the orchestration and tool-execution container run for you.

**Frameworks.**

| Framework | Shape | Good for |
|---|---|---|
| **LangGraph** | explicit state-machine graph | controllable, branching, durable agents |
| **CrewAI** | role-based multi-agent crews | quick multi-agent prototypes |
| **AutoGen** | conversational multi-agent | research, agent-to-agent dialogue |
| **OpenAI Agents SDK** | provider-native loop + handoffs | OpenAI-stack agents |
| **Anthropic Agent SDK / Claude Code** | tool loop + skills + MCP | coding agents, Claude-native |
| **Smolagents / Pydantic-AI / Atomic** | lightweight, typed | minimal, typed agents |

**Memory.** Short-term (the message window) · summarized/episodic · long-term
(vector store of past interactions, retrieved like RAG) · structured (a memory
file/store the agent reads and writes). Skill [`09`](09.vector-databases-embeddings.md)
backs agent memory.

**Reasoning patterns.** ReAct (reason+act interleaved), plan-then-execute,
reflection/self-critique, tree-of-thought, and tool-use planning. Modern models
do much of this natively with adaptive thinking.

**MCP (Model Context Protocol).** An open standard for exposing tools, resources,
and prompts to agents over a uniform interface — build a server once, any
MCP-capable client can use it. The interoperability layer for agentic systems
(skill [`32`](32.mcp-agent-protocols.md); also A2A, ACP).

**Orchestration frameworks** for multi-step *workflows* (graphs of LLM/tool/
retrieval steps with branching, retries, state): LangGraph flows, DSPy, Haystack,
Burr (skill [`29`](29.orchestration-workflow-frameworks.md)).

## 5. Worked example

A minimal but real agent loop with **bounded iterations**, a **read-only tool**
and a **gated side-effecting tool**, using the Anthropic SDK and `claude-opus-4-8`.
This is the skeleton every agent shares.

```python
"""mini_agent.py — bounded agent loop with a gated tool. Anthropic SDK."""
from anthropic import Anthropic

client = Anthropic()

TOOLS = [
    {
        "name": "search_docs",
        "description": "Search internal docs. Use whenever you need facts you don't have.",
        "input_schema": {
            "type": "object",
            "properties": {"query": {"type": "string"}},
            "required": ["query"],
        },
    },
    {
        "name": "send_email",          # side-effecting -> we gate it
        "description": "Send an email. Irreversible; only after explicit confirmation.",
        "input_schema": {
            "type": "object",
            "properties": {"to": {"type": "string"}, "body": {"type": "string"}},
            "required": ["to", "body"],
        },
    },
]

def search_docs(query: str) -> str:
    return "Refunds are allowed within 30 days."          # stub

def send_email(to: str, body: str) -> str:
    # Human-in-the-loop gate for an irreversible action.
    if input(f"Send email to {to!r}? [y/N] ").strip().lower() != "y":
        return "User DENIED sending the email."
    return f"Email sent to {to}."

DISPATCH = {"search_docs": search_docs, "send_email": send_email}

def run(goal: str, max_steps: int = 6) -> str:
    messages = [{"role": "user", "content": goal}]
    for _ in range(max_steps):                            # bound the loop -> no runaway cost
        resp = client.messages.create(
            model="claude-opus-4-8", max_tokens=1024, tools=TOOLS, messages=messages,
        )
        if resp.stop_reason != "tool_use":
            return next(b.text for b in resp.content if b.type == "text")
        messages.append({"role": "assistant", "content": resp.content})
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                try:
                    out = DISPATCH[block.name](**block.input)
                    results.append({"type": "tool_result",
                                    "tool_use_id": block.id, "content": out})
                except Exception as e:                    # surface errors so the agent can recover
                    results.append({"type": "tool_result", "tool_use_id": block.id,
                                    "content": f"Error: {e}", "is_error": True})
        messages.append({"role": "user", "content": results})
    return "Stopped: hit the step budget without finishing."

if __name__ == "__main__":
    print(run("Find the refund window and email it to ops@acme.com."))
```

Notes that make it production-shaped: the loop is **bounded** (cost control), the
irreversible tool is **gated** (safety), tool errors are returned as
`is_error` results so the agent can **recover**, and `response.content` is
appended verbatim with matching `tool_use_id`s. Scale this with compaction/
memory for long horizons and sub-agents for parallel work.

## 6. How to learn it

**Beginner (0–3 months).** Build the loop above by hand; add 2–3 tools; bound
iterations; gate one destructive tool. *Milestone:* a working tool-using agent
that recovers from a tool error.

**Intermediate / job-ready (3–9 months).** Add memory and compaction; build a
**supervisor + sub-agents** topology; use LangGraph or CrewAI for one project;
connect a tool via **MCP**; instrument traces (skill [`22`](22.llm-observability-monitoring.md)).
*Milestone:* a multi-tool, multi-step agent with memory, tracing, and an eval of
its trajectories (skill [`07`](07.evaluation-llm-testing.md)).

**Expert (9+ months).** Design robust topologies; control cost/latency over long
runs; harden against prompt injection through tools; build/operate MCP servers;
evaluate and gate agent behavior in CI. *Milestone:* a production agent doing real
work, with safety gates, observability, and a regression suite.

## 7. Interview signals

- **"Walk me through an agent loop."** observe → decide → act (tool) → observe →
  repeat until done; bounded iterations; append content verbatim; echo
  `tool_use_id`; handle tool errors. Bonus: when *not* to use an agent.
- **"How do you stop an agent from spiraling?"** Iteration/token budgets, gated
  side-effecting tools, validated inputs, error recovery, and observability to
  catch loops and runaway cost.
- **"Single agent vs multi-agent?"** Multi-agent (supervisor/pipeline/swarm)
  buys context isolation and specialization, at the cost of coordination overhead
  and latency. Start single; split when a clear sub-task or parallelism warrants.
- **"How do you manage context over a long run?"** Compaction (summarize),
  context editing (prune stale results), and memory (persist across sessions) —
  and keep the cached prefix stable for cost.
- **"What's MCP and why does it matter?"** A standard interface for tools/
  resources/prompts; build a server once, any client uses it — the interop layer
  for agents.
