## 1. What it is

Working with **embeddings** (text/image → dense vectors) and **vector databases**
(stores that index those vectors for fast similarity search). Covers embedding
model selection, similarity metrics, **approximate nearest-neighbor (ANN)**
indexes and their tradeoffs (HNSW, IVF, PQ), metadata filtering, hybrid (dense +
sparse) search, and operating a vector store.

It exists because **it's the substrate under RAG (#05) and agent memory (#06).**
You can't build either well without understanding how vectors are stored,
indexed, and searched — and the tradeoffs that decide recall, latency, and cost.

## 2. Why employers want it

It underpins the two most-demanded application patterns. The signal:

- **You can build retrieval that actually works** — picking the right embedding
  model and index for the data, latency, and scale.
- **You make the recall/latency/cost tradeoff consciously** — exact vs ANN, HNSW
  vs IVF, quantization, hybrid search.
- **You can operate it at scale** — sharding, filtering, freshness, multi-tenant
  isolation.

## 3. Mental model

**Embeddings turn meaning into geometry; the vector DB makes search over that
geometry fast.**

```
text ─► embedding model ─► vector (e.g. 768-d, unit-normalized)
                                   │
                  vector DB: ANN index + metadata + payload
                                   │
query vector ─► nearest-neighbor search (+ filters) ─► top-k ids/payloads
```

**Similarity metric** — cosine (angle; the default for normalized text
embeddings), dot product (cosine if normalized), Euclidean (L2). Normalize, then
cosine ≈ inner product (fast).

**Exact vs ANN** — exact (brute-force) search is $O(N)$ per query: fine for
thousands, too slow for millions. **ANN** trades a little recall for huge speed
via clever indexes. The core tradeoff is **recall vs latency vs memory**, tuned
per index.

**The indexes:**

- **Flat** — exact, no index; baseline, small data.
- **HNSW** (graph) — navigate a multi-layer proximity graph; great recall +
  latency, higher memory; the most common default. Knobs: `M` (graph degree),
  `ef_construction`/`ef_search` (effort vs recall).
- **IVF** (inverted file) — cluster vectors, search only the nearest clusters
  (`nprobe`); memory-lean, tunable. Often combined with PQ.
- **PQ** (product quantization) — compress vectors into codes; big memory
  savings at some recall cost (IVF-PQ, OPQ).

**Hybrid search** — combine dense (semantic) with sparse/BM25 (lexical) and fuse
(reciprocal-rank fusion). Catches both paraphrases and exact terms/codes/names.

**Metadata filtering** — restrict search by attributes (date, source, tenant,
ACL). Pre- vs post-filtering affects recall and must be handled carefully.

## 4. The landscape

**Embedding models.** Open: sentence-transformers, **BGE** (BAAI), E5, GTE,
Nomic, Jina; hosted: OpenAI `text-embedding-3-{small,large}`, Cohere `embed`,
Voyage. Pick by **MTEB** benchmark, domain fit, dimension (cost/quality), max
sequence length, and multilingual need. **Matryoshka** embeddings let you
truncate dimensions to trade quality for cost.

**Vector stores.**

| Store | Shape | Best for |
|---|---|---|
| **FAISS** | in-process library | research, embedded, fast local |
| **Chroma** | local/lightweight | prototypes, small apps |
| **Qdrant** | server, Rust | filtering-heavy, production |
| **Milvus** | server, scalable | very large scale |
| **Weaviate** | server, hybrid+modules | hybrid search, schemas |
| **pgvector** | Postgres extension | "already have Postgres", transactional |
| **Pinecone** | managed SaaS | no-ops, serverless scale |
| **Elasticsearch/OpenSearch, Redis** | search/cache engines | existing infra, hybrid |

**Operational concerns.** Upsert/delete (freshness), index build vs query
tradeoffs, sharding/replication, batching embeddings, multi-tenancy (namespace/
filter isolation), and cost (memory dominated by vector count × dimension; cut
with quantization or smaller models).

## 5. Worked example

Build an HNSW index, compare it to exact search, and show the
**recall/speed tradeoff** plus metadata filtering — the core skills in one
runnable script (FAISS, local).

```python
"""vectors_demo.py — exact vs HNSW ANN, recall tradeoff, metadata filter. CPU."""
import numpy as np
import faiss

rng = np.random.default_rng(0)
N, d = 50_000, 64
data = rng.normal(size=(N, d)).astype("float32")
faiss.normalize_L2(data)                     # cosine == inner product after this
sources = rng.integers(0, 3, size=N)         # a metadata field: source in {0,1,2}

q = data[:5].copy()                          # 5 query vectors (their true NN is themselves)

# 1. Exact baseline (ground truth for recall).
flat = faiss.IndexFlatIP(d); flat.add(data)
_, gt = flat.search(q, 10)

# 2. HNSW ANN index — tune ef_search for the recall/latency tradeoff.
hnsw = faiss.IndexHNSWFlat(d, 32)            # M = 32 (graph degree)
hnsw.hnsw.efConstruction = 80
hnsw.add(data)
for ef in (16, 64, 128):
    hnsw.hnsw.efSearch = ef                  # higher ef -> better recall, slower
    _, ann = hnsw.search(q, 10)
    recall = np.mean([len(set(a) & set(g)) / 10 for a, g in zip(ann, gt)])
    print(f"efSearch={ef:3d}  recall@10={recall:.2f}")

# 3. Metadata filtering: search only within source == 1 (here via an IDSelector).
sel = faiss.IDSelectorBatch(np.where(sources == 1)[0])
params = faiss.SearchParametersHNSW(sel=sel)
_, filtered = hnsw.search(q[:1], 5, params=params)
print("filtered hits all from source 1:", bool(np.all(sources[filtered[0]] == 1)))
```

The lesson the output teaches: **recall climbs with `efSearch` but so does
latency** — that knob *is* the tradeoff you tune in production. At real scale
you'd add IVF-PQ for memory, hybrid (dense+BM25) fusion, batched embedding, and a
managed store (Qdrant/pgvector/Pinecone) with persistent metadata filtering.

## 6. How to learn it

**Beginner (0–3 months).** Embed text with sentence-transformers; build a FAISS
flat index; do top-k search; understand cosine vs L2. *Milestone:* a semantic
search over a few thousand docs.

**Intermediate / job-ready (3–9 months).** Use HNSW and IVF; measure
recall/latency; add metadata filtering and hybrid search; stand up a server store
(Qdrant or pgvector); choose an embedding model via MTEB. *Milestone:* a
production-shaped retrieval service with tuned ANN and filtering.

**Expert (9+ months).** Quantization (PQ/OPQ) and memory budgeting; sharding/
replication; multi-tenant isolation; freshness pipelines; benchmark embedding
models on *your* data. *Milestone:* you operate a large, fast, fresh vector store
backing a real RAG/agent system.

## 7. Interview signals

- **"HNSW vs IVF — when each?"** HNSW: best recall/latency, higher memory,
  default. IVF(-PQ): memory-lean, tunable via `nprobe`, great at huge scale. Name
  the recall/latency/memory triangle.
- **"Cosine vs dot vs Euclidean?"** Cosine for normalized text embeddings (angle,
  not magnitude); dot == cosine if normalized; L2 when magnitude matters. Pick to
  match how the embedding model was trained.
- **"How do you filter by metadata without killing recall?"** Native filtered ANN
  (pre-filtering in the index) over post-filtering; understand how the store
  handles it; partition/namespace for tenants.
- **"How do you pick an embedding model?"** MTEB + domain fit + dimension/cost +
  max length + multilingual; benchmark on your own queries, not just the
  leaderboard.
- **"Your vector DB is using too much RAM."** Smaller dim / Matryoshka, product
  quantization, IVF-PQ, fewer vectors via better chunking, or disk-backed indexes.
