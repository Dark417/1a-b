## The loop in one picture

Claude Code is, at its core, a loop around the Anthropic **Messages API** with
tools. Everything else is policy and ergonomics on top.

```
                ┌─────────────────────────────────────────────┐
                │  gather context (system prompt, CLAUDE.md,   │
                │  conversation history, tool results so far)  │
                └───────────────────────┬─────────────────────┘
                                        │
                                        ▼
                          ┌──────────────────────────┐
                          │  call the model with the  │
                          │  transcript + tool schemas │  ← streams text/thinking
                          └─────────────┬─────────────┘
                                        │ stop_reason?
              end_turn ◄────────────────┼────────────────► tool_use
                  │                                            │
                  ▼                                            ▼
              done; await                          ┌────────────────────────┐
              next user turn                        │ gate each tool call    │ ← permissions
                                                    │ (allow / ask / deny)   │
                                                    │ run the allowed ones   │ ← tools
                                                    │ (read-only in parallel)│
                                                    └───────────┬────────────┘
                                                                │ tool_result blocks
                                                                ▼
                                              append results, maybe compact, loop ↑
```

### The turn cycle, concretely

1. **Gather context.** The API is *stateless* — every turn resends the full
   transcript: the system prompt, then the alternating user/assistant messages,
   with prior tool calls as `tool_use` blocks and their outputs as `tool_result`
   blocks.
2. **Call the model** with `tools=[...]` (each tool's name, description, and
   JSON-Schema `input_schema`). The response **streams** back as text and, when
   the model wants to act, one or more `tool_use` blocks. The `stop_reason`
   tells the harness what happened:
   * `end_turn` → the model is finished; hand control back to the user.
   * `tool_use` → the model requested tools; execute them and continue.
   * `max_tokens`, `pause_turn`, `refusal` → other terminal/continuation cases.
3. **Execute tools.** For each `tool_use` block: check permissions, run the
   tool, capture the result. Read-only tools (search, read) can run in parallel.
4. **Observe.** Append the assistant message (with its `tool_use` blocks) and a
   user message carrying the matching `tool_result` blocks (correlated by
   `tool_use_id`). Loop back to step 1.

The mini-agent implements this exactly. In Python:

```python
while True:
    step = backend.step(messages, tool_schemas)   # text + tool_calls + done
    context.add_assistant(step.text, step.tool_calls)
    if not step.tool_calls:
        break                                      # == stop_reason "end_turn"
    results = run_tools(step.tool_calls)           # gate + execute
    context.add_tool_results(results)              # tool_result blocks
    context.maybe_compact()                        # token-budget management
```

## The system prompt & context management

A coding agent's context window holds, in priority order:

1. **A frozen system prompt** — the agent's role, tool-use guidance, and
   safety/behaviour rules. It is kept *byte-stable* so it can be **prompt-cached**
   (a single changing byte near the front invalidates the cache for everything
   after it). Volatile facts (current date, mode) are injected *later* in the
   message stream, not into the system prompt.
2. **Project memory** — `CLAUDE.md` files and accumulated auto-memory, giving
   the agent durable, project-specific instructions.
3. **The live conversation** — user turns, assistant turns, and the growing pile
   of `tool_use` / `tool_result` blocks.

### Streaming

Output is **streamed** so the user sees text appear token-by-token instead of
waiting for the whole turn — important because agentic turns can be long. The
SDK exposes a token stream; the harness prints text deltas as they arrive and
assembles the final message (with its tool calls) at the end. The mini-agent
mirrors this with a `stream()` method that yields text chunks and then resolves
the full `Step` (see `Backend.stream` in [`llm.py`](../python/llm.py) /
[`llm.rb`](../ruby/llm.rb)).

### Token budget & compaction

Because the whole transcript is resent every turn, a long session grows toward
the context-window limit. Two complementary techniques keep it bounded:

* **Compaction** — when the conversation approaches the limit, earlier context
  is **summarized** into a compact form and the verbatim old turns are dropped,
  preserving the system prompt and the most recent turns. (Anthropic's API
  offers this server-side; agents can also do it client-side.)
* **Context editing** — *prune* stale tool results / thinking blocks rather than
  summarize them, when old outputs are simply no longer relevant.

The mini-agent's [`context.py`](../python/context.py) / [`context.rb`](../ruby/context.rb)
implements a budget + compaction strategy: it estimates tokens, and once the
estimate crosses a threshold it replaces the oldest run of messages with a
single summary message, keeping the most recent `keep_recent` turns verbatim.
The summary is built deterministically (which tools ran, first lines of results)
so the mechanism is fully offline and inspectable; a real agent asks the model
to summarize instead.

## Why a loop (not a workflow)?

A hard-coded workflow ("read → edit → test") can't handle tasks whose steps
aren't known in advance. The agent loop lets the *model* decide the next action
from the current observations: if a test fails, it reads the traceback and edits
again; if a file is missing, it greps for the right one. The harness's job is
not to plan the work — it's to **execute tools safely, feed results back, and
manage context** so the model can keep reasoning. That division of labor — model
decides, harness gates/executes/observes — is the whole architecture.
