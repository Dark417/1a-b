# 13 · AI System Design

> Skill #13 (Tier 2 — Important). *Architecting end-to-end LLM systems for
> latency, cost, quality, and reliability.* ~50%, weighted up by seniority — the
> skill that separates senior from junior. See the rationale in
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

Architecting **end-to-end LLM systems**: the data flow and the layers —
retrieval, model, tool, cache — and the cross-cutting decisions about
**latency, cost, quality, and reliability**: fallbacks, rate limiting, caching,
multi-tenancy, and evaluation in the loop.

It exists because **senior/staff hires own *systems*, not snippets.** Anyone can
make one API call; designing a system that's fast, cheap, correct, and reliable
under real traffic — with the right tradeoffs — is the differentiating skill.

## 2. Why employers want it

It's the line between a senior and a junior, weighted heavily by level (S1, S2,
S8, S11, S19, S20, R9). The signal:

- **You think in systems and tradeoffs**, not features — you reason about the
  whole pipeline and where it breaks.
- **You design for the four constraints at once** — latency *and* cost *and*
  quality *and* reliability, and you know they trade off.
- **You plan for failure** — fallbacks, degradation, rate limits, retries,
  multi-tenancy, and evaluation built in from the start.

## 3. Mental model

An LLM system is a **pipeline of layers**, each with a quality/latency/cost knob:

```
client ─► gateway (auth, rate limit) ─► cache ─► orchestrator
                                         │            │
                                  (semantic/exact)    ├─► retrieval (vector DB, #09)
                                                       ├─► model (router: cheap↔strong, #16)
                                                       ├─► tools / agents (#06)
                                                       └─► guardrails (#19)
                                                            │
                                          eval + observability + fallbacks (#07/#22)
```

**The four constraints** (you can rarely max all four — design the tradeoff
deliberately):

- **Latency** — streaming, smaller/faster models, caching, parallelism,
  speculative decoding, reduced retrieval, async where the UX allows.
- **Cost** — prompt caching, model routing (Haiku-class for easy, Opus-class for
  hard), batching, trimming prompts, semantic caching, self-host vs API.
- **Quality** — better retrieval/reranking, stronger model, more reasoning, evals
  in the loop, guardrails, human-in-the-loop for high stakes.
- **Reliability** — timeouts, retries, **fallbacks** (model/provider), graceful
  degradation, rate limiting, circuit breakers, idempotency, multi-region.

**Design patterns** to reach for: a **model router** (route by difficulty/cost),
**caching tiers** (exact + semantic), a **fallback chain** (provider/model
failover), **async + queue** for non-interactive work, **multi-tenancy**
(isolation, per-tenant limits/quotas), and **evaluation in the loop** (offline
gate + online monitoring).

**The interview frame** (works for any AI-system-design question): clarify
requirements & scale → define the data flow → choose model/retrieval/tool layers
→ address latency/cost/quality/reliability explicitly → name failure modes and
mitigations → describe evaluation and monitoring.

## 4. The landscape

**Reference architectures.**

| Pattern | Shape | When |
|---|---|---|
| **RAG service** | retrieve → assemble → generate → cite | grounded Q&A over your data (#05) |
| **Agentic system** | loop: model + tools + memory | multi-step tasks, "doing work" (#06) |
| **Pipeline/workflow** | fixed graph of LLM/tool steps | structured multi-step (more reliable than open agents) (#29) |
| **Classify-then-route** | cheap classifier → specialized path | cost control, intent routing |
| **Batch processing** | async queue, 50%-price batch | bulk, non-latency-sensitive |

**Cross-cutting components.** API gateway (auth, rate limit) · **caching** (exact
KV + semantic/embedding cache) · **model router** (LiteLLM/OpenRouter, or custom)
· **fallback/failover** chains · **queue** (SQS/PubSub/Kafka) for async ·
**guardrails** (input/output filtering) · **observability** (traces, token/cost,
SLOs) · **eval harness** (gate + online).

**Scaling & multi-tenancy.** Per-tenant rate limits and quotas, data isolation
(namespaces/filters in the vector store), noisy-neighbor protection, and cost
attribution per tenant.

**Tradeoff levers cheat-sheet.** Faster → smaller model, cache, stream, less
retrieval. Cheaper → route, cache, batch, trim, self-host. Better → rerank,
bigger model, more reasoning, evals/guardrails. More reliable → fallbacks,
timeouts/retries, degrade gracefully, multi-region.

## 5. Worked example

A **model router with a fallback chain and a semantic cache** — the three
patterns that show up in almost every LLM system-design answer — sketched as
correct, idiomatic Python around the Anthropic SDK (`claude-opus-4-8` for hard,
`claude-haiku-4-5` for easy).

```python
"""ai_system.py — router + semantic cache + fallback chain (system-design core)."""
import numpy as np
from anthropic import Anthropic, APIStatusError
from sentence_transformers import SentenceTransformer

client = Anthropic()
embedder = SentenceTransformer("BAAI/bge-small-en-v1.5")

# --- Semantic cache: reuse answers for near-duplicate questions (cost + latency) ---
_cache: list[tuple[np.ndarray, str]] = []
def cache_lookup(qvec, threshold=0.92):
    for vec, answer in _cache:
        if float(vec @ qvec) >= threshold:        # cosine on normalized vectors
            return answer
    return None

# --- Router: send easy queries to a cheap model, hard ones to a strong model ---
def route(query: str) -> str:
    hard = len(query) > 200 or any(w in query.lower()
                                   for w in ("prove", "design", "analyze", "why"))
    return "claude-opus-4-8" if hard else "claude-haiku-4-5"

# --- Fallback chain: try the routed model, then degrade gracefully on failure ---
FALLBACKS = {"claude-opus-4-8": "claude-haiku-4-5", "claude-haiku-4-5": None}

def answer(query: str) -> str:
    qvec = embedder.encode([query], normalize_embeddings=True)[0]
    if (hit := cache_lookup(qvec)) is not None:
        return f"[cache] {hit}"

    model = route(query)
    while model is not None:
        try:
            resp = client.messages.create(
                model=model, max_tokens=512,
                messages=[{"role": "user", "content": query}],
            )
            text = next(b.text for b in resp.content if b.type == "text")
            _cache.append((qvec, text))            # populate the cache
            return f"[{model}] {text}"
        except (APIStatusError, Exception):
            model = FALLBACKS.get(model)           # fail over to the next model
    return "Service temporarily unavailable, please retry."   # graceful degradation

if __name__ == "__main__":
    print(answer("What is 2+2?"))                  # -> routed to Haiku
    print(answer("Design a multi-tenant RAG system and analyze the tradeoffs."))  # -> Opus
```

This one file demonstrates the load-bearing system-design ideas: a **router**
(cost), a **semantic cache** (cost + latency), and a **fallback chain with
graceful degradation** (reliability). A real system layers retrieval, guardrails,
rate limiting, async queues, evals, and observability around this core — but the
*reasoning* (which constraint each component serves) is exactly what an interview
probes.

## 6. How to learn it

**Beginner (0–3 months).** Build one full pipeline (RAG or agent) end to end and
notice where it's slow/expensive/fragile. *Milestone:* a working system you can
diagram with its data flow.

**Intermediate / job-ready (3–9 months).** Add caching, a model router,
fallbacks, rate limiting, and monitoring; practice system-design questions out
loud; estimate latency/cost for each path. *Milestone:* a system with explicit
latency/cost/quality/reliability handling, and a whiteboard design you can defend.

**Expert (9+ months).** Design for scale and multi-tenancy; quantify tradeoffs
with numbers; build evaluation into the architecture; lead design reviews.
*Milestone:* you own the architecture of a production LLM system and can justify
every layer.

## 7. Interview signals

- **"Design a customer-support AI for 10k tenants."** Strong answer walks the
  pipeline (gateway → cache → retrieval → router → model → guardrails → eval),
  addresses each of latency/cost/quality/reliability, and handles multi-tenancy
  (isolation, per-tenant limits, cost attribution).
- **"How do you cut p99 latency in half?"** Stream, route to a faster model,
  cache (exact+semantic), parallelize retrieval, reduce context, speculative
  decoding — and measure the impact of each.
- **"What happens when the model provider goes down?"** Fallback chain (model/
  provider failover), timeouts/retries, graceful degradation, circuit breaker,
  and an SLO/alert.
- **"How do you keep costs predictable?"** Router + caching + batching + prompt
  trimming + per-tenant quotas + budgets/alerts; quantify cost per request.
- **"Where does evaluation fit in the architecture?"** Offline eval gate before
  deploy + online quality/cost monitoring + feedback loop — built into the
  system, not bolted on.
