# 07 · Multi-GPU & Distributed Training — parallelism, collectives, frameworks

> One GPU runs out of memory or time. Scaling out introduces a new problem:
> **communication**. This file covers the three axes of parallelism (data,
> tensor, pipeline — plus their combination), the **collective operations** that
> move gradients and activations between GPUs, **NCCL** (the transport), and the
> frameworks that package it all (DDP, FSDP, DeepSpeed, Megatron-LM). Concepts +
> API sketches; the focus is the mental model an engineer needs to choose and
> configure these.

---

## 1. Why distribute, and the central tension

Two limits force multi-GPU:
- **Throughput** — a dataset/epoch takes too long on one GPU.
- **Memory** — the model + activations + optimizer states don't fit. A model with
  `P` params in fp16 needs ~`2P` bytes for weights, ~`2P` for gradients, and (Adam)
  ~`12P` for optimizer states (fp32 master + two moments) ⇒ ~`16P` bytes just for
  state. A 70B model ⇒ >1 TB ⇒ many GPUs.

The tension: every form of parallelism trades **compute** for **communication**.
The art is overlapping communication with compute and minimizing how much must
cross the (slower-than-DRAM) interconnect — **NVLink** within a node (~hundreds of
GB/s) and **InfiniBand/Ethernet** between nodes (slower still).

---

## 2. The three axes of parallelism

### Data parallelism (DP) — replicate the model, split the batch
Every GPU holds a **full copy** of the model and processes a different shard of
the minibatch. After the backward pass, gradients are averaged across GPUs with an
**all-reduce**, so every replica applies the same update and stays in sync.

- **When:** the model fits on one GPU; you want more throughput. The default,
  simplest, most scalable form. (PyTorch **DDP**.)
- **Cost:** one all-reduce of the full gradient per step (overlapped with
  backward by bucketing gradients as they're produced).
- **Limit:** doesn't reduce per-GPU memory — the whole model is replicated.
  (Solved by FSDP/ZeRO, §5.)

### Tensor / model parallelism (TP) — split each layer across GPUs
Partition the **weight matrices** of a layer across GPUs: each GPU computes a
*slice* of every matmul, and they combine via collectives. E.g. split a linear
layer's columns across GPUs (each computes part of the output), then **all-gather**
or **all-reduce** to assemble the full activation. (Megatron-LM's row/column
parallel linear layers; attention heads split across GPUs.)

- **When:** a single layer is too big, or you need lower latency than DP allows.
- **Cost:** **communication inside every layer** (multiple all-reduces per
  forward/backward) ⇒ needs the fast **intra-node NVLink**; rarely crosses nodes.
- **Limit:** communication-heavy; usually confined to the GPUs of one node.

### Pipeline parallelism (PP) — split the model by layers (depth)
Put different **stages** (groups of layers) on different GPUs; activations flow
GPU0 → GPU1 → … like an assembly line. To keep all stages busy, the minibatch is
split into **micro-batches** that flow through the pipeline so stage *k* works on
micro-batch *i* while stage *k+1* works on *i-1* (GPipe / 1F1B schedules).

- **When:** the model is too deep/large to fit even with TP; spans many nodes.
- **Cost:** point-to-point **send/recv** of activations between adjacent stages,
  plus a **pipeline bubble** (idle time at fill/drain) that micro-batching shrinks
  but never eliminates.
- **Limit:** the bubble; load-balancing stages.

### 3-D parallelism — combine all three
Large-model training (GPT-3/Megatron/DeepSeek scale) uses **all three at once**:
TP within a node (NVLink), PP across nodes (depth), DP across the resulting groups
(replicas) — often **+ sequence/context parallelism** for long context and **ZeRO
sharding** for optimizer state. Choosing the (DP, TP, PP) factorization to fit
memory and minimize communication is the core scaling-engineering problem.

| Axis | Splits | Communication | Reduces memory of |
|---|---|---|---|
| Data | the batch | all-reduce of gradients / step | nothing (replicated) — unless ZeRO |
| Tensor | weights within a layer | all-reduce/all-gather *inside* each layer | weights + activations |
| Pipeline | layers (depth) | send/recv between stages | weights + activations |

## 3. Collective operations — the communication primitives

Distributed training is built on a handful of **collectives** (MPI heritage,
implemented by NCCL). Know what each does:

```
all-reduce:    every rank ends with the SUM (or max/avg) of all ranks' tensors.
               = reduce-scatter + all-gather. The workhorse of data parallelism.
reduce-scatter: sum across ranks, but each rank keeps only its 1/N slice.
all-gather:    every rank ends with the concatenation of all ranks' shards.
broadcast:     rank 0's tensor copied to all ranks (e.g. initial weights).
reduce:        sum to a single root rank.
scatter/gather: distribute / collect shards to/from a root.
all-to-all:    each rank sends a distinct chunk to every other rank (MoE routing).
barrier:       synchronize all ranks.
```

The classic **ring all-reduce** moves each tensor around a ring of GPUs in
`2(N-1)` steps and is **bandwidth-optimal** (each link carries the data ~twice,
independent of N) — why all-reduce scales well. **FSDP/ZeRO** lean on
**reduce-scatter** (gradients) + **all-gather** (parameters) instead of a full
all-reduce, so each GPU only ever stores a shard.

---

## 4. NCCL — the transport

**NCCL** (NVIDIA Collective Communications Library) implements these collectives
optimized for GPU topology: it auto-detects **NVLink/NVSwitch** (intra-node),
**PCIe**, and **InfiniBand/RoCE** (inter-node), builds rings/trees over them, and
does GPU-to-GPU transfers (often GPUDirect RDMA, bypassing the CPU). It's the
backend PyTorch uses for GPU distributed training (`backend="nccl"`). You mostly
don't call it directly — DDP/FSDP/DeepSpeed do — but its **bandwidth and topology
are the ceiling** on scaling efficiency, and `NCCL_*` env vars are common tuning
knobs.

## 5. Frameworks (concepts + API sketches)

### PyTorch DDP — `DistributedDataParallel`
The standard **data-parallel** wrapper. One process per GPU; gradients
all-reduced (bucketed, overlapped with backward).

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")              # one process per GPU
torch.cuda.set_device(local_rank)
model = DDP(model.cuda(), device_ids=[local_rank])
# DistributedSampler shards the dataset; launch with torchrun --nproc_per_node=8
loss.backward()                              # gradients all-reduced here
optimizer.step()
```

### FSDP — `FullyShardedDataParallel` (PyTorch's ZeRO)
Data-parallel **but shards** parameters, gradients, and optimizer states across
ranks (ZeRO stages 1–3), so per-GPU memory drops ~`1/N`. Parameters are
**all-gathered** just-in-time for each layer's forward/backward, then freed;
gradients are **reduce-scattered**. Trains models far larger than one GPU while
staying conceptually data-parallel.

```python
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
model = FSDP(model, auto_wrap_policy=..., sharding_strategy=FULL_SHARD,
             mixed_precision=...)            # FULL_SHARD ≈ ZeRO-3
```

### DeepSpeed (Microsoft)
A training library whose headline feature is **ZeRO** (the idea PyTorch FSDP
adopted): partition optimizer state (ZeRO-1), + gradients (ZeRO-2), + parameters
(ZeRO-3), with **CPU/NVMe offload** (ZeRO-Infinity) to train enormous models on
few GPUs. Also: fused kernels, pipeline parallelism, and inference engines.
Config-file driven; wraps your model/optimizer with `deepspeed.initialize`.

### Megatron-LM (NVIDIA)
The reference implementation of **tensor + pipeline parallelism** for
transformers: column/row-parallel linear layers, parallel attention, efficient
3-D parallelism, sequence parallelism. The toolkit behind GPT-3-scale training;
often combined with DeepSpeed ("Megatron-DeepSpeed").

| Tool | Primary parallelism | Memory trick | Use when |
|---|---|---|---|
| DDP | data | none | model fits on 1 GPU; want throughput |
| FSDP | data + sharding | ZeRO-1/2/3 | model too big for 1 GPU, native PyTorch |
| DeepSpeed | data + sharding (+PP) | ZeRO + offload | huge models, few GPUs, config-driven |
| Megatron-LM | tensor + pipeline | 3-D parallel | giant transformers, max efficiency |

## 6. Practical guidance

- **Start with DDP.** It's simplest and scales throughput linearly when the model
  fits. Use `torchrun`, a `DistributedSampler`, and set seeds per rank.
- **Out of memory? → FSDP / ZeRO** before reaching for tensor/pipeline parallel.
  Sharding optimizer state (ZeRO-1) is cheap and often enough.
- **Single layer too big, or need lower latency → tensor parallel** within a node
  (NVLink); keep TP off the slow inter-node links.
- **Model too deep for a node → pipeline parallel** across nodes; tune
  micro-batches to shrink the bubble.
- **Overlap communication with compute** (DDP gradient bucketing, FSDP prefetch)
  and watch **scaling efficiency** (achieved vs ideal linear speedup) — falling
  efficiency means you're communication-bound; reduce world size per group, fuse,
  or rebalance the parallelism factorization.
- **Gradient accumulation** raises effective batch size without more GPUs.
