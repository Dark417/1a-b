# 11 · MLOps & LLMOps

> Skill #11 (Tier 2 — Important). *Versioning, serving, monitoring, rollback, and
> the model lifecycle.* ~55% of sources. See the rationale in
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

The operational discipline for ML/LLM systems across their lifecycle: experiment
tracking, **model & prompt versioning**, registries, CI/CD for models, serving,
**monitoring/observability**, drift detection, rollback, and **cost & latency
control**. *LLMOps* is the LLM-specific slice — prompt/version management, eval
gating, token/cost dashboards, guardrails — because LLM systems have new failure
modes (non-determinism, prompt drift, silent quality decay, runaway spend).

It exists because **LLM systems are live products that degrade silently.** Ops is
what keeps them reliable, current, and affordable after the demo.

## 2. Why employers want it

R1/R2/R11 flag ops as the gap between prototypes and durable products. The signal:

- **You keep systems reliable in production** — versioned, monitored, with
  rollback when something regresses.
- **You catch silent decay.** Drift, prompt regressions, and creeping cost get
  caught by your dashboards, not by an angry user.
- **You make iteration safe and repeatable** — reproducible runs, gated deploys,
  controlled rollouts.

## 3. Mental model

MLOps closes a **loop** around the model lifecycle:

```
   data ─► train/experiment ─► register (versioned) ─► deploy (CI/CD, canary)
    ▲                                                          │
    │                                                          ▼
 retrain / rollback ◄── monitor (quality, drift, cost, latency) ◄── serve
```

The five disciplines:

1. **Reproducibility** — track every experiment (params, data version, metrics,
   artifact) so any result can be reproduced and compared. Version data, code,
   model, *and prompts*.
2. **Registry & promotion** — models/prompts are versioned artifacts with stages
   (staging → prod); promotion is a deliberate, gated step.
3. **CI/CD for models** — build → **eval gate** (skill [`07`](07.evaluation-llm-testing.md))
   → deploy → canary → full rollout, with automatic rollback on regression.
4. **Monitoring** — operational (latency, error rate, throughput, **token/cost**)
   *and* quality (offline eval drift, online metrics, **input/output drift**,
   user feedback).
5. **Lifecycle response** — detect drift/regression → roll back or retrain/
   re-prompt → re-deploy. Close the loop.

**MLOps vs LLMOps**: classic MLOps centers on *retraining* (data drift → retrain →
redeploy). LLMOps centers on *prompts, evals, and serving cost* — you rarely
retrain a base model; you change prompts/RAG/config, so versioning prompts and
gating on evals matters more than retraining pipelines.

## 4. The landscape

**Experiment tracking & registry.** **MLflow** (tracking + registry, open) ·
**Weights & Biases** (tracking, sweeps, popular) · DVC (data/pipeline
versioning) · Neptune, Comet.

**Pipelines & orchestration.** Airflow / Dagster / Prefect (workflows) · Kubeflow
/ Vertex Pipelines / SageMaker Pipelines (ML-native) · Metaflow.

**Serving.** Hosted LLM APIs · vLLM/TGI/SGLang (self-hosted, skill [`16`](16.inference-optimization-serving.md))
· KServe / BentoML / Ray Serve / Seldon · managed endpoints (SageMaker/Vertex).

**LLM-specific (LLMOps).** Prompt management/versioning (LangSmith, Langfuse,
PromptLayer, Humanloop) · eval gating (Ragas/DeepEval/promptfoo, skill [`07`](07.evaluation-llm-testing.md))
· **observability** for tokens/cost/latency/traces (Langfuse, LangSmith, Phoenix/
Arize, Helicone, OpenLLMetry — skill [`22`](22.llm-observability-monitoring.md)) · guardrails
(skill [`19`](19.safety-alignment-guardrails.md)).

**Monitoring & drift.** Evidently / Arize / WhyLabs (data/model drift) ·
Prometheus + Grafana (ops metrics) · alerting on quality, drift, and cost SLOs.

**Deployment strategies.** Canary, blue-green, shadow, A/B; feature flags;
automatic rollback on metric regression.

## 5. Worked example

The MLOps core in miniature: **track an experiment, register the best model, gate
on an eval threshold** — the reproducibility + promotion loop, with MLflow.

```python
"""mlops_loop.py — track, gate, register with MLflow. Runs locally (file store)."""
import mlflow, mlflow.sklearn
from sklearn.linear_model import LogisticRegression
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.metrics import f1_score

X, y = make_classification(n_samples=1000, n_features=20, random_state=0)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.2, random_state=0)

mlflow.set_experiment("demo-classifier")
PROMOTION_F1 = 0.80                              # the quality gate

best = None
for C in (0.1, 1.0, 10.0):                       # sweep a hyperparameter
    with mlflow.start_run(run_name=f"C={C}"):
        model = LogisticRegression(C=C, max_iter=1000).fit(Xtr, ytr)
        f1 = f1_score(yte, model.predict(Xte))

        mlflow.log_param("C", C)                 # reproducibility: params...
        mlflow.log_metric("f1", f1)              # ...metrics...
        mlflow.sklearn.log_model(model, "model") # ...and the artifact
        print(f"C={C:<5} f1={f1:.3f}")
        if best is None or f1 > best[0]:
            best = (f1, C, mlflow.active_run().info.run_id)

best_f1, best_C, run_id = best
print(f"best: C={best_C} f1={best_f1:.3f}")

# Promotion gate: only register to the model registry if it clears the bar.
if best_f1 >= PROMOTION_F1:
    mlflow.register_model(f"runs:/{run_id}/model", "demo-classifier")
    print("PROMOTED to registry (staging)")     # next: gated CI/CD -> canary -> prod
else:
    raise SystemExit(f"REJECTED: f1 {best_f1:.3f} < gate {PROMOTION_F1}")
```

The same loop applies to LLM systems — swap the sklearn model for a prompt/RAG
config, and the `f1` gate for an **eval suite** (faithfulness/accuracy via
Ragas/DeepEval). The discipline is identical: track → gate → register → promote →
monitor → roll back, with the prompt/config as the versioned artifact.

## 6. How to learn it

**Beginner (0–3 months).** Track experiments with MLflow or W&B; version data
with DVC; register a model. *Milestone:* a reproducible experiment you can
recreate from the tracked run.

**Intermediate / job-ready (3–9 months).** Build a CI/CD pipeline with an **eval
gate**; deploy with a serving framework; add latency/cost/quality monitoring and
a drift check; do a canary rollout with rollback. *Milestone:* an LLM/ML service
with versioning, gated deploys, and dashboards.

**Expert (9+ months).** Full lifecycle automation; drift-triggered retraining/
re-prompting; SLOs and alerting; cost optimization; multi-model/multi-prompt
governance. *Milestone:* you own the ops platform a team's models/prompts flow
through.

## 7. Interview signals

- **"How do you version and roll back an LLM feature?"** Version the prompt/RAG
  config/model as artifacts in a registry; gate promotion on evals; canary/blue-
  green deploy; automatic rollback on metric regression.
- **"How is LLMOps different from MLOps?"** LLMOps centers on prompts, evals, and
  serving cost (rarely retraining a base model); MLOps centers on data drift →
  retrain. Versioning prompts and eval-gating replace retraining pipelines.
- **"How do you detect a silent quality regression?"** Offline eval drift in CI +
  online metrics/user feedback + input/output drift detection + token/cost
  anomalies — with alerts on each.
- **"What goes in your monitoring?"** Ops (latency, error rate, throughput,
  token/cost) + quality (eval scores, drift, feedback) tied to SLOs.
- **"How do you keep experiments reproducible?"** Track params/data version/
  metrics/artifact; pin environments; version code, data, model, and prompt
  together.
