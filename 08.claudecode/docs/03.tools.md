## The tool set

Claude Code's leverage comes from a small, sharp set of built-in tools the model
can call. Each is advertised to the model with a **name**, a **description**, and
a **JSON-Schema `input_schema`**; the model emits a `tool_use` block with the
tool name and an arguments object, and the harness runs it.

| Tool | What it does | When the model uses it |
|---|---|---|
| **Read** | Read a file (text, and in the real product images/PDFs/notebooks). | To inspect code before editing; to read config, logs, data. |
| **Write** | Create or overwrite a file. | To create new files. |
| **Edit** | Exact string replacement in a file. | To make surgical changes without rewriting whole files. |
| **Bash** | Run a shell command (with a timeout). | To run tests, builds, git, package managers, arbitrary tooling. |
| **Glob** | Find files by glob pattern (`**/*.ts`). | To locate files by name/structure. |
| **Grep** | Search file contents by regex. | To find symbols, usages, strings across the codebase. |
| **Agent (Task)** | Spawn a [sub-agent](06.skills-subagents.md) with its own context window and tools. | To offload exploration/research that would flood the main context. |
| **TodoWrite** | Maintain a structured task list. | To plan and track multi-step work so progress is visible and ordered. |

The real product also exposes **web fetch/search**, a **text editor** tool, and
others; the mini-agent implements the file/shell/search core plus an MCP-tool
adapter ([`05.mcp.md`](05.mcp.md)).

## Schemas

A tool definition is exactly the shape the Messages API expects in `tools[]`.
The mini-agent's `edit_file`:

```jsonc
{
  "name": "edit_file",
  "description": "Replace an exact substring in a file. `old` must occur exactly once.",
  "parameters": {                         // == the API's input_schema
    "type": "object",
    "properties": {
      "path": {"type": "string"},
      "old":  {"type": "string", "description": "Exact text to replace; must be unique."},
      "new":  {"type": "string", "description": "Replacement text."}
    },
    "required": ["path", "old", "new"]
  }
}
```

The description is *load-bearing*: the model relies on it to decide **when** to
call the tool, so good descriptions state the trigger condition, not just the
mechanics. On recent models that reach for tools conservatively, a prescriptive
"call this when…" description measurably improves the call rate.

## Why dedicated tools instead of just Bash?

Bash alone is maximally expressive — the model can do almost anything with a
shell. But for the *harness*, every action arrives as an opaque command string,
the same shape whether it's a harmless `grep` or a destructive `rm -rf`.
Promoting an action to a **dedicated tool** gives the harness a typed, named
hook it can **gate, render, audit, and parallelize**. Concretely:

* **Security & reversibility.** A `write_file` / `edit` tool is easy to gate or
  confirm; `bash -c "curl -X POST ..."` is not.
* **Staleness / integrity checks.** A dedicated **Edit** tool can require that
  the target text appears *exactly once*, refusing ambiguous edits that could
  corrupt a file. The mini-agent enforces this:

  ```python
  count = text.count(old)
  if count == 0:  return error("`old` not found")
  if count > 1:   return error(f"`old` occurs {count} times; must be unique")
  ```

  Bash can't enforce that invariant.
* **Custom rendering.** Some tools deserve special UI (a diff view for edits, a
  modal for a question). A typed tool call carries the structure to render.
* **Scheduling.** Read-only tools (`glob`, `grep`, `read_file`, `list_dir`) can
  be marked **parallel-safe**; the harness runs them concurrently. It cannot
  safely parallelize opaque bash commands (one might be `git push`).

**Rule of thumb:** start with Bash for breadth; promote an action to a dedicated
tool when you need to gate, render, audit, or parallelize it.

## Parallel tool calls

The model may request **several tool calls in one turn**. The harness executes
them and returns all results together. The mini-agent partitions a turn's calls
into read-only (run concurrently on a thread pool / threads) and mutating (run
serially), preserving order, then returns one `tool_result` per call:

```python
parallel, serial = partition(calls, by=is_read_only)
# read-only calls run concurrently; mutating ones one at a time
```

This is the same idea as Claude Code marking read-only tools parallel-safe so a
batch of `grep`/`read` calls fans out, while writes are serialized.

## Sandboxing

Every file/path argument in the mini-agent resolves **relative to a workspace
root** and is rejected if it escapes via `..`. That's a minimal version of the
sandboxing real agents apply so the model can't read or write outside the
project. Combined with the permission gate ([`04.permissions.md`](04.permissions.md)),
this bounds what a tool call can touch regardless of what the model asks for.
