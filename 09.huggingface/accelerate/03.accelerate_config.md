## 1. What is `accelerate config`?

`accelerate config` is an interactive command-line wizard that asks you about your hardware setup and writes a YAML file (`~/.cache/huggingface/accelerate/default_config.yaml` by default). When you later run `accelerate launch script.py`, Accelerate reads that YAML and bootstraps the right distributed process group, dtype casting, and optimizer plugin (DeepSpeed / FSDP) without any code changes.

```
$ accelerate config
```

You can also specify a custom config path:
```
$ accelerate config --config_file my_config.yaml
$ accelerate launch --config_file my_config.yaml train.py
```

## 2. The Interactive Q&A Walkthrough

Below is the full sequence of questions and how to answer for common setups.

### Question 1 — Compute environment
```
In which compute environment are you running?
 > This machine
   Amazon SageMaker
```
Choose **This machine** for local/cloud VM training.

### Question 2 — Machine type
```
Which type of machine are you using?
 > No distributed training          (single CPU/GPU)
   multi-CPU
   multi-GPU
   TPU
```

### Question 3 — Number of machines / processes
```
How many different machines will you use (use more than 1 for multi-node)?
  > 1
```
```
How many processes in total will you use?
  > 4           (= number of GPUs you have)
```

### Question 4 — Mixed precision
```
Do you wish to use FP16 or BF16 (mixed precision)?
 > no
   fp16
   bf16
```
- `bf16` is preferred on Ampere (A100, RTX 30xx) and newer GPUs.
- `fp16` works on older GPUs (Volta/Turing) but requires GradScaler.
- `no` = full fp32 (safest, slowest).

### Question 5 — DeepSpeed / FSDP / Megatron (optional)
```
Do you want to use DeepSpeed?  [yes/NO]
Do you want to use FullyShardedDataParallel?  [yes/NO]
Do you want to use Megatron-LM?  [yes/NO]
```

## 3. Generated YAML — Field-by-Field

### Single GPU (minimal)
```yaml
# ~/.cache/huggingface/accelerate/default_config.yaml
compute_environment: LOCAL_MACHINE
distributed_type: 'NO'           # single process
mixed_precision: 'no'
num_machines: 1
num_processes: 1
use_cpu: false
```

### Multi-GPU DDP (4 GPUs on one node)
```yaml
compute_environment: LOCAL_MACHINE
distributed_type: MULTI_GPU      # wraps model in DistributedDataParallel
mixed_precision: bf16
num_machines: 1
num_processes: 4                 # one process per GPU
machine_rank: 0
main_process_ip: null            # only needed for multi-node
main_process_port: 29500
main_training_function: main     # function to call (if using notebook_launcher)
same_network: true
use_cpu: false
rdzv_backend: static
```

**Field reference:**

| Field | Description |
|---|---|
| `distributed_type` | `NO`, `MULTI_GPU`, `MULTI_CPU`, `TPU`, `DEEPSPEED`, `FSDP`, `MEGATRON_LM` |
| `mixed_precision` | `no`, `fp16`, `bf16` |
| `num_processes` | Total processes = num_gpus × num_machines |
| `num_machines` | Number of nodes (machines) in the cluster |
| `machine_rank` | Index of THIS machine (0 = master) |
| `main_process_ip` | IP of rank-0 machine (multi-node only) |
| `main_process_port` | Port for the process group rendezvous (default 29500) |
| `rdzv_backend` | `static` (fixed topology) or `c10d` (etcd/dynamic) |
| `use_cpu` | Force CPU even if GPU is present |

### DeepSpeed ZeRO-2
```yaml
compute_environment: LOCAL_MACHINE
distributed_type: DEEPSPEED
deepspeed_config:
  deepspeed_multinode_launcher: standard
  gradient_accumulation_steps: 4
  gradient_clipping: 1.0
  offload_optimizer_device: 'none'   # 'cpu' for ZeRO-Offload
  offload_param_device: 'none'
  zero3_init_flag: false
  zero3_save_16bit_model: false
  zero_stage: 2                      # 1, 2, or 3
mixed_precision: bf16
num_machines: 1
num_processes: 4
use_cpu: false
```

**ZeRO stages:**
- Stage 1: Partition optimizer states across GPUs
- Stage 2: + partition gradients
- Stage 3: + partition model parameters (enables huge models)
- ZeRO-Offload: Stage 2/3 + optimizer/param on CPU

### FSDP (Fully-Sharded Data Parallel)
```yaml
compute_environment: LOCAL_MACHINE
distributed_type: FSDP
fsdp_config:
  fsdp_auto_wrap_policy: TRANSFORMER_BASED_WRAP
  fsdp_backward_prefetch_policy: BACKWARD_PRE
  fsdp_forward_prefetch: false
  fsdp_offload_params: false         # true = CPU offload
  fsdp_sharding_strategy: 1         # 1=FULL_SHARD, 2=SHARD_GRAD_OP, 3=NO_SHARD
  fsdp_state_dict_type: FULL_STATE_DICT
  fsdp_sync_module_states: true
  fsdp_transformer_layer_cls_to_wrap: GPT2Block   # wrap unit
  fsdp_use_orig_params: true
mixed_precision: bf16
num_machines: 1
num_processes: 4
```

## 4. `accelerate launch` — Running Your Script

```bash
# Use default config
accelerate launch train.py --epochs 3 --lr 1e-4

# Use custom config
accelerate launch --config_file configs/deepspeed_z2.yaml train.py

# Override config at launch time (no need to rerun accelerate config)
accelerate launch \
    --num_processes 8 \
    --mixed_precision bf16 \
    train.py

# Multi-node (2 machines, 4 GPUs each = 8 total processes)
# On machine 0 (master):
accelerate launch \
    --num_machines 2 --machine_rank 0 \
    --main_process_ip 10.0.0.1 --main_process_port 29500 \
    --num_processes 8 \
    train.py
# On machine 1:
accelerate launch \
    --num_machines 2 --machine_rank 1 \
    --main_process_ip 10.0.0.1 --main_process_port 29500 \
    --num_processes 8 \
    train.py
```

### What `accelerate launch` does under the hood
1. Reads config YAML (or CLI flags)
2. For MULTI_GPU: calls `torch.distributed.run` (formerly `torchrun`) with the right `--nproc_per_node`, `--nnodes`, `--rdzv_*` arguments
3. For DeepSpeed: sets up `deepspeed` launcher
4. For TPU: calls `torch_xla.distributed.xla_spawn`
5. Sets environment variables (`LOCAL_RANK`, `RANK`, `WORLD_SIZE`, `MASTER_ADDR`, `MASTER_PORT`)
6. Calls your script; each process initializes `Accelerator()` which reads these env vars

## 6. notebook_launcher

For Jupyter/Colab environments where you can't run shell commands:

```python
from accelerate import notebook_launcher

def training_function():
    from accelerate import Accelerator
    accelerator = Accelerator()
    # ... your training loop ...

# Launch on 2 GPUs from inside a notebook
notebook_launcher(training_function, args=(), num_processes=2)
```

`notebook_launcher` uses `multiprocessing.spawn` internally — avoids the
fork-safety issues of notebooks. Docs:
https://huggingface.co/docs/accelerate/basic_tutorials/notebook

## 7. Accelerate vs raw torch DDP vs Trainer

| Feature | Raw `torch.distributed` | `Accelerate` | HF `Trainer` |
|---|---|---|---|
| Boilerplate | High (manual init_process_group, device mapping) | Low (just `prepare()`) | Minimal |
| Custom training loop | Full control | Full control | Limited (callbacks only) |
| DeepSpeed / FSDP | Manual config | YAML-driven | Some support |
| Mixed precision | Manual `GradScaler` | `mixed_precision=` | `fp16=True` arg |
| Multi-node | Manual | `accelerate launch` flags | Via Trainer args |
| Gradient accum | Manual `no_sync()` | `accumulate()` context | `gradient_accumulation_steps=` |
| Best for | Expert, full control | Research loops | Standard fine-tuning |

**Rule of thumb**: Use `Trainer` when the HF defaults fit; use `Accelerate`
when you need a custom loop with minimal distributed boilerplate.

## 8. Common Pitfalls

1. **`prepare()` order matters** — call it before any `.to(device)` calls.  
2. **`accelerator.backward()` not `loss.backward()`** — skipping this breaks fp16 scaling.  
3. **`accelerator.print()` not `print()`** — in DDP, `print()` fires on all ranks.  
4. **Save only from rank 0** — `if accelerator.is_main_process: accelerator.save_state(...)`.  
5. **Dataloader drop_last** — in DDP without `drop_last=True`, the last partial batch can cause hangs if ranks get different batch counts.  
6. **gradient_accumulation_steps in BOTH Accelerator() and your loop** — they must agree; mismatch causes incorrect effective batch size.
