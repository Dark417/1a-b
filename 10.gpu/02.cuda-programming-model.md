## 1. What a kernel is

A **kernel** is a function that runs *once per thread*, in parallel, on the
device. In CUDA C++ it's marked `__global__`; in Numba it's `@cuda.jit`; in
Triton it's `@triton.jit` (operating per *block* rather than per thread). You do
**not** write the loop over elements — you write the body for *one* work item and
launch a grid of millions of them.

```python
# Numba CUDA — one thread adds one element (see 03.numba-cuda/01.vector_add.py)
from numba import cuda

@cuda.jit
def add(a, b, c, n):
    i = cuda.grid(1)              # this thread's global index
    if i < n:                    # boundary guard
        c[i] = a[i] + b[i]
```

The kernel returns nothing; it writes results into device arrays passed as
arguments. The mental shift from CPU code: **"what does thread `i` compute?"**
instead of **"loop over all i"**.

## 2. Launch configuration — choosing the grid

You launch a kernel with an **execution configuration**: how many blocks, and how
many threads per block.

```python
threads_per_block = 128
blocks_per_grid = (n + threads_per_block - 1) // threads_per_block   # ceil-div
add[blocks_per_grid, threads_per_block](d_a, d_b, d_c, n)            # Numba syntax
```

In CUDA C++ the syntax is `add<<<blocks, threads>>>(...)`. The **ceil-division**
ensures `blocks × threads ≥ n` so every element is covered; the price is that the
*last* block has some threads with `i ≥ n` — hence the **boundary guard**
`if i < n`. Forgetting it is the #1 beginner bug (out-of-bounds writes / garbage).

Choosing the config:

- **Threads per block** — a multiple of the warp size (32); 128 or 256 are good
  defaults. Too small wastes warp slots; too large can hurt occupancy
  (registers/shared memory per block). Max is 1024.
- **Blocks per grid** — usually enough to cover the data *and* to give every SM
  several blocks (for latency hiding). It's fine — often good — to launch far
  more blocks than SMs; the runtime schedules them.
- **Dimensions** — 1-D for vectors, 2-D for matrices/images, 3-D for volumes.
  Purely a convenience; `dim3` for both grid and block.

```python
# 2-D launch for a matrix (see 03.numba-cuda/02.matmul_naive.py)
block = (16, 16)                 # 256 threads, a 16x16 tile
grid  = ((N + 15)//16, (M + 15)//16)   # (x=cols, y=rows) covering all of C
```

A robust pattern for arbitrary-size data is the **grid-stride loop**: launch a
fixed grid and have each thread stride through the array, so the same kernel
handles any `n` and any GPU size:

```python
@cuda.jit
def add_strided(a, b, c, n):
    start = cuda.grid(1)
    stride = cuda.gridsize(1)          # total threads = blockDim*gridDim
    for i in range(start, n, stride):
        c[i] = a[i] + b[i]
```

## 3. Indexing — from coordinates to a global index

Every thread knows four built-in coordinates per dimension:

| Built-in | Meaning |
|---|---|
| `threadIdx.{x,y,z}` | this thread's index *within its block* |
| `blockIdx.{x,y,z}` | this block's index *within the grid* |
| `blockDim.{x,y,z}` | threads per block (block shape) |
| `gridDim.{x,y,z}` | blocks per grid (grid shape) |

The canonical 1-D global index:

```
i = blockIdx.x * blockDim.x + threadIdx.x          # == cuda.grid(1)
```

2-D (rows/cols of a matrix):

```
row = blockIdx.y * blockDim.y + threadIdx.y        # == cuda.grid(2)[0]
col = blockIdx.x * blockDim.x + threadIdx.x        # == cuda.grid(2)[1]
```

Numba provides `cuda.grid(ndim)` and `cuda.gridsize(ndim)` as shorthand. (Note:
in the CUDA *simulator* used on this CPU-only machine, `cuda.grid(2)` has a bug in
boundary blocks, so `02.matmul_naive.py` spells out the explicit form — which is
exactly what `cuda.grid` expands to. See `03.numba-cuda/README.md`.)

**Row- vs column-major matters for coalescing.** Map `threadIdx.x` (the lane that
varies fastest within a warp) to the *innermost, contiguous* dimension so the
warp's 32 accesses are adjacent in memory — coalesced. Mapping it to the strided
dimension scatters the accesses. (Section 06 develops this.)

## 4. The memory model — scopes and lifetimes

CUDA's variables have a **scope** that mirrors the hierarchy from section 01:

| Declaration | Lives in | Scope | Lifetime |
|---|---|---|---|
| local var (`acc`) | registers (maybe spill→local/global) | one thread | thread |
| `__shared__` array | shared memory (on-SM SRAM) | one block | block |
| `__device__` global / kernel arg arrays | global memory (DRAM) | whole grid | application |
| `__constant__` | constant memory (cached, read-only) | whole grid | application |

Key rules:

- **Threads communicate within a block via shared memory** — declare a
  `cuda.shared.array`, have threads cooperatively fill it, synchronize, then read
  each other's contributions. This is the basis of tiling and reductions.
- **Blocks do not communicate** during a launch (except via slow global-memory
  atomics, or by ending the kernel). If block-wide cooperation is needed, do it
  across *two* kernel launches, or with atomics, or (advanced) cooperative-group
  grid sync.
- **Global memory persists across kernel launches** — you upload inputs once, run
  several kernels that read/write global arrays, and download results at the end.
  Minimizing host↔device traffic is a top-level performance concern.

**Atomics.** `atomicAdd`, `atomicMax`, `atomicCAS`, etc. perform a
read-modify-write that's indivisible across threads — essential when many threads
update the same location (e.g. histogramming, or accumulating reduction partials
into one slot). They serialize contending threads, so use them sparingly.

## 5. Synchronization

Three levels, matching the hierarchy:

- **Block barrier** — `__syncthreads()` (Numba: `cuda.syncthreads()`). Every
  thread in the block waits until *all* reach the barrier. Used around shared
  memory: fill the tile → `syncthreads()` → use the tile → `syncthreads()` before
  overwriting it. **Must be reached by all threads** in the block — putting it
  inside a divergent `if` that not all threads enter is undefined behavior and a
  classic deadlock/garbage bug.
- **Warp-level** — threads in a warp run in lockstep (SIMT), and modern CUDA
  exposes explicit **warp primitives**: `__shfl_sync` (read another lane's
  register), `__ballot_sync`, `__reduce_add_sync`, etc. These do intra-warp
  communication with *no shared memory and no barrier* — the fastest reductions
  and scans use them (section 06).
- **Device / grid level** — by default, a kernel launch is asynchronous w.r.t.
  the host, and ordering between launches on the same **stream** is guaranteed.
  `cudaDeviceSynchronize()` (host) waits for the device to finish.
  **Streams** let independent work overlap; **events** time and order across
  streams. (See `05.pytorch-performance.md` for streams/CUDA graphs.)

## 6. The host/device workflow

A CUDA program is a *host* (CPU) program that orchestrates *device* (GPU) work.
The canonical lifecycle (visible in every `03.numba-cuda` file's host wrapper):

```
   HOST (CPU)                              DEVICE (GPU)
   ──────────                              ────────────
1. allocate & fill input arrays (NumPy)
2. cudaMalloc / cuda.to_device   ───────►  allocate device memory, copy H2D
3. configure grid/block
4. launch kernel<<<grid,block>>> ───────►  thousands of threads execute
   (asynchronous — returns immediately)
5. (optionally launch more kernels;
    they queue on the stream in order)
6. cuda.copy_to_host  ◄───────────────────  copy results D2H (this syncs)
7. use results on the CPU
```

```python
# the pattern, in Numba (03.numba-cuda/01.vector_add.py)
d_a = cuda.to_device(a)                    # 2. H2D copy
d_b = cuda.to_device(b)
d_c = cuda.device_array_like(a)            #    allocate output on device
add[blocks, threads](d_a, d_b, d_c, n)     # 4. launch (async)
result = d_c.copy_to_host()                # 6. D2H copy (synchronizes)
```

Performance corollaries:

- **PCIe transfers are expensive.** Keep data resident on the device across many
  kernels; don't ping-pong to the host. Overlap unavoidable copies with compute
  using **pinned memory** + `non_blocking=True` on separate **streams**
  (section 05).
- **Launches are async.** Timing a kernel requires a synchronize (or CUDA events)
  or you'll measure only the launch overhead, not the work.
- **Kernel launch has overhead** (~µs). For many tiny kernels, *fusing* them into
  one (Triton, `torch.compile`) or capturing them in a **CUDA graph** removes
  per-launch cost.

## 7. A complete worked example (read alongside the code)

`03.numba-cuda/03.matmul_tiled.py` exercises *every* idea above:

1. **Kernel** computing one C-tile per block.
2. **2-D launch config** sized to cover an arbitrary `(M,N)`.
3. **Indexing** with explicit `blockIdx*TILE + threadIdx`.
4. **Shared memory** (`cuda.shared.array`) staging A/B tiles.
5. **Synchronization** (`cuda.syncthreads()`) around tile load and use.
6. **Boundary guards** for ragged M/K/N.
7. **Host workflow** wrapper doing H2D → launch → D2H.

It runs on this CPU via `NUMBA_ENABLE_CUDASIM=1` and checks against `a @ b`.

## 8. Pitfalls checklist

- [ ] Missing **boundary guard** → out-of-bounds writes on the tail block.
- [ ] `syncthreads()` inside divergent control flow → deadlock / stale reads.
- [ ] Mapping `threadIdx.x` to the strided dimension → uncoalesced, slow.
- [ ] Forgetting to synchronize before reading shared memory another thread wrote.
- [ ] Timing without `cudaDeviceSynchronize` → measuring launch, not compute.
- [ ] Excess registers / shared memory per block → low occupancy.
- [ ] Host↔device copies in the inner loop → PCIe-bound.
- [ ] Data races on global memory without atomics.
