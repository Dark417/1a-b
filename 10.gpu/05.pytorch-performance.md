# 05 · PyTorch Performance — profiling, AMP, fusion, compile, graphs, memory

> Most ML engineers never write a CUDA kernel; they make PyTorch go fast. This is
> the toolbox: **measure first** (profiler), then apply mixed precision, operator
> fusion, `torch.compile`, CUDA graphs, the right memory format, and overlapped
> copies. Runnable CPU demos of every API are in `05.profile_demo.py` — run it
> with `python 05.profile_demo.py`. The *speedups* need a GPU, but the *APIs and
> concepts* are demonstrated and verified on CPU.

---

## 0. The golden rule: profile before you optimize

You cannot optimize what you haven't measured. The most common mistake is tuning
a kernel that isn't the bottleneck, or fighting compute when you're memory-bound.
Always: **profile → find the dominant cost → fix that → re-profile.**

---

## 1. `torch.profiler` — where does the time go?

The built-in profiler records every operator (and, on GPU, every CUDA kernel and
the CPU↔GPU gaps), with timings, shapes, and a trace you can open in Chrome /
TensorBoard / Perfetto.

```python
from torch.profiler import profile, record_function, ProfilerActivity

with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             record_shapes=True, profile_memory=True) as prof:
    with record_function("forward"):      # custom labels for your code regions
        out = model(x)
    out.sum().backward()

print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))
prof.export_chrome_trace("trace.json")    # open in chrome://tracing / Perfetto
```

What to look for:
- **Self CPU/CUDA time per op** — the actual hot ops (often matmul, attention).
- **Gaps between kernels** — launch overhead or CPU-bound dispatch (→ fuse /
  compile / CUDA graphs).
- **`aten::to` / `cudaMemcpy`** showing up — you're moving data H2D/D2H in the
  hot loop (→ keep tensors on device, pin + async).
- **Memory** (`profile_memory=True`) — peak allocations, fragmentation.

Use a **schedule** (`wait`/`warmup`/`active`) to skip warmup steps and capture a
steady-state window in long training runs.
`demo_profiler()` in `05.profile_demo.py` runs a real profile on CPU and prints
the top ops by self time.

The classic GPU diagnosis: if **GPU utilization is low** and the profiler shows
gaps, you're **launch-bound / input-bound** (fix with compile, graphs, bigger
batches, faster data loading), not compute-bound.

## 2. AMP / autocast — mixed precision

Modern GPUs run fp16/bf16 matmuls on **Tensor Cores** several times faster than
fp32, and halve memory traffic and footprint. **Automatic Mixed Precision** runs
eligible ops (matmul, conv) in low precision while keeping accuracy-sensitive ops
(reductions, softmax, loss) and a master weight copy in fp32.

```python
scaler = torch.amp.GradScaler("cuda")          # only needed for fp16, not bf16
for x, y in loader:
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        out  = model(x)
        loss = loss_fn(out, y)
    scaler.scale(loss).backward()              # scale ↑ to avoid grad underflow
    scaler.step(optimizer)                     # unscales, then steps
    scaler.update()
    optimizer.zero_grad()
```

- **bf16** (Ampere+) has fp32's exponent range → no loss scaling needed, very
  robust; preferred for training when available.
- **fp16** has more mantissa bits but a tiny range → needs **`GradScaler`** to
  keep small gradients from flushing to zero.
- The `GradScaler.is_enabled()` flag is `False` on CPU; `demo_autocast()` shows
  the `torch.autocast(device_type="cpu", dtype=torch.bfloat16)` path actually
  changing a matmul's output dtype to bf16.

## 3. Operator fusion

Pointwise chains (`x.sin() * 2 + x.cos()**2`, biases+activations, layernorm) are
**memory-bound**: each op reads and writes the whole tensor to global memory. The
arithmetic is trivial; the DRAM round-trips dominate. **Fusion** combines the
chain into a *single* kernel that reads the input once, does all the math in
registers, and writes once — cutting memory traffic by the chain length.

You rarely fuse by hand anymore; `torch.compile` (below), Triton, and the JIT
fusers do it. The fused softmax in `04.triton/02.fused_softmax.py` is a worked
example: 5 PyTorch kernels → 1.

## 4. `torch.compile` — the one-line accelerator

`torch.compile(model)` traces your model (TorchDynamo), optimizes the graph
(decompositions, fusion), and generates fused **Triton** kernels on GPU
(TorchInductor). Often a 1.3–2×+ speedup for one line, no model changes.

```python
model = torch.compile(model)                 # default
model = torch.compile(model, mode="max-autotune")   # autotune kernels, slower compile
model = torch.compile(model, fullgraph=True)        # error on graph breaks (faster)
```

Knobs and gotchas:
- **Modes**: `default`, `reduce-overhead` (uses CUDA graphs under the hood),
  `max-autotune` (searches kernel configs).
- **Graph breaks** — dynamic Python (data-dependent `if`, printing, `.item()`)
  splits the graph and loses fusion across the break. `fullgraph=True` surfaces
  them.
- **Recompilation** — changing input shapes/dtypes triggers recompiles; use
  `dynamic=True` or pad to fixed shapes if shapes vary a lot.
- First call is slow (compilation); steady-state is fast.
- `demo_compile()` compiles a pointwise chain on CPU and verifies the result is
  bit-for-bit (within tolerance) identical to eager — proving fusion preserves
  semantics.

## 5. CUDA graphs — kill launch overhead

Each kernel launch costs a few microseconds of CPU work. For models with **many
small kernels** (small batch, lots of layers), the CPU can't issue launches fast
enough and the GPU starves — *launch-bound*. A **CUDA graph** records a sequence
of launches once and replays the whole thing with a single call, removing
per-kernel CPU overhead and inter-kernel gaps.

```python
# record once
g = torch.cuda.CUDAGraph()
static_in = torch.randn(N, device="cuda")
with torch.cuda.graph(g):
    static_out = model(static_in)            # captured, not run
# replay many times (fixed shapes; copy new data into static_in first)
static_in.copy_(new_input)
g.replay()
```

Requirements: **static shapes** and **fixed memory addresses** (you reuse the
same input/output tensors). `torch.compile(mode="reduce-overhead")` applies CUDA
graphs automatically when it's safe. Huge wins for inference and small-batch
training; irrelevant when already compute-bound.

## 6. Memory format — `channels_last` (NHWC)

cuDNN and Tensor Cores prefer **NHWC** ("channels last") layout for convolutions;
the default PyTorch layout is **NCHW**. Requesting `channels_last` avoids implicit
layout transposes inside cuDNN and unlocks faster kernels — often a free speedup
for CNNs in AMP.

```python
model = model.to(memory_format=torch.channels_last)
x     = x.to(memory_format=torch.channels_last)
y     = model(x)                             # stays channels_last
```

`demo_memory_format()` shows the layout flag propagating through a `Conv2d` on
CPU. (No speed change on CPU, but the API and the `is_contiguous(memory_format=…)`
check are real.)

## 7. Pinned memory + async copies — overlap H2D with compute

Pageable host memory must be staged through a pinned buffer before a DMA to the
GPU, and the copy is synchronous. **Page-locked (pinned)** memory can be DMA'd
directly and, with `non_blocking=True` on a side **stream**, the copy **overlaps**
with kernel compute — hiding the PCIe transfer.

```python
pinned = cpu_tensor.pin_memory()                       # page-locked
gpu    = pinned.to("cuda", non_blocking=True)          # async DMA
# in DataLoader:
DataLoader(ds, pin_memory=True, num_workers=4)         # the common path
```

`demo_pinned()` calls `pin_memory()` on CPU (no GPU to copy to, so the async copy
is a no-op) and prints the exact production pattern. Combine with **multiple
CUDA streams** so copy and compute run concurrently. (Note: bf16/fp32 issues
aside, prefetching the *next* batch while the current one trains is the highest-
ROI version of this.)

## 8. A practical optimization order

1. **Profile.** Find the bottleneck (compute vs memory vs launch vs data).
2. **AMP (bf16)** — usually the biggest single win on modern GPUs.
3. **`torch.compile`** — fusion + Inductor Triton kernels, one line.
4. **Fix data loading** — `pin_memory`, `num_workers`, prefetch; don't starve the
   GPU.
5. **`channels_last`** for CNNs.
6. **CUDA graphs / `reduce-overhead`** if launch-bound (many small kernels).
7. **Bigger batch / gradient accumulation** to raise arithmetic intensity.
8. Only then consider **custom Triton/CUDA kernels** for a proven hot op.
