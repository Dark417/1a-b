# 08 · LLM Inference Optimization — the engineering view

> Training optimizations (sections 05–07) maximize throughput on big batches.
> **Inference** has a different cost structure: autoregressive decoding is
> **memory-bandwidth-bound** and **latency-sensitive**, with a growing **KV
> cache** dominating memory. This file is the serving engineer's toolbox: KV
> cache, paged attention, continuous batching, quantization, speculative
> decoding, and FlashAttention — what each does, why it works, and where it bites.
> These are the techniques inside vLLM, TGI, TensorRT-LLM, SGLang, and llama.cpp.

---

## 1. Why LLM inference is its own problem

Decoding one token at a time has two phases:

- **Prefill** — process the whole prompt in parallel. Compute-bound (big
  matmuls); uses the GPU well.
- **Decode** — generate tokens one at a time, each depending on the last. **Each
  step is a tiny matmul (batch of 1 token) against the full weights** ⇒
  **memory-bandwidth-bound**: you re-read all the weights from HBM to produce a
  single token. The GPU's FLOPs sit mostly idle; the bottleneck is moving weights
  and the KV cache.

Consequences that drive everything below:
- **Batch more requests together** to amortize the weight reads (continuous
  batching).
- **Shrink the bytes you move** (quantization).
- **Avoid recomputing the past** (KV cache) — but then manage its memory (paged
  attention).
- **Produce more than one token per forward pass** (speculative decoding).

Two metrics to optimize: **TTFT** (time-to-first-token, dominated by prefill) and
**TPOT/ITL** (time-per-output-token, dominated by decode bandwidth).

---

## 2. KV cache — don't recompute the past

In self-attention, token *t* attends to the keys/values of all tokens `≤ t`.
Without caching, generating token *t* recomputes K and V for the entire prefix —
O(t²) total, quadratic waste. The **KV cache** stores each layer's K and V for
every past token, so each new step computes K/V for **only the new token** and
attends against the cached rest. Decode becomes O(t) per step.

Cost: memory. KV size = `2 (K and V) × layers × seq_len × n_kv_heads × head_dim ×
batch × bytes`. For long context and many concurrent requests this **dwarfs the
weights** and is the binding constraint on how many requests you can batch.
Mitigations:
- **GQA/MQA** (grouped/multi-query attention) — share K/V across query heads,
  shrinking the cache several-fold (used by Llama-2/3, Mistral). (See
  `05.transformers/llm-architectures` in this repo.)
- **KV-cache quantization** — store K/V in int8/fp8.
- **Paged attention** (next) — eliminate the *fragmentation* waste.

---

## 3. Paged attention — virtual memory for the KV cache

Naively, each request reserves a **contiguous** KV buffer sized for its
*maximum* possible length. Most of it is unused (requests finish early, lengths
vary) ⇒ massive **internal fragmentation**; you can serve far fewer requests than
memory should allow. **PagedAttention** (vLLM) borrows OS virtual memory: split
the KV cache into fixed-size **blocks (pages)**, keep a per-request **block table**
mapping logical positions → physical blocks, and allocate blocks **on demand**.

Wins:
- Near-zero fragmentation ⇒ much higher batch sizes / throughput (vLLM reported
  ~2–4× over prior serving systems).
- **Copy-on-write block sharing** — multiple sequences sharing a prompt (beam
  search, parallel samples, a common system prefix) **share** physical KV blocks
  until they diverge (**prefix caching**).

This is the central innovation that made high-throughput open LLM serving
practical; it's why vLLM became the default engine.

---

## 4. Continuous (in-flight) batching

Static batching waits to fill a batch, runs it to completion, then starts the
next — but generations finish at *different* lengths, so fast requests wait idle
for slow ones, and new arrivals wait for the whole batch. **Continuous batching**
(a.k.a. iteration-level / in-flight batching) schedules at the **token step**: as
soon as a sequence emits its EOS, its slot is freed and a **waiting request is
admitted mid-flight**. The batch composition changes every iteration, keeping the
GPU saturated.

Combined with paged attention (dynamic KV allocation makes admitting/evicting
requests cheap), this is the throughput backbone of vLLM, TGI, and TensorRT-LLM.
Schedulers add **chunked prefill** (interleave long prompts' prefill with ongoing
decodes so one big prompt doesn't stall everyone) and priority/fairness policies.

## 5. Quantization — move and store fewer bits

Inference is bandwidth-bound, so **storing weights (and KV) in fewer bits** both
fits bigger models and speeds decode (less to read from HBM). Precision tiers and
methods:

- **INT8** — e.g. **LLM.int8()** (mixed int8 with fp16 outliers),
  **SmoothQuant** (migrate activation outliers into weights so both quantize
  cleanly). ~2× memory cut, usually negligible quality loss.
- **INT4 / 4-bit** — the popular regime for local/consumer inference:
  - **GPTQ** — one-shot, second-order (Hessian-based) post-training quantization
    of weights to 3–4 bits.
  - **AWQ** (Activation-aware Weight Quantization) — protect the
    salient weight channels (those multiplying large activations); strong 4-bit
    quality, fast kernels.
  - **bitsandbytes NF4** — the QLoRA 4-bit format for fitting big models for
    fine-tuning/inference.
- **GGUF** — the **llama.cpp** file format + quantization scheme (Q4_K_M, Q5_K_M,
  Q8_0, …) with **k-quants** that mix bit-widths per block for a good
  quality/size trade-off; the standard for CPU/edge and mixed CPU-GPU offload.
- **FP8** (Hopper/Ada) — hardware-native 8-bit float for both training and
  inference; better dynamic range than int8.

Trade-off axis: fewer bits → smaller/faster but more accuracy risk; **weight-only**
quant helps the bandwidth-bound decode most, while **weight+activation** quant is
needed to actually use faster low-precision *compute*. (Deeper treatment +
runnable demo planned in `05.transformers/llm-architectures/quantization.py`.)

## 6. Speculative decoding — more tokens per forward pass

Decode is bandwidth-bound, so a single large-model forward pass is "wasted" on one
token. **Speculative decoding** uses a cheap **draft** model to propose *several*
tokens, then the big **target** model **verifies them all in one parallel forward
pass**, accepting the longest correct prefix (a rejection-sampling scheme keeps
the output distribution **exactly** that of the target model — no quality loss).
If the draft is right *k* tokens in a row, you got `k` tokens for ~one big-model
pass ⇒ 2–3× latency reduction in practice.

Variants:
- **Draft model** — a small same-family model (the original Leviathan et al. /
  Chen et al. method).
- **Self-speculation / Medusa** — extra decoding heads on the target model predict
  several future tokens (no separate draft model).
- **EAGLE**, **Lookahead decoding** — feature-level / n-gram-based drafting.

Speedup depends on the **acceptance rate** (how often the draft matches), which
depends on draft quality and how "predictable" the text is.

## 7. FlashAttention — IO-aware exact attention (engineering view)

Standard attention materializes the `N×N` score matrix in HBM ⇒ O(N²) memory and
many slow DRAM round-trips — the long-context bottleneck. **FlashAttention** never
writes the score matrix to global memory: it **tiles** Q, K, V, computes softmax
**online** (running max/sum/output with rescaling) entirely in **SRAM**, so memory
is **O(N)** and the kernel is IO-optimal and *exact*. (The algorithm is derived
and run on CPU in `04.triton/04.fused_attention.py`.)

For inference specifically:
- **Prefill** uses FlashAttention to process long prompts without the O(N²)
  memory blowup.
- **Decode** uses specialized variants — **FlashDecoding** / **PagedAttention
  kernels** — that parallelize the attention over the (long) KV sequence for a
  single query token, and read the **paged** KV cache directly.
- **FlashAttention-2/3** improve work partitioning and use Hopper features (async,
  fp8) for higher utilization.

It's foundational: KV cache, paged attention, and long context all rely on an
attention kernel that doesn't choke on sequence length.

## 8. Putting it together — the modern serving stack

A request flows through a system like **vLLM / TGI / TensorRT-LLM / SGLang**:

```
request → scheduler (continuous batching, chunked prefill, prefix-cache lookup)
        → prefill  (FlashAttention; fill paged KV blocks)
        → decode loop:
              continuous batch of many requests' single tokens
              quantized weights (INT4/INT8/FP8) read from HBM
              paged-attention kernel reads each request's KV blocks
              [optional] speculative decoding (draft + verify)
        → detokenize / stream tokens out; free KV blocks on EOS
```

| Technique | Attacks | Typical engine |
|---|---|---|
| KV cache | redundant recompute | all |
| GQA/MQA | KV memory size | model architecture |
| Paged attention | KV fragmentation | vLLM, TensorRT-LLM, SGLang |
| Continuous batching | GPU idle on ragged lengths | vLLM, TGI, TensorRT-LLM |
| Quantization (INT4/8, FP8, GGUF) | bandwidth & footprint | vLLM, llama.cpp, TensorRT-LLM |
| Speculative decoding | one-token-per-pass waste | vLLM, TGI, TensorRT-LLM, Medusa |
| FlashAttention | O(N²) attention memory | all |

(The serving engines themselves are catalogued in `07.frameworks/serving-inference/`.)
