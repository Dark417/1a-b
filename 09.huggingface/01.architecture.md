> `tokenizers`, `accelerate`, `peft`, `trl`, `diffusers`, `optimum`, `gradio`)

## 1. The mental model: a hub-and-spoke ecosystem

There is one **data plane** (the Hub: a git+LFS/Xet artifact store) and a set of
**libraries** that each own one layer of the ML lifecycle but all speak the same
two dialects: *repo ids* (`org/name`) and the *shared local cache*. Nothing is
monolithic — you can use `datasets` without `transformers`, or `tokenizers`
standalone — but they compose because they agree on those two contracts.

```
                         ┌───────────────────────────────────────┐
                         │            HUGGING FACE HUB            │
                         │  models · datasets · spaces · papers   │
                         │   git repos + LFS/Xet + model cards    │
                         └───────────────────────────────────────┘
                                  ▲  download / upload  ▲
            huggingface_hub  ─────┘  (the ONLY client)  └─────  (used by ALL below)
                                          │
        ┌───────────────┬────────────────┼────────────────┬────────────────┐
        ▼               ▼                ▼                ▼                ▼
   ┌─────────┐    ┌──────────┐     ┌────────────┐   ┌──────────┐    ┌───────────┐
   │datasets │    │tokenizers│     │transformers│   │diffusers │    │ sentence- │
   │ (data)  │───▶│ (text →  │────▶│  (models,  │   │ (image/  │    │transformers│
   │ Arrow   │    │  tokens) │     │ pipelines, │   │  audio   │    │(embeddings)│
   │ stream  │    │  BPE/WP  │     │  Trainer,  │   │  gen)    │    └───────────┘
   └─────────┘    └──────────┘     │ generation)│   └──────────┘
                                   └─────┬──────┘
                  ┌────────────────┬─────┴──────┬───────────────┐
                  ▼                ▼            ▼               ▼
            ┌──────────┐    ┌──────────┐  ┌──────────┐   ┌──────────┐
            │accelerate│    │  peft    │  │   trl    │   │ optimum  │
            │(device + │    │(LoRA /   │  │(SFT/DPO/ │   │(ONNX/    │
            │ mixed-pr │    │ adapters)│  │ RLHF on  │   │ OpenVINO/│
            │ + multi- │    │          │  │ top of   │   │ quantize │
            │  GPU)    │    │          │  │  Trainer)│   │  export) │
            └──────────┘    └──────────┘  └──────────┘   └──────────┘
                                   │
                                   ▼  serve
                     ┌───────────────────────────────┐
                     │ gradio / Spaces · TGI · pipeline│
                     └───────────────────────────────┘
```

Read it top-down: **the Hub stores artifacts**, `huggingface_hub` is the single
client every other library calls to fetch/push them, and the spokes are
specializations — data, tokenization, modelling, training adapters, and serving.

## 2. Layer-by-layer: who owns what

| Library | Layer | Core abstractions | Depends on |
|---|---|---|---|
| **huggingface_hub** | transport / Hub client | `hf_hub_download`, `snapshot_download`, `HfApi`, `login`, `ModelCard` | — (stdlib + `requests`) |
| **tokenizers** | text → token ids | `Tokenizer`, `models.BPE/WordPiece`, `trainers`, `pre_tokenizers` | (Rust) |
| **datasets** | data access | `Dataset`, `DatasetDict`, `IterableDataset`, `load_dataset`, Arrow memory-map | `huggingface_hub`, `pyarrow` |
| **transformers** | models & training | `AutoModel*`, `AutoTokenizer`, `pipeline`, `Trainer`, `GenerationMixin` | `huggingface_hub`, `tokenizers`, `torch` |
| **accelerate** | hardware abstraction | `Accelerator`, `notebook_launcher`, config; powers `Trainer` internally | `torch` |
| **peft** | parameter-efficient tuning | `LoraConfig`, `get_peft_model`, `PeftModel` | `transformers`, `accelerate` |
| **trl** | preference/RL training | `SFTTrainer`, `DPOTrainer`, `PPOTrainer`, `GRPOTrainer` | `transformers`, `peft`, `accelerate` |
| **diffusers** | diffusion models | `DiffusionPipeline`, `UNet2DModel`, schedulers (`DDPMScheduler`) | `transformers`, `accelerate` |
| **optimum** | hardware/runtime export | `ORTModel*` (ONNX Runtime), OpenVINO, quantization, BetterTransformer | `transformers` |
| **sentence-transformers** | embeddings | `SentenceTransformer`, `util.semantic_search`, `CrossEncoder` | `transformers`, `torch` |
| **gradio** | UI / Spaces | `Interface`, `Blocks`, `ChatInterface` | — |
| **evaluate** | metrics | `evaluate.load("accuracy")`, `Metric.compute` | `datasets` |

The dependency arrows matter: **`peft`, `trl`, and `diffusers` are *extensions*
of `transformers`**, not parallel stacks. They take a `transformers` model and
wrap or train it. `accelerate` sits *under* `Trainer` — you get it for free, and
reach for it directly only when writing a custom training loop.

## 3. The keystone: `Auto*` class resolution

The single most important mechanism in `transformers` is the **`Auto*` factory**.
You never need to know that `bert-base-uncased` is a `BertModel` — you call
`AutoModel.from_pretrained("...")` and the right class is chosen *from the repo's
`config.json`*:

```
AutoModel.from_pretrained("prajjwal1/bert-tiny")
        │
        ├─ huggingface_hub.hf_hub_download("…/config.json")   # fetch metadata
        │
        ├─ read config.json:  {"model_type": "bert",
        │                       "architectures": ["BertModel"], …}
        │
        ├─ CONFIG_MAPPING["bert"]      → BertConfig            # model_type → config class
        ├─ MODEL_MAPPING[BertConfig]   → BertModel            # config → model class
        │
        ├─ download model.safetensors (preferred) or pytorch_model.bin
        └─ instantiate BertModel(config) and load weights      → ready model
```

Key facts:

- **`model_type`** in `config.json` is the routing key. Each architecture
  registers `(config, model, tokenizer)` triples in mapping dicts.
- The `Auto*` family has **task-specific heads**: `AutoModel` (bare encoder /
  backbone, no head), `AutoModelForSequenceClassification`,
  `…ForTokenClassification`, `…ForQuestionAnswering`, `…ForCausalLM`,
  `…ForSeq2SeqLM`, `…ForMaskedLM`. Pick the head matching your task; the body
  weights load from the checkpoint, the head is fresh unless the checkpoint
  already has one.
- **`AutoTokenizer`** does the same for tokenizers (reads `tokenizer_config.json`
  → fast Rust tokenizer when `tokenizer.json` is present, else a Python "slow"
  one). **`AutoConfig`**, **`AutoFeatureExtractor`/`AutoImageProcessor`**, and
  **`AutoProcessor`** (multimodal) round out the family.
- `trust_remote_code=True` lets a repo ship a *custom* architecture as Python in
  the repo — convenient but it executes arbitrary code, so only enable it for
  repos you trust.

This is why the Hub + `transformers` feel like one system: `config.json` is a
**contract**, and `Auto*` is the dispatcher that reads it.

## 4. Pipelines vs. manual model driving

There are three altitudes at which you can use a model. Pick by how much control
you need.

### (a) `pipeline` — highest level, "just do the task"
```python
from transformers import pipeline
clf = pipeline("sentiment-analysis", model="prajjwal1/bert-tiny")
clf("I love this!")        # → [{'label': 'LABEL_1', 'score': 0.51}]
```
A `pipeline` bundles **tokenizer + model + task-specific pre/post-processing**.
It picks a sensible default model per task if you omit `model=`. Use it for
inference, demos, and quick baselines. ~40 task strings exist
(`text-generation`, `ner`, `question-answering`, `summarization`,
`zero-shot-classification`, `automatic-speech-recognition`, `image-classification`, …).

### (b) `AutoModel*` + `AutoTokenizer` — manual, full control
```python
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)
ids = tok("Hello", return_tensors="pt")
out = model.generate(**ids, max_new_tokens=10)     # you own every knob
tok.decode(out[0])
```
Use when you need custom decoding, access to `hidden_states`/`attentions`,
batching control, custom heads, or to plug into `Trainer`/`peft`/`trl`.

### (c) `Trainer` (or a raw `accelerate` loop) — training
`Trainer` wraps the optimizer/scheduler/eval/checkpoint/logging loop and uses
`accelerate` under the hood for device + mixed precision + distributed. Drop to a
hand-written `accelerate` loop only for non-standard objectives.

> Rule of thumb: **inference → pipeline; control → Auto*; training → Trainer**;
> custom objective → accelerate loop; PEFT/preference training → peft/trl on top.

## 5. The cache & download workflow (cross-library)

Every library funnels downloads through `huggingface_hub` into **one shared
cache** (`$HF_HOME/hub`, default `~/.cache/huggingface/hub`). The flow on a
`from_pretrained` / `load_dataset` call:

```
from_pretrained(repo_id, revision="main")
   │
   ├─ resolve revision → commit SHA (HEAD of branch, or the tag/SHA you pinned)
   │     (skipped entirely if HF_HUB_OFFLINE=1 → cache-only)
   │
   ├─ for each needed file:
   │     ├─ is blob <sha256> already in cache?  ── yes ─▶ use it (symlink)
   │     └─ no ─▶ download to tmp, verify hash, atomic-rename into blobs/,
   │              symlink under snapshots/<commit-sha>/
   │
   └─ load weights from the snapshot dir (mmap for safetensors)
```

Consequences worth internalizing:
- **Content-addressed + symlinked** → two revisions sharing a file share one
  blob on disk; pinning many revisions is cheap.
- **Resumable + atomic** → interrupted downloads resume; you never see a
  half-written file.
- **Offline reproducibility** → pre-warm the cache once, then set
  `HF_HUB_OFFLINE=1` (and pin commit SHAs) for byte-identical, network-free runs.
- `HF_HUB_ENABLE_HF_TRANSFER=1` swaps in the Rust `hf_transfer` downloader for
  faster large-file pulls. See [`00.manifest.md`](00.manifest.md) §6 for the full
  env-var table and cache layout.

## 6. Two end-to-end traces (how the spokes collaborate)

**Fine-tune a classifier and serve it:**
```
datasets.load_dataset      →  Dataset (Arrow, memory-mapped)
        ↓ .map(tokenize)      uses AutoTokenizer (← tokenizers, ← hub)
AutoModelForSequenceClassification.from_pretrained   (← hub)
        ↓
Trainer(model, args, train_ds, eval_ds, compute_metrics)   (← accelerate under the hood, ← evaluate)
        ↓ .train() / .evaluate()
trainer.push_to_hub()      →  weights + card land on the Hub  (← hub)
        ↓
pipeline("text-classification", model="me/my-model")  /  Gradio Space  /  TGI
```

**LoRA-tune a generative model with TRL:**
```
load_dataset →  SFTTrainer(model, peft_config=LoraConfig(...), ...)   (trl wraps Trainer; peft wraps the model; accelerate runs it)
        ↓ .train()      (only the LoRA adapter weights update)
model.save_pretrained()  →  tiny adapter (MBs, not GBs)
        ↓
PeftModel.from_pretrained(base, adapter)  →  merge_and_unload()  →  push_to_hub  →  serve
```

Each arrow is a library boundary, and every arrow crossing the Hub goes through
`huggingface_hub`. That is the whole architecture: **one store, one client, many
specialized spokes that agree on repo ids and a shared cache.**

## 7. When to add `optimum` / `gradio`

- **optimum** is the *production-export* spoke: convert a `transformers` model to
  ONNX Runtime / OpenVINO / TensorRT, or apply graph optimizations and
  static/dynamic quantization, behind the same `from_pretrained` API
  (`ORTModelForSequenceClassification`). Reach for it when CPU/edge latency or a
  non-PyTorch runtime matters. (Doc-only here; see `hub/` and the workflow doc.)
- **gradio** is the *UI* spoke and the runtime behind most **Spaces**. A few
  lines (`gr.Interface(fn, inputs, outputs).launch()`) turns any function — e.g.
  a `pipeline` call — into a shareable web app. Spaces is just a Hub repo that
  runs your Gradio/Streamlit/Docker app.
