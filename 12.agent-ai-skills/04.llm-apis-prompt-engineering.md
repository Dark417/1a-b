# 04 · LLM APIs & Prompt Engineering

> Skill #04 (Tier 1 — Core). *Provider APIs, tool calling, structured output, and
> measured prompt design.* In ~80% of postings; prompt-engineering openings up
> 135.8% YoY (R1). See the rationale in
> [`../11.agent-ai-engineer/03.ranked-skills.md`](../11.agent-ai-engineer/03.ranked-skills.md).

---

## 1. What it is

Fluency with hosted-model APIs — Anthropic (Claude), OpenAI, Google (Gemini) —
covering sync + streaming requests, token counting, context windows, system
prompts, **function/tool calling**, **structured output**, prompt caching, and
multi-turn state. Plus prompt *engineering* as a measured discipline: designing,
testing, and **optimizing** prompts against evals rather than tuning by vibes.

It exists because the LLM API is **the daily surface of most applied AI work** —
the fastest path from idea to working product. The model is a function call; the
craft is in the prompt, the schema, the tool definitions, the state management,
and the resilience around that call.

## 2. Why employers want it

It's the most immediately productive AI skill and one of the fastest-growing job
categories (R1). The signal:

- **You ship features fast.** Idea → working prototype in hours, because you know
  the API surface cold.
- **You make output reliable.** Structured outputs + tool calling turn a chatty
  model into a typed, callable component you can build a system on.
- **You optimize, not guess.** You A/B prompts against an eval set, measure
  faithfulness/accuracy/cost, and iterate — the difference between a demo and a
  product (links to [`07.evaluation-llm-testing.md`](07.evaluation-llm-testing.md)).

## 3. Mental model

Everything goes through **one endpoint** (`/v1/messages` for Claude): a list of
`messages` (alternating user/assistant), an optional `system` prompt, and
parameters. Tool use, structured output, streaming, and caching are *features of
that one call*, not separate APIs.

```
system prompt  ─┐
tool defs      ─┼─► /v1/messages ─► response: [text | thinking | tool_use] blocks
messages[]     ─┘                     + stop_reason + usage(tokens)
```

The four levers you pull:

- **System prompt** — the durable role/constraints/format. Keep it *frozen* so
  prompt caching can reuse it (a single byte change invalidates the cached
  prefix — see [`11.mlops-llmops.md`](11.mlops-llmops.md) on cost control).
- **Tool calling** — give the model typed tools; it emits a `tool_use` block,
  you execute and return a `tool_result`, it continues. This is the bridge from
  *chat* to *doing things* (and the foundation of agents, skill #06).
- **Structured output** — constrain the response to a JSON schema so you get a
  validated object, not prose you have to parse hopefully.
- **Decoding/thinking controls** — on modern Claude models, `thinking:
  {"type": "adaptive"}` lets the model decide how much to reason; `output_config:
  {"effort": ...}` trades quality for cost/latency.

**Prompt-engineering principles that actually move metrics**: be specific and
give the desired *format*; show 1–3 examples (few-shot) for tricky tasks; let
the model reason before answering on hard tasks; ground with retrieved context
(RAG) instead of hoping it "knows"; put stable content first for caching; and
**measure** — never ship a prompt change you didn't eval.

## 4. The landscape

**Providers & SDKs.** Anthropic (`anthropic` Python / `@anthropic-ai/sdk`),
OpenAI, Google Gemini, plus open-model runtimes that mimic these APIs
(Ollama, vLLM's OpenAI-compatible server, TGI). Cross-provider routers:
LiteLLM, OpenRouter.

**Core request features** (Claude, current models like `claude-opus-4-8`):

| Feature | What it does | When to use |
|---|---|---|
| Streaming | tokens as they generate | chat UIs, long outputs (avoids timeouts) |
| Tool use | typed function calling + agentic loop | actions, retrieval, structured extraction |
| Structured output | response constrained to a JSON schema | typed pipelines, no fragile parsing |
| Prompt caching | reuse a stable prefix at ~0.1× cost | large shared system prompts, RAG context |
| Adaptive thinking | model self-decides reasoning depth | hard reasoning/agentic tasks |
| Batches | async bulk at 50% price | non-latency-sensitive jobs |
| Token counting | exact pre-flight token count | budgeting, truncation decisions |

**Prompting techniques.** Zero/few-shot, chain-of-thought ("think step by
step"), self-consistency (sample N, vote), ReAct (reason+act with tools),
role/persona prompting, output-format pinning, delimiters/XML tags for structure,
and **prompt optimization** frameworks (DSPy compiles/optimizes prompts against a
metric; see [`29.orchestration-workflow-frameworks.md`](29.orchestration-workflow-frameworks.md)).

**Resilience (carries over from skill #01).** Timeouts, retries with backoff,
rate-limit handling (the SDK retries 429/5xx automatically), idempotency, and
bounded concurrency for fan-out.

## 5. Worked example

A typed extraction call with **structured output** plus a **tool-calling** loop —
the two patterns that turn an LLM into a reliable component. Uses the Anthropic
Python SDK and the current model `claude-opus-4-8`.

```python
"""llm_api_demo.py — structured output + tool calling with the Anthropic SDK."""
from anthropic import Anthropic

client = Anthropic()  # reads ANTHROPIC_API_KEY from the environment

# --- 1. Structured output: response constrained to a JSON schema ---
SCHEMA = {
    "type": "object",
    "properties": {
        "name": {"type": "string"},
        "email": {"type": "string", "format": "email"},
        "plan": {"type": "string", "enum": ["free", "pro", "enterprise"]},
        "wants_demo": {"type": "boolean"},
    },
    "required": ["name", "email", "plan", "wants_demo"],
    "additionalProperties": False,
}

resp = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=512,
    output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
    messages=[{
        "role": "user",
        "content": "Extract: Jane Doe (jane@co.com) wants Enterprise and a demo.",
    }],
)
import json
data = json.loads(next(b.text for b in resp.content if b.type == "text"))
print(data["plan"])        # "enterprise"  -> a validated object, not hopeful parsing

# --- 2. Tool calling: a manual agentic loop (full control over execution) ---
TOOLS = [{
    "name": "get_weather",
    "description": "Get current weather. Call this whenever the user asks about weather.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

def get_weather(city: str) -> str:        # your real implementation goes here
    return f"18C and clear in {city}"

messages = [{"role": "user", "content": "What's the weather in Paris?"}]
while True:
    resp = client.messages.create(
        model="claude-opus-4-8", max_tokens=512, tools=TOOLS, messages=messages,
    )
    if resp.stop_reason != "tool_use":
        break
    messages.append({"role": "assistant", "content": resp.content})
    results = []
    for block in resp.content:
        if block.type == "tool_use":          # the model asked to call a tool
            out = get_weather(**block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,       # must echo the tool_use id
                "content": out,
            })
    messages.append({"role": "user", "content": results})

print(next(b.text for b in resp.content if b.type == "text"))
```

Why this is idiomatic: the schema makes extraction a *contract* (the API
guarantees valid JSON), and the loop appends `response.content` verbatim and
echoes each `tool_use_id` — the load-bearing details that make tool calling
work. (The SDK also offers a `tool_runner` that hides this loop; the manual form
is shown because it's what you reach for when you need approval gates or custom
logging.)

## 6. How to learn it

**Beginner (0–3 months).** Read your provider's quickstart; build a CLI chatbot
with streaming and multi-turn state; count tokens; handle errors. *Milestone:* a
streaming chat app with system prompt, retries, and token budgeting.

**Intermediate / job-ready (3–9 months).** Master tool calling and structured
output; add prompt caching for a large shared prefix; write 5–10 prompts and
**eval** them on a small labeled set; learn few-shot/CoT/ReAct. *Milestone:* a
typed extraction or tool-using feature with an eval harness gating prompt
changes.

**Expert (9+ months).** Optimize prompts with DSPy or systematic A/Bs; build
multi-provider fallback/routing; tune cost via caching + model selection + batch;
design prompts robust to injection (see [`19.safety-alignment-guardrails.md`](19.safety-alignment-guardrails.md)).
*Milestone:* a production LLM feature with measured quality, bounded cost, and a
prompt-regression suite in CI.

## 7. Interview signals

- **"How do you get reliable JSON out of an LLM?"** Structured output /
  `output_config.format` (schema-constrained) or strict tool use — not prompt-
  and-pray; validate with pydantic; handle the refusal/`max_tokens` edge cases.
- **"Walk me through tool calling."** Define typed tools → model emits
  `tool_use` → execute → return `tool_result` with the matching id → loop until
  `end_turn`. Mention parallel tool calls and approval gates for destructive ops.
- **"How would you cut the cost of this LLM feature in half?"** Prompt caching
  for the shared prefix, right-size the model (Haiku vs Opus), batch the non-
  urgent calls, trim the prompt, cap `max_tokens` — and *measure* each.
- **"How do you know a prompt change is an improvement?"** An eval set with a
  metric (accuracy / LLM-as-judge / faithfulness), run before/after, gate in CI —
  not eyeballing one example.
- **"Defend against prompt injection in a tool-using app."** Treat retrieved/user
  content as untrusted, keep operator instructions in the system channel, gate
  side-effecting tools, validate tool inputs.
