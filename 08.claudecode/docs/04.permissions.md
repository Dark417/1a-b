# 04. Permissions, sandboxing & hooks

> Clean-room: built from the public Claude Code settings & hooks docs. Code:

> [`../ruby/permissions.rb`](../ruby/permissions.rb). Citations:
> [`07.references.md`](07.references.md).

A coding agent runs commands and edits files on your machine, so **trust and
control** are first-class. Claude Code gates every potentially-dangerous tool
call behind a permission system, configured in `settings.json`, and lets you
extend it with hooks.

## The three decisions: allow / ask / deny

Each tool call resolves to one of:

* **allow** — run it without prompting.
* **ask** — prompt the user to approve (the default for risky actions).
* **deny** — refuse it outright.

**Deny always wins over allow.** Rules from every settings scope are *merged*
(not overridden), so a project deny rule can't be lost by a user-level allow.

### Rules and allowlist patterns

Rules are `Tool(pattern)` strings. The pattern matches a *signature* built from
the tool name and its key argument, with `*`/`**` wildcards:

```jsonc
{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Read(~/.zshrc)"
    ],
    "deny": [
      "Bash(curl *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  }
}
```

The mini-agent models this directly. It builds a signature per call — `bash(<command>)`,
`<tool>(<path>)`, or `<tool>(<pattern>)` — and matches it against the allow/deny
lists with glob semantics:

```python
def tool_signature(name, args):
    if name == "bash":     return f"bash({args['command']})"
    if "path" in args:     return f"{name}({args['path']})"
    if "pattern" in args:  return f"{name}({args['pattern']})"
    return f"{name}()"
```

The decision order is: **deny → mode policy → read-only auto-allow → explicit
allow → mode auto-allow → ask** — deny first, ask as the safe fallback.

## Permission modes

A *mode* sets the baseline policy for a session:

| Mode | Behavior |
|---|---|
| **default** | Ask before risky (mutating) tools; read-only tools run freely. |
| **acceptEdits** | Auto-allow file writes/edits; still ask for other risky tools (e.g. bash). |
| **plan** | **Read-only.** Explore and propose a plan, but *block every mutating tool* — no writes, no shell side-effects — until you approve and switch out of plan mode. |
| **bypassPermissions** | Allow everything. For trusted sandboxes / CI only. |

The mini-agent's gate encodes each mode. Plan mode, for example:

```python
if mode is Mode.PLAN and not (read_only or name in READ_ONLY_TOOLS):
    return Decision.DENY          # only read-only exploration is permitted
```

This is why **plan mode** is the safe way to let an agent investigate a large
change before it touches anything: the model can read, grep, and reason, but the
harness refuses any write until you've reviewed the plan.

## Sandboxing

Permissions decide *whether* a call runs; **sandboxing** bounds *what it can
reach* if it does. In the mini-agent every path resolves under a workspace root
and `..` escapes are rejected ([`03.tools.md`](03.tools.md)). Real agents layer
on OS-level isolation, network egress controls, and read-only mounts. The two
work together: a denied call never runs, and an allowed call can't wander
outside the project.

## Hooks

**Hooks** are user-defined commands (or HTTP endpoints / prompts / sub-agents)
that fire at points in the agent's lifecycle, letting you automate validation,
logging, blocking, or context injection deterministically — *outside* the
model's control. They're configured in `settings.json` under `hooks`, grouped by
event and an optional tool **matcher**:

```jsonc
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "if": "Bash(rm *)",
        "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh"
      }]
    }]
  }
}
```

### Key events

| Event | Fires | Can it block? |
|---|---|---|
| **PreToolUse** | Before a tool executes. | **Yes** — can `allow` / `deny` / `ask`, or rewrite the tool input. |
| **PostToolUse** | After a tool succeeds. | No — but can add context or replace the tool output. |
| **UserPromptSubmit** | Before the model sees a new user prompt. | Yes — can block or inject context. |
| **Stop** | When the model finishes a turn. | Yes — can force the conversation to continue. |
| **SessionStart / SessionEnd** | Once per session. | No — used to load/save context. |

### How a hook decides

A `command` hook receives a JSON payload on stdin (`tool_name`, `tool_input`,
`cwd`, `permission_mode`, …) and signals its decision via **exit code** or
**JSON output**:

* exit `0` → success; any JSON output is parsed.
* exit `2` → **blocking error**; stderr is sent to the model and the action is blocked.
* other → non-blocking error; logged, action continues.

A `PreToolUse` hook can return structured JSON to allow/deny:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Destructive rm -rf blocked"
  }
}
```

Hooks are the **deterministic** complement to the model's judgment: where the
permission gate asks the model's harness to allow/ask/deny per policy, a hook
lets *you* run arbitrary code to enforce invariants (auto-format after every
edit, run lint before a commit, block `rm -rf`, redact secrets) regardless of
what the model decides.
