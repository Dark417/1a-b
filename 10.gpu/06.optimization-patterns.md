# 06 · GPU Optimization Patterns — coalescing, banks, tiling, warps, roofline

> The reusable techniques that separate a slow kernel from a fast one. Each is a
> direct response to the architecture in `01.gpu-architecture.md`: respect the
> memory hierarchy, feed the warp efficiently, and reuse data. The runnable
> embodiments live in `03.numba-cuda/` (tiling, reductions) and `04.triton/`
> (fused softmax, blocked matmul, online-softmax attention).

---

## 1. Memory coalescing — the single most important rule

Global memory is read/written in **transactions** of 32/64/128 bytes. When the 32
threads of a warp issue loads, the hardware merges them into as few transactions
as possible. The rule:

> **Make consecutive threads access consecutive addresses.** Map `threadIdx.x`
> (the fastest-varying lane) to the **innermost, contiguous** array dimension.

```
Coalesced (good):   thread t reads A[t]        → 1 transaction serves 32 threads
Strided (bad):      thread t reads A[t * 32]   → 32 separate transactions
```

A coalesced access uses 100% of each transaction's bytes; a scattered one can
waste 31/32 of the bandwidth. On a memory-bound kernel (most of DL), this is the
difference between fast and unusable.

Practical corollaries:
- For a **row-major** matrix, let `threadIdx.x` index **columns** (contiguous),
  not rows. Transposed access patterns are the usual culprit — stage through
  shared memory to fix them (a *coalesced* global read + *transposed* shared
  read).
- **Alignment** matters: 128-byte-aligned base addresses let transactions line up.
- `vector_add` (`03.numba-cuda/01`) and the Triton kernels are coalesced by
  construction because lane `i`/`offs` indexes contiguous elements.

## 2. Shared-memory bank conflicts

Shared memory is split into **32 banks**, 4 bytes wide, interleaved by word. A
warp can read 32 words in one cycle **iff** they fall in 32 different banks. If
two threads hit the same bank (different addresses), the accesses **serialize** —
a *k-way bank conflict* is k× slower.

```
addr = base + index*stride;  bank = (addr/4) % 32
stride 1  → threads hit banks 0,1,2,…,31  → conflict-free
stride 32 → all threads hit bank 0        → 32-way conflict (worst case)
```

Fixes:
- Avoid power-of-two strides that alias banks; the classic trick is **padding** a
  shared array's row by one element (`shared[TILE][TILE+1]`) so column accesses
  fall in different banks.
- **Broadcast** (all threads read the *same* address) is conflict-free by special
  case.
- The halving-stride reduction in `04.reduction.py` keeps active threads
  contiguous partly to stay conflict-free.

## 3. Tiling / blocking — the data-reuse pattern

Naive matmul reads each element of A and B from global memory `K` times. **Tiling**
loads a small TILE×TILE square of A and B into **shared memory** once, lets the
whole block reuse it, then slides along K. Global traffic drops by a factor of
TILE. The recipe (see `03.numba-cuda/03.matmul_tiled.py`):

```
for each K-tile:
    cooperatively load A-tile and B-tile into shared memory
    __syncthreads()                      # tile fully loaded
    each thread does TILE multiply-adds from shared memory (fast)
    __syncthreads()                      # done before overwriting the tile
accumulate in a register; write C once at the end
```

This generalizes far beyond matmul: **stage reused data in shared memory, sync,
compute, sync.** It is *the* fundamental GPU optimization — turning a
memory-bound kernel into a compute-bound one by raising **arithmetic intensity**
(FLOPs per byte). Triton's blocked matmul (`04.triton/03`) does the same thing,
with the compiler managing the shared memory and adding **grouped program
ordering** to also improve **L2** reuse across tiles.

## 4. Warp-level primitives

Threads in a warp run in lockstep, so they can exchange register values directly —
**no shared memory, no barrier**. These are the fastest way to communicate within
32 lanes:

- `__shfl_sync(mask, val, src)` — read lane `src`'s `val`.
- `__shfl_down_sync` / `__shfl_xor_sync` — shift/butterfly patterns for reductions
  and scans.
- `__ballot_sync` / `__any_sync` / `__all_sync` — vote across the warp.
- `__reduce_add_sync` (Ampere+) — a single-instruction warp reduction.

A **warp reduction** with `__shfl_down_sync` collapses 32 values to 1 in 5 steps
with zero shared memory — the inner loop of fast reductions and the partial-sum
step of attention/softmax kernels. (Numba exposes `cuda.shfl_down_sync` etc.)

---

## 5. Reductions — the parallel-tree pattern

Reducing N values (sum, max, argmax) with an associative operator is the canonical
parallel pattern: a **tree** of `log₂N` levels instead of N serial steps. The
textbook block reduction (`03.numba-cuda/04.reduction.py`):

1. each thread loads one (or several, grid-stride) elements into shared memory;
2. halving-stride loop: `for s = blockDim/2; s>0; s/=2: if tid<s: sdata[tid] += sdata[tid+s]; __syncthreads()`;
3. thread 0 writes the block's partial; finish partials with a second launch or
   `atomicAdd`.

Mark Harris's "Optimizing Parallel Reduction" walks through 7 successive
speedups: avoid divergent modulo, sequential addressing (no bank conflicts), first
add during load, **unroll the last warp** with shuffles, full unrolling via
templates, multiple elements per thread. The same skeleton powers `softmax`
(max-reduce + sum-reduce, `03.numba-cuda/05`) and the online-softmax in attention
(`04.triton/04`).

## 6. Occupancy & register pressure (recap, applied)

From section 01: occupancy = resident warps / max warps, capped by whichever of
**registers/thread**, **shared memory/block**, or **block slots** runs out first.
Tuning levers:
- Reduce registers per thread (smaller loop bodies, `__launch_bounds__`) to fit
  more warps — but not at the cost of spilling to local (global) memory.
- Smaller shared-memory tiles fit more blocks; larger tiles reuse more data.
  There's a sweet spot — autotune it.
- Remember **occupancy isn't the goal**: enough to hide latency, plus high
  instruction-level parallelism (independent work per thread), can beat max
  occupancy (Volkov).

## 7. The roofline model — is my kernel compute- or memory-bound?

The roofline plots attainable performance against **arithmetic intensity** `I`
(FLOPs per byte of DRAM traffic):

```
  attainable FLOP/s = min( peak_FLOP/s ,  peak_BW × I )
```

```
 FLOP/s
   ▲           ________________  peak compute (flat roof)
   │          /
   │        /  ← memory-bound region (slope = peak bandwidth)
   │      /
   │    /
   │  /
   └────────────────────────────► arithmetic intensity I (FLOP/byte)
         I_ridge
```

- Left of the **ridge point** `I_ridge = peak_FLOP / peak_BW`: you're
  **memory-bound** — limited by `peak_BW × I`. Raise `I` (fuse ops, tile for
  reuse, use lower-precision/quantized data) or improve coalescing.
- Right of the ridge: **compute-bound** — limited by FLOP/s. Use Tensor Cores
  (fp16/bf16, `tl.dot`), reduce wasted work.

Most DL pointwise/normalization/attention kernels sit on the **memory-bound
slope**, which is *why* fusion and tiling (raising `I`) are the dominant wins —
and why `torch.compile` and FlashAttention matter so much. Measure `I` with the
profiler / Nsight Compute and locate yourself on the roof before optimizing.
