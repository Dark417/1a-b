## 1. What it is

**GPU programming** is writing code that runs on the *massively parallel*
architecture of a graphics processor — thousands of threads executing the same
program over different data (SIMT: single-instruction, multiple-threads).
**CUDA** is NVIDIA's platform and C/C++ dialect for it; **Triton** is a
Python-embedded language for writing GPU kernels at a higher level. The skill is
writing and *optimizing* **kernels** — the small programs that do the actual math
— and understanding the hardware well enough to make them fast.

It exists because the entire deep-learning revolution runs on GPUs, and the gap
between a naive kernel and an optimized one is often **10–100×**. Frameworks hide
this most of the time, but the biggest latency/cost wins — a fused attention
kernel, a custom quantized matmul, a faster sampler — come from someone who can
drop below PyTorch into the kernel layer. That person is rare and expensive.

## 2. Why employers want it

Section 11 ranks this #23 and flags it as **gating performance roles**: required
at NVIDIA (S9/S10) and inference/perf teams (S28), a strong differentiator
everywhere else. The signal:

- **You can squeeze the hardware.** FlashAttention, paged-attention, fused kernels
  — the techniques that make modern LLMs feasible are *kernel* work. You can write
  or at least read and optimize them.
- **You understand the memory hierarchy.** You know that GPU performance is
  usually **memory-bound**, not compute-bound, and you optimize data movement, not
  just FLOPs.
- **You can profile.** You read Nsight/`ncu` output, find the bottleneck
  (occupancy? bandwidth? bank conflicts?), and fix it with evidence.
- **You bridge research and silicon.** You make a new architecture actually fast,
  not just correct on paper.

## 3. Mental model

**The hardware, bottom-up.** A GPU is a grid of *Streaming Multiprocessors* (SMs),
each running many threads. You launch a **grid** of **blocks** of **threads**;
threads run in lock-step groups of 32 called **warps**.

```
  GRID  ─┬─ BLOCK 0 ─┬─ thread 0,1,2,…  (a block runs on ONE SM,
         │           │                   threads share fast SHARED memory)
         ├─ BLOCK 1 ─┤
         └─ …        └─ warp = 32 threads executing in lock-step (SIMT)

  MEMORY HIERARCHY (fast+small → slow+big):
    registers   (per-thread, ~fastest)
    shared mem  (per-block, ~100s of KB, programmer-managed cache — KEY lever)
    L2 cache    (per-GPU)
    global mem  (HBM, GBs, ~1000+ GB/s but ~100× slower than shared per access)
```

**The performance levers (memorize these):**

- **Coalescing.** When the 32 threads of a warp read *consecutive* global-memory
  addresses, the hardware merges them into one wide transaction. Strided/random
  access wastes bandwidth — often the #1 fix.
- **Shared memory + tiling.** Stage a *tile* of data from slow global memory into
  fast shared memory once, reuse it across many threads, write back once. This is
  how tiled matmul and FlashAttention win — they minimize global-memory traffic.
- **Occupancy.** How many warps are resident per SM (limited by registers/shared
  memory per thread). Higher occupancy hides memory latency by switching to
  another warp while one waits — but it's a means, not the goal.
- **Memory-bound vs compute-bound (the roofline).** Most DL kernels are
  *memory-bound*: bottlenecked by bandwidth, not arithmetic. **Operator fusion**
  (do more math per byte loaded) is the dominant optimization — fuse, don't
  launch ten kernels that each re-read the same tensor.
- **Divergence & bank conflicts.** Branches that split a warp serialize it;
  shared-memory accesses that collide on the same bank serialize too. Avoid both.
- **Tensor Cores.** Dedicated matrix-multiply units (FP16/BF16/FP8) — using them
  (via WMMA/cuBLAS/CUTLASS) is how you hit peak FLOPs.

## 4. The landscape

**Ways to write a GPU kernel (low → high level)**
- **CUDA C/C++** — full control, the ground truth. You manage threads, shared
  memory, synchronization. Maximum performance, maximum effort. Required at NVIDIA.
- **Triton** (OpenAI) — write kernels in Python at the *block* level; the compiler
  handles coalescing, vectorization, and much scheduling. ~80% of the perf for a
  fraction of the effort; the modern default for custom DL kernels (used in
  PyTorch's `torch.compile`/Inductor, vLLM, Unsloth). → see
  [`../10.gpu/04.triton`](../10.gpu/04.triton).
- **Numba CUDA** — write CUDA kernels in Python with `@cuda.jit`; great for
  learning and numeric kernels. → [`../10.gpu/03.numba-cuda`](../10.gpu/03.numba-cuda).
- **CuPy** — NumPy-compatible arrays on GPU; drop-in acceleration without writing
  kernels.
- **cuTile / Tile IR** (NVIDIA, newer) — tile-based programming model raising the
  abstraction further.

**Libraries you call instead of writing kernels**
- **cuBLAS** (GEMM/BLAS), **cuDNN** (DL primitives), **CUTLASS** (templated
  GEMM/conv building blocks, Tensor Cores), **Thrust** (parallel algorithms),
  **CUB** (block/warp primitives), **NCCL** (multi-GPU collectives → #24).

**Profiling & debugging**
- **Nsight Systems** (`nsys`) — timeline: where time goes across the app.
- **Nsight Compute** (`ncu`) — per-kernel deep dive: occupancy, memory throughput,
  warp stalls, the roofline. The tool that turns guessing into knowing.
- **`compute-sanitizer`** (race/memory errors), `cuda-gdb`.

**Cross-vendor / alternatives:** ROCm/HIP (AMD), oneAPI/SYCL (Intel), OpenCL,
Apple Metal, **OpenAI Triton** (also targets AMD), Mojo. NVIDIA + CUDA dominates;
the rest matter for specific hardware.

**Tradeoffs:** CUDA C++ = max control/perf, slow to write, NVIDIA-only. Triton =
near-CUDA perf, Pythonic, fast iteration — start here unless you need the last
10%. Call a library (cuBLAS/CUTLASS/cuDNN) before writing your own GEMM — you
rarely beat them. Write a custom kernel only for **fusion** or a primitive the
libraries don't provide.

## 5. Worked example

A **Triton vector-add kernel** — the "hello world" of GPU programming that still
teaches the real concepts: the grid launch, per-program block of work, masking the
tail, and coalesced loads/stores. Runs on any CUDA GPU (`pip install triton
torch`); the comments map each line to a hardware concept.

```python
"""triton_vecadd.py — element-wise add as a Triton kernel (idiomatic).
Requires a CUDA GPU. Run: python triton_vecadd.py
"""
import torch
import triton
import triton.language as tl


@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    # Each "program" (≈ a block) handles BLOCK contiguous elements.
    pid = tl.program_id(axis=0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)   # consecutive → COALESCED access
    mask = offsets < n                             # guard the ragged last block
    x = tl.load(x_ptr + offsets, mask=mask)        # coalesced global load
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)  # coalesced global store


def add(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    out = torch.empty_like(x)
    n = x.numel()
    # The grid: enough programs to cover n, one per BLOCK-sized chunk.
    grid = lambda meta: (triton.cdiv(n, meta["BLOCK"]),)
    add_kernel[grid](x, y, out, n, BLOCK=1024)
    return out


if __name__ == "__main__":
    torch.manual_seed(0)
    x = torch.rand(1_000_003, device="cuda")   # non-multiple of BLOCK → tests mask
    y = torch.rand_like(x)
    out = add(x, y)
    assert torch.allclose(out, x + y), "kernel wrong!"
    print("OK — Triton kernel matches torch. Now profile with: ncu python triton_vecadd.py")
```

Vector-add is *memory-bound* (3 global accesses per 1 add) — so the only thing
that matters is **coalesced** access and saturating bandwidth, which the
consecutive `offsets` achieve. The same skeleton — load a tile, compute, store —
scales up to fused softmax, layernorm, and (with shared-memory tiling) the matmul
and attention kernels that dominate LLM compute.

## 6. How to learn it

**Beginner (weeks).** Learn the execution model (grid/block/thread/warp) and the
memory hierarchy. Write vector-add and a reduction in Numba-CUDA or Triton. Read
the CUDA C++ Programming Guide's first chapters. *Milestone:* a correct kernel you
can explain in terms of coalescing and the grid.

**Job-ready (1–3 months).** Implement tiled matmul (shared memory), softmax,
layernorm, and a fused op in Triton; profile each with Nsight Compute and improve
it from the roofline (find: memory-bound? low occupancy? bank conflicts?). Write
the same matmul in CUDA C++ to feel the control. Integrate a custom kernel into
PyTorch (`torch.compile` / a custom op). *Milestone:* you take a slow op, profile
it, and make it measurably faster with a written before/after.

**Expert.** Write Tensor-Core kernels (CUTLASS/WMMA, mixed precision); implement
or optimize a real fused kernel (FlashAttention-style: online softmax + tiling to
avoid materializing the attention matrix); reason about persistent kernels,
warp-specialization, and the latest hardware (Hopper/Blackwell, FP8, TMA).
*Milestone:* a kernel that beats the library baseline on a real workload, with
Nsight evidence.

## 7. Interview signals

What's probed: do you understand the hardware, and can you reason about *why* a
kernel is slow?

**Q: "Why is most deep-learning code memory-bound, and what do you do about it?"**
Strong answer: arithmetic intensity (FLOPs per byte) is low for element-wise/
normalization/attention ops, so HBM bandwidth — not the ALUs — is the bottleneck
(the roofline's left side). Fix it with **operator fusion** (more compute per byte
loaded), **tiling** into shared memory to reuse data, and coalesced access. Cite
FlashAttention as the canonical example (fuse + tile to avoid writing the N×N
matrix to HBM).

**Q: "What is memory coalescing?"**
Strong answer: when the 32 threads of a warp access consecutive global addresses,
the hardware coalesces them into one wide transaction, using bandwidth
efficiently. Strided or random access fragments into many transactions, wasting
bandwidth — usually the first thing to fix. Tie it to laying out data so warp lane
i touches element i.

**Q: "What limits occupancy and why does it matter?"**
Strong answer: registers-per-thread and shared-memory-per-block cap how many warps
fit on an SM. More resident warps let the scheduler hide memory latency by
switching warps. But occupancy is a means, not the goal — a low-occupancy kernel
with great memory reuse can beat a high-occupancy one. Profile, don't assume.

**Q: "Walk me through optimizing a kernel."**
Strong answer: profile first (`ncu`) to find the bottleneck; check the roofline
(memory- vs compute-bound); then apply the matching fix — coalesce, tile into
shared memory, fuse, remove divergence/bank conflicts, use Tensor Cores — and
re-profile to confirm. Evidence-driven, not guess-driven.
